# SoloMap 本地项目远程控制方法论

## 这份方法论解决什么问题

独立开发者使用 Agent 推进项目时，不应该因为离开工作电脑就完全失去项目状态，也不应该为了远程可见而把代码、路线图、记忆和日志交给云端。

这份方法论定义 SoloMap 如何在“持续掌握项目”和“用户数据留在本地”之间做判断。

核心原则是：

> 远程工作台只延伸用户的观察与决策能力，不搬走本地项目的事实与执行权。

## 远程控制的真正目标

远程工作台不是为了让浏览器复制完整开发环境，而是让用户在离开电脑时仍能回答：

- Agent 是否还在推进。
- 哪个项目遇到阻塞。
- 是否需要补充目标或要求。
- 是否应该停止或重试。
- 哪个结果正在等待用户判断。

如果一项能力不能降低这些动作的阻力，就不应因为“网页也能展示”而进入官网。

## 双表面、一套项目心智

本地插件和官网工作台不是两套产品流程：

```text
本地插件：建立项目事实、执行和证据
官网工作台：远程观察、补充和控制
```

用户面对的仍是同一个项目、同一个下一步和同一条 Agent 对话。官网不得创造第二套路线图、任务状态或完成判断。

### 本地插件回答

- 项目实际是什么状态。
- Agent 真正执行了什么。
- 文件和路线图发生了什么变化。
- 验证证据是否足够。
- 一个动作是否安全、可执行。

### 官网工作台回答

- 现在是否有事情需要我处理。
- 哪些任务仍在推进。
- 我可以补充什么要求。
- 我可以请求停止、重试还是继续。
- 哪些详细内容必须回到本地查看。

## 本地事实原则

用户数据本地化不是存储偏好，而是产品责任边界。

下列内容属于项目事实，默认不得离开用户设备：

- 代码和项目文件。
- 路线图、完成标准和项目文档。
- Prompt、Agent 输出和完整对话。
- 终端日志、Git diff、文件名和验证证据。
- 项目记忆、附件、凭证和环境配置。

官网可以获得本地设备生成的最小状态投影，但不能因此成为这些事实的副本或恢复来源。

## 最小投影原则

远程界面只显示完成用户动作所必需的信息。

判断一项数据是否可以进入投影时，依次询问：

1. 没有这项数据，用户还能完成当前远程动作吗？
2. 能否把原始内容压缩成状态、数量或一句摘要？
3. 是否包含代码、路径、文件名、Prompt、日志或其他项目细节？
4. 是否由本地设备生成并在发送前完成脱敏？
5. 是否仍通过端到端加密传输？

只要第一问答案是“能”，该数据就不应同步。

例如：

| 用户动作 | 足够的信息 | 不需要的信息 |
| --- | --- | --- |
| 判断任务是否完成 | 完成状态、更新时间、一句结果摘要 | 完整 Agent 输出和终端日志 |
| 判断是否重试 | 失败类别、是否可重试 | 调用栈、文件内容和完整命令 |
| 判断是否回到电脑 | 是否需要本地处理、原因摘要 | 本地路径和环境详情 |
| 查看改动规模 | 修改文件数量、验证是否通过 | 文件名、Git diff 和代码片段 |

## 意图与事实分离

远程操作必须区分“用户提出了什么”和“系统实际发生了什么”。

```text
用户在官网请求停止
-> 请求已排队
-> 本地设备收到
-> 本地检查当前状态
-> 执行停止
-> 回传已停止
```

官网不能在请求发出后立即把项目事实改成“已停止”。同理：

- 请求重试不等于新的运行已经启动。
- 发起 Solo 不等于 Agent 已经开始工作。
- 用户确认不等于高风险动作已经执行。
- 消息送达不等于命令执行成功。

这条分离保证官网不会制造比本地更“新”但不真实的状态。

## 在线优先、离线诚实

官网工作台优先服务在线设备的实时控制。设备离线时，正确体验是明确受限：

```text
设备离线
最后一次本地浏览器缓存：14:32
新的要求将在设备上线后投递
```

离线时可以排队经过端到端加密的用户要求，但不能：

- 推断最新项目状态。
- 声称 Agent 正在执行。
- 用过期状态代替当前事实。
- 为了保持页面可用而上传项目数据库。

本地化产品允许离线能力受限，不允许用虚假连续性掩盖设备不可达。

## 远程动作分级

### A 级：只读观察

可以默认开放：

- 设备在线状态。
- 项目当前下一步。
- 运行中、已完成、失败和待确认数量。
- 本地生成的有限结果摘要。

### B 级：可逆控制

可以在设备授权后开放：

- 发起 Solo 请求。
- 补充对话要求。
- 请求停止运行。
- 请求重试失败运行。
- 刷新状态投影。

这些动作仍需本地设备检查状态、权限和幂等性。

### C 级：高风险动作

首版必须回到本地完成：

- 发布、部署、上架和生产变更。
- 支付、账单和外部消息发送。
- 权限、凭证和外部账号操作。
- 删除、覆盖和不可逆写入。
- 任意终端命令。

未来如果某项 C 级动作需要远程开放，必须单独设计授权、结果预览、二次确认、有效期和撤销路径，不能沿用普通按钮直接放行。

## “需要你处理”优先

官网第一屏不应复制完整路线图或本地侧边栏，而应优先显示需要用户介入的事项：

```text
需要确认
正在推进
失败与阻塞
最近完成
```

排序依据是行动价值，不是内部对象类型。用户不需要先理解 Agent、Flow、运行记录或设备路由，才能知道下一步该做什么。

每个事项只展示：

- 发生了什么。
- 为什么需要用户。
- 用户现在能做什么。
- 哪些详情只能在本地查看。

## Solo 是远程任务入口

远程用户往往先有一个临时问题，而不是先知道它属于哪个路线图环节。因此官网应允许直接发起 Solo：

```text
提出当前问题
-> 发送到指定本地设备
-> Agent 在本地项目中处理
-> 官网接收结果摘要
-> 用户决定仅保留、关联环节或调整路线图
```

官网不得在发起前要求用户选择路线图环节，也不得在完成后自动改变路线图。现有 Solo 归属规则在远程入口中保持不变。

## 设备不是用户的管理负担

设备存在是因为真实项目环境和 Agent CLI 位于本地，不应演变成要求用户理解的执行拓扑。

首版只暴露稳定选择：

- 哪台电脑在线。
- 当前项目在哪台电脑执行。
- 当前是否有运行。
- 哪些浏览器获得远程访问授权。

不向普通用户暴露连接协议、租约、队列、密钥、进程、端口和内部执行节点模型。

同一项目出现在多台设备时，首版由用户选择唯一当前执行设备，不做自动调度。系统不能为了显得智能而把任务路由到用户没有明确选择的环境。

## 隐私承诺必须可验证

“本地优先”不能只停留在文案。每个版本都应能验证：

- 网络请求不包含代码、文件、路线图、Prompt、日志和记忆正文。
- 服务端只能看到连接元数据与不可读密文。
- 没有设备或浏览器私钥时无法恢复项目投影。
- 撤销浏览器后无法读取后续消息。
- 同步接口不存在任意文件上传和远程 Shell 能力。
- 完整详情入口明确回到本地插件。

如果一项功能无法通过这些检查，就不能以官网工作台能力交付。

## 首版成功标准

官网工作台首版不以“网页覆盖了多少本地功能”为成功，而以三个用户结果为准：

1. 离开电脑后，用户能知道 Agent 是否仍在推进。
2. 出现阻塞时，用户能补充要求、请求停止或重试。
3. 需要用户判断时，用户能及时看到并完成安全范围内的决定。

只要这三个结果稳定成立，官网就已经成为真实工作台。在线路线图编辑、完整日志、跨设备调度和更多远程动作都不是首版完成条件。

## 功能进入官网的判断门

任何新功能进入官网前，必须同时通过：

### 用户动作门

- 它是否解决用户离开本地界面后的真实行动阻力？
- 它是否比“回到本地处理”带来明显价值？

### 数据最小化门

- 能否只传状态或摘要？
- 是否避免代码、路径、日志、Prompt 和项目记忆？

### 权威一致性门

- 本地是否仍是唯一事实权威？
- 断线、旧状态和重复投递是否不会改变真实结果？

### 安全门

- 服务端是否仍无法读取项目内容？
- 动作是否可撤销、可审计并受固定命令边界约束？

### 用户心智门

- 用户是否仍在推进同一个项目，而不是管理第二套云端对象？
- 界面是否只暴露用户必须理解的选择？

任一门不通过，该能力应留在本地插件或重新缩小范围。

## 与 SoloMap 方法论的关系

官网工作台不改变 SoloMap 的项目循环：

```text
项目想法
-> 路线图
-> Agent 执行
-> 本地证据
-> 用户判断
-> 下一步与路线图更新
```

它只在用户无法停留在本地界面时延伸三种能力：

```text
观察
-> 补充
-> 决定
```

本地插件继续负责执行与证据，官网继续服从路线图、Solo、Flow 和完成标准的既有产品边界。
