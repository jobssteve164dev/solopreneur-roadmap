# 项目初始化基座方法论

## 目标

项目基座是 SoloMap 在项目第一天建立的最小脚手架，用来让项目具备可推进、可验证、可审计的起点。

它不是项目发展蓝图，不替代路线图，不固化项目未来结构，也不接入跨项目经验库。

## 用户心智

用户只选择项目类型。SoloMap 根据项目类型自动判断应建立的最小基座，不再询问 CI、文档、安全、记忆等工程细节。

新项目默认直接写入缺失基座文件。已有项目只做体检，并在 Action 中提示缺失项；用户决定是否让 Agent 补齐。

## 第一版固定产物

第一版只固定 5 个入口：

- `README.md`
- `AGENTS.md`
- `PROJECT_MEMORY.md`
- `.github/workflows/ci.yml`
- `.github/workflows/security.yml`

这些文件只提供项目起步所需的最低稳定面。

`README.md` 面向人，说明项目是什么、如何运行、如何验证、如何交付。

`AGENTS.md` 面向 Agent，说明当前仓库的目标、边界、修改纪律、验证要求和安全注意事项。

`PROJECT_MEMORY.md` 面向跨会话 Agent，记录当前项目长期稳定事实、决策、边界、验证方式和高价值交接。它不记录日志、prompt、一次性总结或执行流水。

`ci.yml` 提供最小验证链路，只跑项目中存在的安装、lint、typecheck、test、build 或健康检查。

`security.yml` 提供最小安全审计链路，按技术栈选择依赖审计，并在适合的代码项目中启用 CodeQL。

## 非目标

第一版不默认创建完整 `docs/` 体系。

第一版不默认创建发布、部署、矩阵测试、规范手册、ADR、贡献指南或复杂安全策略。

第一版不因为已有项目缺基座而阻断路线图、Solo 或项目推进。

第一版不覆盖已有文件。老项目补齐只能创建缺失项。

## 项目类型影响

项目类型只影响基座生成的默认强度。

核心产品、基础设施和工具项目默认更重视 CI、构建、安全审计和可发布性。

内容产品、研究试验、日常工作和归档维护默认使用更轻的健康检查，不把复杂工程治理强加给项目。

项目类型不能让用户承担额外配置心智。差异由生成逻辑吸收。

## Action 消费

Action 读取基座体检结果，但基座缺失是非阻断提醒。

缺失项可以显示为：

```text
项目基座缺失 2
```

展开后列出缺失文件，并提供“补齐项目基座”动作。

基座缺失不能覆盖业务下一步，不能把项目顶成 P0，也不能阻止路线图生成。只有用户主动选择补齐时，Agent 才创建缺失文件。

## 验收标准

- 新项目添加后自动拥有 5 个基座入口。
- 已有项目不会被自动覆盖。
- 老项目缺失项会出现在 Action 提醒中。
- 缺基座不阻断路线图、Solo、Flow 或项目选择。
- 基座文件少而精，没有生成大而全的项目规范体系。
