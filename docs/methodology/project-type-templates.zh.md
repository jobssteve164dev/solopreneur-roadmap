# 项目类型与初始路线图模板

> 不同类型的项目有不同的执行模式。这个文档提供了 6 种项目类型的定义、特征和初始路线图模板。

---

## 核心产品类 (Core Product)

### 定义

面向外部用户，需要获得采用、付费或长期使用的产品。这是独立开发者的主要收入来源或影响力来源。

### 特征

- **目标明确**：要解决的真实问题是什么，为谁解决
- **市场闭环**：不只做产品，还要能触达用户、获得反馈、转化收入
- **持续迭代**：需要基于市场反馈不断改进
- **单位经济**：有明确的成本、收入或价值贡献度

### 例子

- SoloMap（帮助独立开发者管理项目）
- 小说连载产品（CONTENT_FACTORY）

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,问题与客户发现,"确认问题是否真实存在，找到愿意帮助验证的用户",问题发现,,agy,Pending
2,产品基础与首个可用版本,"打造最小化可交付产品（MVP），能验证核心假设",产品打造,1,agy,Pending
3,分发与市场触达,"通过官网/社群/营销把产品展示给潜在用户",市场触达,2,agy,Pending
4,反馈收集与单位经济,"记录用户反馈，计算初步的成本与价值",规模化改进,3,agy,Pending
5,持续改进循环,"基于反馈改进产品，启动 Build->Sell->Learn->Improve 循环",规模化改进,4,agy,Pending
```

### 完成标准

- ✓ 有明确的目标用户和他们的真实问题
- ✓ 已实现的 MVP 能被真实用户访问和使用
- ✓ 至少收集过 5+ 个真实用户的反馈
- ✓ 有明确的单位经济数据（成本、转化、LTV）
- ✓ 至少完成过一个 Build->Sell->Learn->Improve 周期

## 基础设施类 (Infrastructure)

### 定义

为多个其他项目提供能力的项目。这类项目的变更影响面大，需要严格的版本管理和兼容性保障。

### 特征

- **多项目依赖**：被 3+ 个项目依赖
- **稳定性优先**：破坏性变更会影响下游多个项目
- **需要版本管理**：major.minor.patch 语义化版本
- **向后兼容**：提供明确的迁移路径
- **文档清晰**：接入标准、契约、变更日志必须完整

### 例子

- Cloudapi（统一 LLM/API 接入层）
- GITOPS（部署和运维平台）
- 共享的认证/授权系统

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,明确能力范围与契约,"定义这个基础设施要提供什么，契约是什么",能力设计,,agy,Pending
2,核心能力实现,"实现第一版能力，内部可用",核心实现,1,agy,Pending
3,接入标准与文档,"定义外部项目怎么接入，提供清晰的接入指南",标准化,2,agy,Pending
4,第一个真实消费者接入,"找一个业务项目作为首个消费者，验证接入方案",验证,3,agy,Pending
5,版本管理与兼容性保障,"建立版本管理流程，确保破坏性变更有迁移路径",治理,4,agy,Pending
6,监控与告警,"部署监控，能实时发现接入方的问题",运维,5,agy,Pending
```

### 完成标准

- ✓ 有明确的语义化版本
- ✓ 至少被 2 个项目正式接入并在生产使用
- ✓ 接入文档完整，包括示例代码
- ✓ 有明确的变更日志和迁移指南
- ✓ 有监控和告警，能及时发现下游问题

## 内容产品类 (Content Product)

### 定义

内容是核心交付物的项目。例如小说连载、定期报告、数据分析、视频系列等。

### 特征

- **周期性交付**：按周/月/季度有规律地产出内容
- **工程化流程**：内容生产本身也可以工程化、自动化
- **质量管理**：需要编辑流程、质量检查、版本管理
- **分发渠道**：需要有成熟的分发方式（网站、社群、邮件等）
- **受众互动**：需要收集和回应反馈

### 例子

- 《修仙世界的底层代码被我改了》（文学作品）
- WeChat 公众号内容
- 工作报告
- 数据分析报告

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,内容主题与受众确认,"明确这个内容产品的主题、受众、发布频率",内容规划,,agy,Pending
2,生产工作流设计,"设计内容从构思到发布的工作流，确定需要哪些自动化工具",工程化,1,agy,Pending
3,第一期内容发布,"按照工作流生产并发布第一期内容",生产,2,agy,Pending
4,分发渠道建设,"确保内容能通过各种渠道触达目标受众",分发,3,agy,Pending
5,反馈收集与改进,"收集受众反馈，改进内容质量和生产流程",改进,4,agy,Pending
6,持续产出,"确立可持续的生产和分发节奏",运维,5,agy,Pending
```

### 完成标准

- ✓ 有清晰的发布节奏（周/月/季度）
- ✓ 至少完成过 3 期内容的完整周期
- ✓ 有明确的生产工作流和自动化工具
- ✓ 有至少 2 个以上的分发渠道
- ✓ 有来自受众的反馈并有改进行动

## 试验和研究类 (Experiment & Research)

### 定义

用来探索想法、学习新技术、验证假设的项目。这类项目成功的定义是"学到了什么"，而不一定是"产品上线"。

### 特征

- **快速试错**：周期短（1-4 周），迭代快
- **结果可失败**：不到线也没关系，重在学到东西
- **明确的学习目标**：要验证什么假设，要学什么技术
- **实验边界清晰**：不能无限期拖，要有明确的"学够了"时间点
- **知识沉淀**：即使项目失败，学到的东西要记录下来

### 例子

- 法律知识库试验
- 分析工具原型
- 新技术栈探索

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,明确学习目标,"这个试验要验证什么假设或学什么技术",目标确认,,agy,Pending
2,快速原型,"在 1-2 周内做出最简单的原型验证想法",原型开发,1,agy,Pending
3,结果评估,"评估试验结果，决定是值得深入还是放弃",评估,2,agy,Pending
4,知识沉淀,"无论成功失败，把学到的东西记录到 .codex-memory",总结,3,agy,Pending
```

### 完成标准

- ✓ 有明确的学习目标或验证的假设
- ✓ 在预期时间内（通常 2-4 周）完成了试验
- ✓ 清楚地记录了试验结果（成功或失败）
- ✓ 把学到的东西写进 `.codex-memory/inbox/` 或 `.codex-memory/domains/`
- ✓ 基于结果做了决策（深入、放弃、改进）

**注意：** 试验项目可以在任何阶段停止。停止的项目也应该完成"知识沉淀"这一步。

## 工具和脚手架类 (Tools & Scaffolding)

### 定义

为了提升自己或团队效率而构建的工具、脚本、模板、框架。这类项目的价值在于"减少重复工作"。

### 特征

- **明确的使用场景**：谁会用，用来干什么
- **可复用性**：可以在多个项目中使用
- **易集成**：新项目能快速集成这个工具
- **低维护成本**：一旦做好，很少需要改
- **清晰的接口**：使用方法要很明白

### 例子

- code-server 容器配置
- 项目初始化脚本
- 重复任务的自动化脚本
- 项目模板库

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,明确工具的价值与使用场景,"这个工具解决什么重复问题，哪些项目会用它",需求确认,,agy,Pending
2,核心功能实现,"实现工具的核心功能",开发,1,agy,Pending
3,清晰的使用说明与示例,"写清楚怎么用，提供可复制的示例",文档,2,agy,Pending
4,在一个真实项目中验证,"在另一个项目中实际用这个工具，看是否好用",验证,3,agy,Pending
5,持续维护与改进,"根据使用反馈改进工具",维护,4,agy,Pending
```

### 完成标准

- ✓ 有明确的使用文档和示例代码
- ✓ 已在 2+ 个项目中成功使用
- ✓ 集成成本低（通常 <30 分钟）
- ✓ 接口稳定，不经常破坏性变更
- ✓ 有明确的迭代和版本管理流程

## 归档和维护类 (Archive & Maintenance)

### 定义

已经上线、相对稳定、不需要频繁新增功能的项目。这类项目的优先级通常较低，重点是"保持稳定"。

### 特征

- **低频更新**：通常是缺陷修复、安全更新、依赖更新
- **稳定性优先**：宁可慢一点上新功能，也不能出问题
- **监控告警**：要有完整的监控，能及时发现问题
- **文档齐全**：因为很少动代码，文档必须非常清晰，未来维护时能快速上手
- **无人值守**：理想情况下能自动化大部分维护工作

### 例子

- 已上线的视频产品
- 已结束的报告项目
- 稳定运行的内部工具

### 初始路线图模板

```csv
id,title,description,stage,dependencies,agentCli,status
1,健康状况评估,"评估项目当前的监控、告警、文档是否完整",评估,,agy,Pending
2,建立监控与告警,"如果缺失，补齐监控和告警系统",建设,1,agy,Pending
3,缺陷修复与安全更新,"修复已知缺陷，更新依赖的安全补丁",维护,2,agy,Pending
4,文档更新,"更新维护文档，确保新维护者能快速上手",文档,3,agy,Pending
5,定期检查周期,"建立定期检查（每月/每季度）的流程",流程建设,4,agy,Pending
```

### 完成标准

- ✓ 有完整的监控和告警系统
- ✓ 有清晰的维护文档
- ✓ 有明确的缺陷修复和安全更新流程
- ✓ 有定期检查（至少每月一次）的计划
- ✓ 能在无人看守情况下运行至少一个月无重大问题

## 类型与优先级的关系

| 项目类型 | 默认优先级 | 何时升优先级 | 何时降优先级 |
|---------|---------|-----------|-----------|
| 核心产品 | P1 | 新功能验证、市场机会 | 遇到长期 blocker、市场需求下降 |
| 基础设施 | P1（如果被依赖） | 下游项目等待、安全漏洞 | 无依赖项目、迁移完成 |
| 内容产品 | P2-P1 | 发布周期临近、粉丝活跃 | 季节性低谷、更新延期 |
| 试验研究 | P3 | 突然有新发现、假设被推翻 | 学习目标达成、时间用完 |
| 工具脚手架 | P2 | 被多个项目等待、加速系数大 | 已有替代方案、少项目用 |
| 归档维护 | P3 | 生产事故、安全漏洞 | 完全下线 |

---

## 如何选择项目类型

**问自己三个问题：**

1. **谁是使用者？**
   - 外部用户 → 核心产品 或 内容产品
   - 其他内部项目 → 基础设施 或 工具
   - 自己的学习 → 试验研究
   - 保持现状 → 归档维护

2. **什么时候算"完成"？**
   - 有真实用户在用 → 核心产品
   - 被其他项目依赖 → 基础设施
   - 按计划周期产出 → 内容产品
   - 学到了 → 试验研究
   - 被 2+ 个项目用上 → 工具脚手架
   - 系统正常运行 → 归档维护

3. **现在应该做什么？**
   - 用对应的初始路线图模板
   - 从第一个环节开始
