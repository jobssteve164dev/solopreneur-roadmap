# 统一学习账本方法论

## 这份文档解决什么判断

这份文档说明 SoloMap 应如何判断一条执行经验是否值得沉淀、如何被召回、如何晋升，以及如何避免学习机制变成新的后台噪音。

核心判断只有一句：**学习只有在改变下一次行动质量时才成立。**

## 适用范围

本文适用于：

- 路线图推进后的复盘。
- Solo 对话中的用户纠偏。
- Flow 微循环中的 Planner / Builder / Verifier 反馈。
- Daily Review 的学习收口。
- 战略金字塔的学习信号吸收。
- 跨项目经验晋升为 memory、pattern、decision、domain 或 strategy signal。

本文不要求用户手动维护账本。用户只需要在必要时确认、忽略或纠偏重要学习信号。

## 第一原则

学习管线的第一原则是行动改进。

一条学习产物必须至少改变下面一类结果：

- 下一次计划怎么定。
- 下一次实现如何避坑。
- 下一次验证跑什么。
- 下一次是否需要用户确认。
- 下一个项目是否可以复用能力。
- 当前项目是否应该加码、收缩、暂停或进入路线图调整。

如果它只是在描述过去发生了什么，就不是有效学习。

## 四层学习模型

```text
事实层：发生了什么
候选层：可能值得复用什么
确认层：什么已经被证明可靠
行动层：下一次因此怎么做
```

### 事实层

事实层回答“发生了什么”。

事实必须能指向：

- 文件。
- diff。
- 命令。
- 测试。
- Flow trace。
- run digest。
- 用户明确选择。
- Agent 执行状态。

没有证据的 Agent 总结不能进入事实层。

### 候选层

候选层回答“可能值得复用什么”。

候选可以由系统自动提炼，但只能保持 candidate 状态。

典型候选：

- 某个验证命令证明了一个模块的闭环。
- 某次 Flow Verifier 发现了假完成。
- 用户指出了一个体验边界。
- 某个项目反复出现相同失败原因。
- 某条战略判断需要下周继续观察。

### 确认层

确认层回答“什么已经可靠”。

确认来源可以是：

- 同类验证重复通过。
- 用户明确确认。
- 后续执行复用成功。
- 失败模式再次出现并被同一经验解释。
- 候选被人工晋升到长期记忆。

未经确认的候选不能冒充长期规则。

### 行动层

行动层回答“下一次因此怎么做”。

有效学习必须能转成：

- Plan：调整范围、路径或风险判断。
- Build：改变实现方式。
- Verify：改变验证命令或证据要求。
- Review：改变今日安排。
- Strategy：改变项目组合判断。

不能转成行动的学习，只能留在低权重候选池。

## 学习产物判断标准

一条候选是否值得保留，用五个问题判断：

1. 它是否有证据。
2. 它是否能在未来复用。
3. 它是否能改变行动、验证或战略判断。
4. 它是否比原始日志更清晰。
5. 它是否不会把内部治理负担转嫁给用户。

五项都满足，才是高质量候选。

如果只满足前两项，它可以短期保留，但不应高权重召回。

## Flow 微循环如何沉淀学习

Flow 是学习账本的高密度来源，因为它把目标拆成了可归因的微循环。

### Planner 产物

Planner 可沉淀：

- 路径选择依据。
- 被放弃方案。
- 风险预判。
- 需要用户确认的边界。
- 验证计划。

Planner 失败时，重点沉淀规划缺口，而不是沉淀自然语言方案。

### Builder 产物

Builder 可沉淀：

- 实际触碰文件。
- 实现动作与完成标准的对应关系。
- 自测命令。
- 已知缺口。
- 偏离计划的解释。

Builder 失败时，重点沉淀“无动作证据”“越界变更”“未跑验证”等风险模式。

### Verifier 产物

Verifier 是 Flow 学习中最重要的沉淀点。

Verifier 可沉淀：

- 通过验证的闭环路径。
- `implemented_unverified` 的原因。
- `verified_failed` 的失败证据。
- `deviated` 的偏航原因。
- `needs_confirmation` 的用户授权边界。
- H/I/J 评分背后的硬闸门。

Verifier 产物优先进入下一轮 Planner 的风险约束。

## 普通执行如何沉淀学习

普通路线图推进、Solo、路线图调整和 review 的学习粒度比 Flow 粗，但仍应写入账本。

### 路线图推进

重点沉淀：

- 这个环节是否完成。
- 使用了哪些验证。
- 失败或阻断原因。
- 哪些文件和模块被触碰。
- 是否产生可复用实现模式。

### Solo

重点沉淀：

- 用户对方向、体验、边界、文案或执行方式的纠偏。
- 未归属路线图但可能影响项目判断的事实。
- 需要后续路线图调整的信号。

Solo 不应自动把所有聊天内容变成长期记忆。

### 路线图调整

重点沉淀：

- 为什么调整路线图。
- 哪些学习信号触发调整。
- 哪些项目阶段被补齐或降级。
- 调整后如何验证它没有偏离项目方向。

### Review

重点沉淀：

- 复核发现的缺口。
- 通过复核的验证模式。
- 需要用户确认的风险。

Review 不能只沉淀“另一个 Agent 说了什么”，必须绑定证据。

## 召回方法

召回不是搜索全部历史，而是按当前任务选择最可能改变行动的经验。

召回时优先考虑：

- 同项目经验。
- 同类入口：step、solo、roadmap revision、flow。
- 同角色：planner、builder、verifier。
- 同文件或模块。
- 同风险词：failed、deviated、unverified、confirmation。
- 已确认或已晋升经验。

召回输出必须用行动语言：

```text
适用：什么时候用
本轮应做：具体改变什么
避免：不要重复什么
证据：来自哪里
```

禁止输出：

- “历史上做过类似事情”这种空泛总结。
- 大段执行日志。
- 用户无法行动的目录、字段或 schema 解释。

## Daily Review 方法

Daily Review 使用学习账本时，只回答今天的动作排序。

判断顺序：

1. 是否有学习风险必须先收口。
2. 是否有已验证经验可以降低今天执行成本。
3. 是否有候选需要用户确认后才能影响行动。
4. 是否有项目因为学习信号应进入主推进或收尾。

Daily Review 不做候选仓库清理，不把“整理学习材料”伪装成用户任务。

## 战略金字塔方法

战略金字塔吸收学习信号时，应把学习分成两类：

- 已验证或已确认经验：可以支撑加码、复用能力、收缩低效路径。
- 未收口风险候选：只能提示谨慎，不能直接作为战略事实。

战略判断应该问：

- 哪些项目正在产生可复用能力。
- 哪些失败模式正在重复消耗注意力。
- 哪些验证经验证明某个方向值得加码。
- 哪些候选还需要用户确认或下一轮验证。

战略金字塔不应变成学习候选列表。

## 晋升方法

候选晋升前必须回答：

- 这条经验未来会在哪些情景被复用。
- 它的证据是什么。
- 它是否已经被验证或用户确认。
- 它应该进入哪一层。

晋升目标选择：

| 目标 | 使用条件 |
| --- | --- |
| 项目记忆 | 只对当前项目长期成立 |
| Pattern | 多项目或多任务可复用的执行/验证/排障模式 |
| Decision | 已确认且影响后续方向的选择 |
| Domain | 跨项目领域知识 |
| Operating rule | 跨任务通用执行约束 |
| Strategy signal | 会影响组合排序、加码、收缩或暂停 |

晋升后，候选应标记为 promoted，避免重复提示用户处理同一件事。

## 拒绝方法

候选应被拒绝的情况：

- 只是执行流水。
- 没有证据。
- 未来复用概率低。
- 与当前事实冲突。
- 已经过期。
- 会把内部实现细节转嫁给用户。
- 只是 Agent 自我解释。

拒绝不是删除历史。原始事实仍可保留，候选不再作为高权重召回材料。

## 与优先级的关系

学习账本不直接替用户决定项目优先级。

它只提供证据：

- 失败和偏航信号可能把项目推向异常处理。
- 已验证经验可能降低项目推进成本。
- 重复风险可能阻止继续加码。
- 战略信号可能触发路线图调整。

项目优先级仍应由项目状态、阻断、用户目标、商业阶段、学习信号和战略判断共同决定。

## 反模式

以下做法会让学习管线失效：

- 只统计候选数量，不看候选是否影响行动。
- 把所有项目卡片都显示同一类学习 tag。
- 把未确认候选直接注入战略结论。
- 把内部账本目录和字段暴露给普通用户。
- 学习写入失败导致主执行失败。
- 召回过多历史，稀释当前任务注意力。
- 把用户纠偏写成普通实现细节。
- 把 Flow Verifier 的失败包装成完成。

## 成熟度模型

### 第一阶段：可记录

系统能稳定写入学习事件和候选。

成功标准：

- 不丢关键执行来源。
- 存储失败不阻断主流程。
- 项目卡片能显示真实学习线索。

### 第二阶段：可召回

系统能在下一次执行前召回相关候选。

成功标准：

- 同项目、同角色、同风险经验能命中。
- 召回结果能改变计划、验证或边界。
- Prompt 不被历史噪音淹没。

### 第三阶段：可确认

用户或系统能确认、拒绝和晋升候选。

成功标准：

- 候选状态清晰。
- 晋升目标清晰。
- rejected 不再反复打扰。

### 第四阶段：可战略吸收

学习信号进入项目组合判断。

成功标准：

- 战略金字塔能区分风险候选和已验证经验。
- Daily Review 能把学习信号转成今日动作。
- 路线图调整能引用学习证据。

### 第五阶段：可自适应

系统能根据学习结果调整下一轮执行策略。

成功标准：

- Flow Planner 自动吸收 Verifier 风险。
- 同类失败越来越少。
- 已验证路径复用率提升。
- 项目组合判断越来越少依赖临时直觉。

## 方法论验收

学习账本方法论是否生效，看四个结果：

- 下次执行是否少踩同一个坑。
- 下次验证是否更直接。
- 今日安排是否更少拍脑袋。
- 战略判断是否更能区分事实、候选和已确认经验。

如果这些结果没有发生，即使账本里有很多文件，也还不是有效学习系统。
