# SoloMap Agent Task Flow 方法论

## 这份文档解决什么判断

这份文档说明 SoloMap 如何从“启动 Agent CLI”升级为“可复核、可续推、可验收的 Agent 任务流”。

核心判断只有一句：**Agent Task Flow 的最小完成单位不是一次 Agent 调用，而是一个路线图环节或 Solo 任务被推进到明确结论。**

补充判断：路线图环节能够被推进到明确结论，必须由多个可证据化的微观执行循环支撑。单次 Agent 调用、CLI 退出码或 Agent 自述完成都不能单独作为路线图完成依据。

## 当前问题

当前 Agent 链路已经具备任务流骨架：

- 用户选择路线图环节或 Solo 入口。
- 系统注入项目上下文、环节记忆、执行经验和用户补充。
- 本地 Agent CLI 在 VS Code 终端中执行。
- 系统记录输入、输出、状态、变更文件和运行摘要。
- 后续任务可以读取相关历史经验。

但这仍然偏向人工推进。用户仍需要判断：

- Agent 是否真的完成了。
- 是否还需要继续。
- 是否应该跑验证。
- 失败后下一步是什么。
- 是否可以更新环节状态。

因此下一阶段的目标不是直接做多环节连跑，而是先把单个任务闭环做实。

## 第一版目标

第一版 Agent Task Flow 应聚焦单环节自动闭环：

```text
启动任务
  -> 主 Agent 执行
  -> 收集运行结果
  -> 副 Agent 复核
  -> 判断完成 / 打回 / 需要确认
  -> 必要时主 Agent 续推
  -> 写入完成证据
```

完成后，用户看到的是一个明确结论：

- `已完成`
- `需要确认`
- `发现问题，已继续修正`
- `失败，并给出下一步`

而不是一段需要用户自行裁判的 Agent 输出。

## 微观执行循环作为可靠单元

Agent Task Flow 不应直接从“Agent run 成功”跳到“路线图环节完成”。中间必须形成微观执行循环：

```text
意图 -> 判断 -> 动作 -> 证据 -> 结果 -> 归因
```

每个循环回答一个具体问题：

```text
这个意图是否已经被规划、实施、验证，并能归因到路线图完成标准？
```

因此 Task Flow 的滚动逻辑应改为：

```text
路线图环节启动
  -> 创建微观循环
  -> Planner 形成意图和判断
  -> Builder 实施
  -> SoloMap 采集事实证据
  -> Verifier 审查
  -> SoloMap 决定循环状态
  -> 聚合循环结果判断环节是否完成
      -> 不满足：生成下一微观循环
      -> 满足：完成环节并推荐下一路线图环节
```

相关方法论见 `docs/methodology/micro-execution-loop-methodology.zh.md`，执行设计见 `docs/architecture/micro-execution-loop-flow.zh.md`。

## 单环节优先

第一版不优先做多环节连跑。

原因：

- 多环节连跑会放大单环节未闭环的问题。
- 路线图环节本身已经是用户的项目推进单位。
- 先证明一个环节能稳定完成、复核、续推和沉淀，后续多环节协作才有地基。

多环节连跑应作为后续能力，只在以下条件满足时启用：

- 前一环节有完成证据。
- 后一环节依赖已满足。
- 不涉及高风险授权动作。
- 用户明确开启或确认继续。

## 主副 Agent 协作流程

### 1. 任务启动

系统从现有入口启动任务：

- 路线图环节。
- Solo 对话。
- 路线图调整。

启动前应准备：

- 用户本轮目标。
- 当前项目事实。
- 路线图环节上下文。
- 完成标准。
- 相关执行经验。
- 相关 Issue、交付信号或学习候选。
- 本轮附件。

### 2. 主 Agent 执行

主 Agent 接收完整任务，负责实际交付。

它应产出：

- 文件变更或明确的无变更结论。
- 运行命令或验证命令。
- 完成判断。
- 已知风险。
- 下一步是否需要用户确认。

### 3. 结果收集

SoloMap 在主 Agent 结束后收集可验证事实：

- 退出状态。
- touched files。
- 文件 diff 摘要。
- 运行命令。
- 验证结果。
- `.agent_status.json` 或等价完成信号。
- run digest。

这些事实进入副 Agent 复核上下文，而不是把完整原始日志直接塞给副 Agent。

结果收集必须形成绑定到本次 execution 的验收包，而不是读取复核时刻的活动工作区。验收包记录任务开始 revision、结束 patch 或文件哈希、目标、完成标准和验证证据。主 Agent 的输出尾部只能作为定位线索，不能作为通过依据。

### 4. 副 Agent 复核

副 Agent 默认只读，围绕以下问题复核：

- 用户原始目标是否被满足。
- 完成标准是否被满足。
- 是否存在明显遗漏。
- 是否跑了必要验证。
- 是否有用户向体验问题。
- 是否有工程自描述、模板口吻或实现痕迹泄漏到普通用户界面或内容。
- 是否有高风险动作需要用户确认。

副 Agent 输出必须收敛成三类之一：

```text
pass
revise
needs_user_confirmation
```

不能输出开放式长篇讨论让用户自行判断。

普通 Step / Solo 的复核只输出目标是否满足、证据是否足够和逐项检查，不复用 Flow 的 H/I/J 评分与 Planner/Builder/Verifier 对象。每个 `pass` 必须引用验收包中的真实证据；SoloMap 在接受结论前校验证据路径和适用完成标准覆盖。

Step 使用路线图环节目标和既有完成标准。Solo 使用用户本轮原始要求；实施或修复任务可以进入自动修正，讨论或判断任务只检查回答是否真正回应用户，不套用代码改动或测试要求。Flow 继续在自己的微观循环中使用 H/I/J，两条路径只共享证据采集和只读执行底座。

复核运行使用强制只读权限。Agent 只向标准输出返回结构化 JSON，复核结果文件由 SoloMap 自己写入；不能为了让 Agent 写结果文件而授予整个项目写权限。

### 5. 打回续推

当副 Agent 输出 `revise` 时，SoloMap 应把可执行问题打回主 Agent。

打回内容应包含：

- 哪个目标没满足。
- 哪个文件或结果有问题。
- 需要补什么验证。
- 完成后如何判断。

第一版自动续推一次，并优先接续原主 Agent 会话。修正完成后，第二次复核只检查失败项与新增差异。第二次仍未通过、证据过期或重复出现同一问题时停止自动推进，前台给出简短结论和下一步。

### 6. 用户确认

当副 Agent 输出 `needs_user_confirmation` 时，系统停止自动推进。

需要确认的典型情况：

- 发布或部署。
- 删除或不可逆动作。
- 外部写入或消息发送。
- 成本、权限或隐私边界变化。
- 产品方向或路线图结构变化。
- Agent 之间判断冲突且无法通过证据解决。

前台应说明用户需要决定什么，而不是展示内部争论。

### 7. 完成沉淀

当任务通过复核后，系统写入：

- execution log。
- step memory。
- run digest。
- 可复用学习候选。
- 必要时更新路线图环节状态。

完成标准是：下一轮任务能从这次结果中知道发生了什么、验证了什么、还剩什么风险。

## 复核触发策略

第一版可以支持三种策略：

| 策略 | 含义 | 适用 |
| --- | --- | --- |
| 关闭 | 不自动触发副 Agent | 成本敏感或用户手动控制 |
| 高风险任务 | 代码、发布、路线图调整、用户向内容等任务触发 | 推荐默认 |
| 全部任务 | 每次 Agent 任务后都复核 | 质量优先 |

推荐默认：`高风险任务`。

高风险任务包括：

- 修改运行时代码、配置、构建或发布链路。
- 修改用户直接看到的 UI、内容、文案或营销材料。
- 修改路线图结构或项目长期文档。
- 涉及权限、凭证、外部服务或生产环境。
- 主 Agent 明确标注不确定、失败、部分完成或未验证。

## 前台表达

前台表达应围绕用户动作，而不是内部机制。

推荐状态：

- `正在推进`
- `正在复核`
- `继续修正中`
- `需要确认`
- `已完成`
- `未完成`

不推荐状态：

- `Reviewer Agent running`
- `Cabinet deliberating`
- `orchestration node failed`
- `routing policy matched`
- `digest validation pending`

日志详情可以保留 Agent 来源、命令和复核记录，但主界面不应要求用户理解这些对象。

## 与执行经验层的关系

Agent Task Flow 依赖执行经验层，但不等于执行经验层。

执行经验层回答：

```text
过去哪些事实对本轮有用？
```

Agent Task Flow 回答：

```text
本轮任务如何被推进到明确结论？
```

因此复核和续推结果也应进入 run digest，成为未来任务可召回的经验。

## 与路线图的关系

路线图仍然决定项目下一步做什么。

Agent Task Flow 决定这一步如何被完成。

两者关系：

```text
Roadmap = what to do next
Agent Task Flow = how this step gets done
```

第一版完成后，SoloMap 的核心能力会从：

```text
Roadmap + Agent launcher
```

升级为：

```text
Roadmap + Agent task closure
```

## 后续阶段

### 阶段 1：主副 Agent 单环节闭环

- 设置中支持主 Agent 和复核 Agent。
- 单环节结束后自动复核。
- 明确问题自动打回主 Agent。
- 完成后写入证据。

### 阶段 2：验证角色

- 增加命令验证或测试验证角色。
- 支持副 Agent 建议验证命令。
- 系统区分“已跑验证”和“建议验证但未跑”。

### 阶段 3：任务类型角色

- 根据任务类型引入文档、研究、发布等角色。
- 仍然保持主界面的一套心智。
- 用户只选择目标和授权，不维护角色矩阵。

### 阶段 4：低风险多环节连续推进

- 仅在完成证据稳定后启用。
- 每个环节完成后都能停下。
- 高风险动作必须用户确认。

## 禁止项

- 禁止把多 Agent 协作做成前台主任务系统。
- 禁止让用户手工维护复杂角色矩阵。
- 禁止让多个 Agent 并发修改同一任务文件。
- 禁止把副 Agent 的开放式意见直接丢给用户裁判。
- 禁止用自动化绕过用户授权。
- 禁止把复核、digest、路由、状态机等内部对象暴露为普通用户必须理解的概念。
