# SoloMap 项目生长方法论

## 这份文档解决什么判断

这份文档固定 SoloMap 如何从“记录 AI 对话和路线图推进”升级为“帮助用户理解项目如何长出来”。

核心判断只有一句：**SoloMap 不应该让用户沉浸在更重的 AI 对话里，而应该把对话、代码、验证和反馈压缩成项目生长事实。**

## 产品主语

SoloMap 的主语不是聊天记录、Agent 会话、文件树或代码仓库，而是项目本身。

用户打开 SoloMap 时，真正想知道的是：

- 这个项目现在长到了哪里。
- 哪些能力已经形成。
- 哪些能力还只是想法、草稿或未验证代码。
- 最近 AI 和人工工作塑造了项目的哪一块。
- 当前最值得推进、验证或修正的地方在哪里。

因此，项目生长方法论把 SoloMap 的核心问题定义为：

```text
项目目标
  -> 路线图阶段
  -> 产品能力
  -> 代码结构
  -> 执行历史
  -> 验证证据
  -> 下一步生长动作
```

这条链路必须从用户目标出发，不能从内部数据表、Agent 对话或目录结构出发。

## 与聊天 UI 的边界

更强的聊天 UI 不是 SoloMap 的主线。

Agent 对话可以继续存在，但只能作为项目生长链路中的执行通道和证据来源。它不应成为用户的主要工作空间。

允许增强的部分：

- 对话结束后沉淀结果摘要、触碰文件、验证信号、失败信号和下一步。
- 对话中出现权限请求、用户问题或停止动作时，提供内嵌交互。
- 运行历史可以下钻，但默认折叠为项目事实。

禁止偏航的部分：

- 新增脱离路线图、Solo 任务或项目目标的重型聊天中心。
- 把多 Agent 会话列表变成主入口。
- 把工具调用、终端日志、raw output 或 transcript 当作用户默认阅读对象。
- 用“更好聊”替代“项目继续长大”。

## 项目生长图的定位

项目生长图不是代码地图，也不是 SpaceSniffer 皮肤版文件浏览器。

它是项目能力、执行历史、验证证据和代码结构之间的关系图。

它应该回答：

- 这个项目由哪些主要能力和模块构成。
- 每个能力落在哪些代码区域。
- 哪些区域最近在生长。
- 哪些区域被 Agent 反复改动或验证失败。
- 哪些区域已经支撑产品主路径。
- 哪些区域缺少测试、发布、反馈或路线图归属。

代码结构只是底图。用户真正要看的，是项目能力如何在代码里成形。

默认图形主语必须是“产品能力如何由真实模块共同支撑”，阅读顺序是能力、实现模块、协作依赖、验证证据。目录、包名和测试文件只有在能解释这条链时才出现；扫描器发现了多少对象、依赖工具输出了多少节点，不构成用户价值。

## 生长事实的六层

### 1. 结构层

结构层回答“项目由什么组成”。

它包括：

- 文件树。
- 目录聚合。
- 语言分布。
- 文件大小和代码行数。
- 入口文件和包边界。
- import / dependency 关系。

结构层不能只展示大小。大文件不一定重要，小文件也可能是主路径入口。

### 2. 职责层

职责层回答“这块代码服务什么能力”。

它把文件和目录映射到用户能理解的产品能力，例如：

- 首次引导。
- 路线图生成。
- 路线图推进。
- Solo 对话。
- Agent 执行。
- 运行记录。
- 发布与验证。
- 付费能力。

职责层可以由规则推断、Agent 归纳和用户确认共同形成。用户不需要理解内部模块命名，但需要能理解这块代码对项目有什么用。

### 3. 演化层

演化层回答“哪里最近在长”。

它包括：

- Git churn。
- 最近提交时间。
- 最近 Agent 触碰时间。
- 多次运行是否集中在同一区域。
- 长期未动但仍处于主路径的区域。

演化层用于帮助用户区分“稳定主干”“快速生长”“反复返工”“长期沉睡”。

### 4. 执行层

执行层回答“谁推动了这块生长”。

它把现有运行事实挂到结构和职责上：

- 哪个路线图环节触碰了这块。
- 哪次 Solo 对话触碰了这块。
- 哪个 Agent CLI 执行了相关任务。
- 本次运行状态是完成、失败、停止还是待验证。
- 相关 handoff 建议是什么。

执行层的来源包括 `execution_logs`、`run_records`、`run_files`、`run_signals`、Run Digest 和 Execution Graph。

### 5. 证据层

证据层回答“这块是否真的成立”。

它包括：

- 测试命令和结果。
- 构建、编译、lint、类型检查结果。
- GitHub Actions / Release / deploy 信号。
- 人工验收或截图证据。
- 失败信号和未覆盖项。

证据层必须优先服务判断。用户不应先看到原始日志，而应先看到能否推进、缺什么证据、下一步该补什么。

### 6. 动作层

动作层回答“下一步让项目哪里继续长”。

它把前五层聚合成可执行建议：

- 补验证。
- 继续修正。
- 拆分过重入口。
- 回收实验残留。
- 完成路线图环节。
- 调整路线图。
- 发布或收集反馈。

动作层必须是用户语言，不应出现索引、schema、digest、embedding、graph score 等内部概念。

## 生长状态

项目生长图中的能力或模块可以用以下状态表达：

| 状态 | 用户含义 |
| --- | --- |
| 已成形 | 有代码、有验证、有路线图或交付归属 |
| 正在生长 | 最近持续被改动或被 Agent 推进 |
| 待验证 | 已实现但证据不足 |
| 反复返工 | 多次触碰、失败或回滚集中 |
| 缺归属 | 有代码但没有清晰路线图、能力或用户动作归属 |
| 风险集中 | 核心路径、改动频繁、验证不足或入口过重 |
| 可沉淀 | 已稳定，可以形成文档、模式、测试或能力边界 |

这些状态是为了降低判断成本，不是给用户制造审计压力。前台文案应倾向“需要关注”“缺验证”“变化很快”“主路径”，少用“高危”“低质”这类惩罚性表达。

## 与路线图的关系

路线图回答“项目应该如何推进”。  
项目生长图回答“项目实际长成了什么样”。

两者必须互相校验：

- 路线图环节完成后，应能在生长图上看到对应能力或证据。
- 生长图发现缺口时，应能提示继续推进、补验证或调整路线图。
- 没有路线图归属的代码增长，应被标为缺归属，而不是默认视为进展。
- 长期没有代码或验证落地的路线图环节，应被标为未长成。

## 与执行经验层的关系

执行经验层记录“过去如何推进”。  
项目生长层聚合“这些推进如何塑造项目”。

执行经验层可以告诉下一位 Agent：

- 上次先看了哪些文件。
- 哪些错误路径不要重复。
- 哪些验证命令有效。

项目生长层进一步告诉用户：

- 哪个能力被这些运行塑造。
- 哪块代码因这些运行变得稳定、脆弱或未验证。
- 下一步该让项目哪一块继续长。

## 与 CodeGraph 的关系

CodeGraph 可以作为代码结构辅助，但不能成为项目生长层的唯一事实源。

CodeGraph 适合提供：

- symbol。
- call graph。
- import / dependency 边。
- 影响半径。

它不能替代：

- 路线图归属。
- Agent 运行结果。
- 测试和发布证据。
- 用户目标和产品能力判断。

第一版项目生长层应先用文件系统、Git、import graph 和 SoloMap 现有运行索引建立自己的事实模型。CodeGraph 后续作为增强能力接入。

## 前台表达原则

用户界面必须以项目生长动作组织，而不是以内部数据对象组织。

推荐表达：

- “这块能力最近在快速成形。”
- “这块已经实现，但缺少验证证据。”
- “最近 4 次 Agent 都改到这里，建议先收口。”
- “这块代码没有路线图归属，可能是实验残留。”
- “这个环节已经有代码和验证，可以进入发布/反馈。”

避免表达：

- `growth_nodes`
- `executionGraph.byFile`
- `run_files role=touched`
- `digest score`
- `module classifier`
- `embedding hit`

## 完成标准

项目生长能力真正成立，不以图画出来为准，而以 SoloMap 能稳定回答以下问题为准：

1. 项目由哪些主要能力和模块构成？
2. 当前路线图环节实际影响了哪些代码区域？
3. 最近 AI 工作主要塑造了哪块项目能力？
4. 哪些区域已经有验证，哪些只是改过代码？
5. 哪些区域正在快速变化、反复失败或缺少归属？
6. 用户下一步应该推进、验证、修正还是调整路线图？

如果只能展示文件大小、目录层级和改动次数，这个能力还没有完成。
