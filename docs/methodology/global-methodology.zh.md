# 全局工程方法论：独立开发者的多项目并行模式

> 从单项目的执行驾驶舱升级为投资组合的全局管理面
>
> 这套方法论定义了独立开发者如何在**同时管理多个项目**的环境中，通过复利机制、能力复用和全局协调，实现**比线性增长快得多的进度加速**。

---

## 第一部分：基础理论

### 0. 为什么需要全局方法论

**观察到的现象：**

当前独立开发者的工作模式不再是"一个项目，从想法到上线"。而是：

```
同时管理 10-30 个项目
  ├─ 核心产品 2-3 个（需要持续投入）
  ├─ 基础设施 2-3 个（跨项目依赖）
  ├─ 内容产品 3-5 个（文学、报告、工具等）
  ├─ 试验和研究 10-15 个（验证想法）
  └─ 归档和维护 5-10 个（已上线但低频维护）
```

这种并行不是"我闲的时候切到另一个项目"。而是**真实的、系统化的、需要全局优化的多线程执行**。

**目前的问题：**
- 每个项目用 SoloMap 独立执行，项目间无法共享经验
- 相似问题在多个项目里重复解决
- 决策之间有冲突，但无法全局看到
- 好的实践在一个项目成功了，其他项目不知道
- 全局优先级无法跨项目优化（总是忙得不停，但可能在做最不紧急的事）

**全局方法论的目标：**

不是让你"同时做得更多"，而是让你"同时做得更快、质量更好、重复工作更少"。

### 1. 核心理念：从项目循环到投资组合循环

#### SoloMap 的单项目循环（现有）

```
项目想法 
  → 问题发现 
  → 产品打造 
  → 市场触达 
  → 持续改进
```

这套循环**对单个项目有效**。但独立开发者的真实循环是**嵌套的**：

#### 全局投资组合循环（新增）

```
┌─────────────────────────────────────────────────────┐
│           投资组合顶层循环（跨项目）               │
│                                                       │
│  全局能力池 → 优先级协调 → 资源分配 → 执行 → 学习反馈
│    ↓            ↓           ↓        ↓       ↓
│  可复用能力  全局最优   人力/时间  单项目  复利
│  决策历史    下一步     管理      SoloMap 沉淀
│  执行模式    判断
│
└─────────────────────────────────────────────────────┘
         ↓            ↓              ↓
    ┌────────┐   ┌─────────┐   ┌──────────┐
    │ 项目 A │   │ 项目 B  │   │ 项目 C   │
    │ 循环   │   │ 循环    │   │ 循环     │
    └────────┘   └─────────┘   └──────────┘
```

**关键差异：**

| 单项目循环 | 投资组合循环 |
|--------|----------|
| 自成一体，依赖外部投入 | 内部循环，相互反馈 |
| 项目完成了就结束 | 完成的学习进入全局池 |
| 每个项目各自决策 | 全局优先级统一决策 |
| 能力每次重新创造 | 能力第一次创造，后续复用 |
| 执行速度是线性的 | 执行速度是指数增长 |

### 2. 三个增长阶段

#### 阶段 1：基础积累（现在）
- 单个项目运行 SoloMap 方法论
- `.codex-memory` 开始沉淀跨项目知识
- 11 个已初始化项目，各自独立推进
- 还未形成全局协调

**特征：** 忙但收效不明显，经验沉淀不系统

#### 阶段 2：有向复用（近期目标）
- SoloMap 在执行时自动查询 `.codex-memory`
- 新项目用模板快速初始化
- 相同问题在第二个项目里被识别和复用
- 全局优先级开始出现

**目标：** 第二个项目快 2 倍，第三个快 3 倍

#### 阶段 3：自适应循环（长期）
- 全局学习面板自动发现可复用模式
- Agent 在任何项目工作时都能查询全局决策
- 项目间的依赖和冲突自动可视化
- 全局优先级自动调整

**目标：** 投资回报率从 1 倍变成 10 倍

## 第二部分：全局执行模型

### 3. 项目分类与对齐

独立开发者的项目虽然多，但可以按**执行模式**分类，而不只是按业务属性。

#### 按执行模式分类

```
┌──────────────────────────────────────────────────────┐
│            独立开发者的项目分类                      │
├──────────────────────────────────────────────────────┤
│                                                       │
│  1. 核心产品类（核心收入/影响力来源）             │
│     └─ 特征: Build -> Sell -> Learn -> Improve 完整循环
│     └─ SoloMap方法论完全适用
│     └─ 例: SoloMap、Cloudapi、CLOUDMCP                 │
│                                                       │
│  2. 基础设施类（被多个项目依赖）                 │
│     └─ 特征: 跨项目消费，变更影响面大
│     └─ 需要: 版本管理、向后兼容、治理约束
│     └─ 例: GITOPS、Cloudapi provider adapters        │
│                                                       │
│  3. 内容产品类（内容为核心交付物）               │
│     └─ 特征: 内容工程化、周期性交付、持续更新
│     └─ 需要: 模板、工程化流程、批量操作
│     └─ 例: novel、wechat、content_factory             │
│                                                       │
│  4. 试验和研究类（验证想法、学习）               │
│     └─ 特征: 快速试错、结果可失败、重在学习
│     └─ 需要: 轻量路线图、明确边界条件
│     └─ 例: BC、laws、analytics                        │
│                                                       │
│  5. 工具和脚手架类（提升效率）                   │
│     └─ 特征: 支持其他项目执行、可复用
│     └─ 需要: 接口稳定、文档清晰、易集成
│     └─ 例: code-server-container、scripts           │
│                                                       │
│  6. 归档和维护类（已上线/已完成）                │
│     └─ 特征: 低频更新、稳定性优先
│     └─ 需要: 监控、缺陷修复、安全更新
│     └─ 例: ST-video、revenue                          │
│                                                       │
└──────────────────────────────────────────────────────┘
```

**为什么要分类？**

不同类型的项目，其路线图模型、完成标准、执行纪律都不同：

- **核心产品**要完整的四阶段循环
- **基础设施**要严格的版本管理和兼容性测试
- **内容产品**要生产流程和批量工具
- **试验类**要轻量路线图，允许结果失败
- **工具类**要清晰的消费者契约

### 4. 全局优先级模型

**问题：** 当同时有 10 个项目要推进，哪个最该做？

**旧做法：** 凭感觉，导致忙得不停但做的是最不紧急的事。

**新做法：** 按优先级矩阵，优先级来自四个维度：

```
优先级 = f(收入潜力, 阻断面, 学习价值, 执行成本)
```

#### 优先级决策框架

| 优先级 | 特征 | 例子 | 操作 |
|-------|------|------|------|
| 🔴 **P0 阻断** | 某个关键路径上的 blocker；其他 3+ 个项目等待这个完成 | Cloudapi 的能力增强被 4 个项目等待 | 立即处理，可中断其他工作 |
| 🟠 **P1 核心** | 直接产生收入或验证关键假设的项目；当前应该专注的方向 | SoloMap 新功能、内容产品周期性输出 | 本周必做，按计划推进 |
| 🟡 **P2 积累** | 有价值但不紧急；做了会增强能力池，但没有时间限制 | 新的可复用模式、工具完善、文档更新 | 有空余时间就做 |
| 🟢 **P3 试验** | 学习型项目；结果可以失败，重在探索 | 新想法验证、小工具试验 | 利用碎片时间 |

**如何运用这个框架：**

每周/每天，问自己三个问题：

1. **有没有 P0？** 有→立即处理，其他让开。
2. **本周的 P1 是什么？** 明确一个，其他都是 P2。
3. **P2 和 P3 能并行吗？** 用碎片时间交替。

### 5. 全局学习循环

SoloMap 的四阶段循环是**项目内的学习**。全局方法论要加入**项目间的学习**。

```
单个项目的学习流         全局学习流
        ↓                      ↓
  问题→方案→验证          验证结果
        ↓                  ↓     ↓
    本项目记忆      是否跨项目  进入 .codex-memory
                   适用？
                      ↓
                  能力/决策/模式
                  进入全局池
                      ↓
              下个项目自动查询
```

**关键转变：** 不是"项目 A 完成，然后项目 B 从零开始"，而是"项目 A 的学习变成项目 B 的起点"。

## 第三部分：执行约束

### 6. 多项目并行时的执行纪律

#### 原则 1：同一时间，同一个方向

**为什么？** 并行不等于同时做。你的大脑在项目之间切换有成本。

**做法：**
- 每个 8 小时工作块，分配到 1-2 个项目
- 同一项目的多个环节尽量连续推进
- P0 中断除外，否则坚持当前项目推完再切

#### 原则 2：三层决策清晰分离

| 层级 | 决策者 | 频率 | 权力范围 |
|-----|--------|------|---------|
| 全局优先级 | 你 | 每周 | 哪个项目本周该做 |
| 项目路线图 | SoloMap + Agent | 每个项目 | 这个项目的环节拆分 |
| 环节执行 | Agent + 你 | 每次 | 这个环节怎么做 |

**错误做法：** 
- ❌ 每天改全局优先级（导致上下文切换成本太高）
- ❌ 让 Agent 决定"本周该做哪个项目"（这是你的权力）
- ❌ 手工调整每个环节的细节（这是 Agent 该管的）

#### 原则 3：知识管理必须与执行同步

**问题：** 项目做完了，知识也丢了。

**做法：** 
- 每个环节完成时，SoloMap 自动捕获可复用的学习候选
- 每周审核一次学习候选，决定是否进入 `.codex-memory`
- 进入 `.codex-memory` 的东西，下个项目自动查询

### 7. 项目间的依赖与协调

当项目之间有依赖关系时，优先级的计算就变了。

```
例: CLOUDMCP 依赖 Cloudapi
  
  CLOUDMCP 想做新功能 X
    → 但需要 Cloudapi 先增强能力 Y
      → Cloudapi 的能力 Y 在 P2
        → 因为 CLOUDMCP 等待，Y 升到 P1

跨项目依赖链会自动调整优先级
```

**管理依赖的方法：**

1. **显式建模：** 在全局 `portfolio.csv` 中记录跨项目依赖
2. **优先级联动：** 依赖的下游被阻断时，上游自动升到 P1
3. **定期检查：** 每周扫一遍有没有被隐形阻断的项目

### 8. 能力复用的三个时机

能力复用不是"被动等别人分享"，而是**主动识别和复用**。

#### 时机 1：项目初始化
```
新项目 A 要开始
  → 检查 .codex-memory/patterns
  → "这个问题我们在项目 B 解过"
  → 复用项目 B 的成熟方案
  → 项目 A 快 2 倍
```

#### 时机 2：环节卡点
```
项目 C 环节 3 遇到问题
  → SoloMap 自动查询 .codex-memory
  → "同类问题在项目 D 怎么解决的"
  → Agent 参考历史方案
  → 问题更快被解决
```

#### 时机 3：决策冲突
```
项目 E 的新架构和项目 F 的设计方向冲突
  → 查看 .codex-memory/decisions
  → 看过往类似冲突怎么处理的
  → 做出全局最优决策，而不是项目内最优
```

## 第四部分：知识与工具

### 9. `.codex-memory` 在全局方法论中的角色

`.codex-memory` 不是"备忘录"，而是**全局决策的材料库**。

#### 五层知识模型

```
profile.md
  ↓
  你的长期偏好、工作风格、禁忌
  （稳定的，很少变）

operating-rules.md
  ↓
  跨项目的执行原则、决策规则
  （通用的，多项目都适用）

domains/
  ↓
  后端、前端、产品、基础设施的领域知识
  （技能层，跨项目复用）

patterns/
  ↓
  解决过的问题类型、成熟方案、排障套路
  （方案层，具体且可操作）

decisions/
  ↓
  已确认的技术决策、架构决策、业务决策
  （决策层，明确理由和影响范围）

projects/
  ↓
  各项目的长期稳定事实、当前状态、入口
  （项目层，项目级记忆）
```

**关键原则：**
- 信息流是**向上沉淀，向下查询**
- 项目级学习 → patterns/decisions → 下个项目查询
- 从不混用通用规则和项目特例
- 所有知识都要有"何时适用、何时不适用"的清晰边界

### 10. SoloMap 与 `.codex-memory` 的协作

#### 模型 A：现在（知识被动分离）

```
SoloMap 项目内工作
  ↓
  完成
  ↓
  知识留在 .solopreneur/
```

#### 模型 B：目标（知识主动流转）

```
SoloMap 项目内工作
  ↓
  查询 .codex-memory（查看相似案例）
  ↓
  执行和学习
  ↓
  生成学习候选
  ↓
  定期审核 + 提升到 .codex-memory
  ↓
  下个项目自动查询这些知识
```

**具体工作流：**

1. **初始化时：** 新项目 → 扫 `.codex-memory/patterns` → 找相似项目的起点方案 → 快速初始化
2. **执行时：** 遇到问题 → Agent 查询 `.codex-memory/` → 推荐已知解法 → 快速解决
3. **完成后：** 环节完成 → 自动提取"这个模式可能跨项目适用" → 周期审核 → 提升
4. **下个项目：** 重复循环

## 第五部分：度量与反馈

### 11. 如何衡量复利效果

复利的核心是**投入不增加，但产出在加速**。

#### 度量 1：环节完成速度加快

```
项目 A 完成某个环节耗时: T_a
项目 B 同类环节耗时:    T_b
项目 C 同类环节耗时:    T_c

如果 T_a > T_b > T_c，说明复利在生效

目标：T_c ≈ T_a / 2  （复用经验，速度翻倍）
```

#### 度量 2：重复问题减少

```
新项目启动时的 blocker 数: N_first
类似类型的第二个项目:     N_second

如果 N_second < N_first * 0.5，说明学习在积累
```

#### 度量 3：决策冲突提前发现

```
跨项目决策冲突：
  - 第一次: 完全没看到，到冲突时才发现
  - 第二次: 提前在规划时就看到了
  
说明全局决策透明度在提升
```

#### 度量 4：能力复用率

```
新环节需要的能力
  ├─ 第一次出现: 100% 需要自己创造
  ├─ 第二次: 70% 能直接复用，30% 需要改进
  └─ 第三次: 95% 能直接复用，5% 只需微调

复用率从 0% → 70% → 95%，说明能力沉淀在发生
```

### 12. 反馈与调整

全局方法论不是一成不变的。你需要定期评估和调整。

#### 月度反思（高层）

- ✓ 这个月最有效的是什么？（值得坚持）
- ✗ 哪些决策事后看是错的？（需要改进）
- ❓ 发现了什么新的跨项目模式？（值得记录）
- 🚀 下个月的全局优先级应该怎么调？

#### 季度审查（中层）

- 32 个项目中，哪些是"核心"该专注？
- 哪些基础设施投入回报率最高？
- 是否出现了新的项目类型需要新的执行模式？
- `.codex-memory` 中的知识是否真的在被复用？

#### 年度规划（顶层）

- 过去一年，投资回报率从多少变到多少？
- 是否从"阶段 1：基础积累"升到了"阶段 2：有向复用"？
- 下一年的目标是什么？

## 第六部分：实践指南

### 13. 快速开始

#### 本周行动

1. **分类你的项目**
   - 打开 `.solomap-global/portfolio.csv`
   - 把 32 个项目分到 6 个类别中
   - 记录每个项目的"为什么要做"和"当前状态"

2. **确定本周 P0 和 P1**
   - 有没有被其他 3+ 个项目阻断的工作？ → 如果有，这是 P0
   - 这周最该推进什么？ → 这是 P1
   - 其他都是 P2 或 P3

3. **激活 `.codex-memory` 查询**
   - 新项目初始化前，扫一遍 `.codex-memory/projects/`
   - 看有没有相似的项目可以学
   - 复制他们的起点方案

#### 本月行动

4. **建立学习审核流程**
   - 每周五，查看 `.solomap-global/.solopreneur-learning/`
   - 标记"这个值得跨项目复用"
   - 推送到 `.codex-memory/inbox/`

5. **第一次跨项目复用**
   - 找两个类似的项目（比如都是内容产品）
   - 从第一个项目的 `step-memory` 复制方案
   - 用到第二个项目，记录耗时对比

#### 本季度行动

6. **全面推行全局优先级**
   - 不再按"感觉"切换项目
   - 用优先级矩阵做决策
   - 月度评估优先级是否合理

### 14. 常见陷阱

#### ❌ 陷阱 1：过早追求"全局最优"

**错误：** 第一周就尝试优化所有 32 个项目的依赖

**正确：** 从最关键的 3-5 个项目开始，先让这些项目的复利效果明显，再扩大

#### ❌ 陷阱 2：把所有知识都往 `.codex-memory` 写

**错误：** 每个环节的细节都记，导致记忆爆满，查询效率下降

**正确：** 只记"跨项目第二次以上出现的知识"。第一次出现的东西留在 `step-memory`

#### ❌ 陷阱 3：决策权下沉给 Agent

**错误：** 让 Agent 决定"本周该做哪个项目"

**正确：** 你决定优先级，Agent 决定环节怎么执行

#### ❌ 陷阱 4：知识管理与执行脱离

**错误：** 有完整的 `.codex-memory`，但项目里从不查询

## 附录 A：全局方法论与 SoloMap 四阶段的关系

SoloMap 的四阶段循环（问题发现 → 产品打造 → 市场触达 → 规模化改进）**并未改变**，只是**嵌入到了全局循环中**。

```
全局循环

发现跨项目的问题类型
  ↓
分配给合适的项目
  ↓
  ├─ 项目内 SoloMap 四阶段
  │   ├─ 问题发现
  │   ├─ 产品打造
  │   ├─ 市场触达
  │   └─ 规模化改进
  │
  └─ 环节完成
      ↓
      提取跨项目学习
      ↓
      进入全局能力池
```

每个项目仍然遵循 SoloMap 的四阶段，但**每个阶段的起点都比上一个项目更高**（因为有之前项目的积累）。

## 附录 B：术语表

| 术语 | 定义 |
|------|------|
| **投资组合** | 所有项目的集合，视为一个整体 |
| **全局优先级** | 跨项目的执行优先级，根据收入潜力、阻断面、学习价值、执行成本计算 |
| **能力复用** | 在一个项目中验证成功的方案，在下个项目中直接使用 |
| **跨项目依赖** | 一个项目的完成被另一个项目所依赖 |
| **学习候选** | 项目完成后，可能跨项目适用的知识，等待审核 |
| **全局能力池** | `.codex-memory/` 中已确认的模式、决策、知识 |
| **复利效应** | 后续项目的执行速度因能力复用而加快 |
