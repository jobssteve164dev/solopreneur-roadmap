# 上下文检索与记忆分类方法论

## 这份文档解决什么判断

这份文档指导 Agent 在任务开始时决定“需要读什么”，在任务结束时决定“新知识应该写到哪里”，避免两个相反问题：启动时把所有知识塞进上下文，结束时又把所有结论都塞进项目记忆。

核心判断只有一句：**知识按任务需要进入执行，按未来复用范围进入记忆。**

## 适用范围

适用于 SoloMap 管理的 Solo、路线图环节、Flow、复核、路线图调整，以及未来接入同一记忆系统的其他 Agent 运行。

## 开始任务：先判断需要什么知识

### 第一步：读取不可跳过的当前事实

- 用户本轮原话。
- 项目规则。
- 用户明确附加的文件、日志或错误。
- 当前代码、配置、测试和运行状态。

历史知识不能替代这一步。

### 第二步：按判断类型选入口

| 当前需要回答的问题 | 优先入口 |
| --- | --- |
| 用户长期偏好、沟通禁忌是什么 | `profile.md` |
| 跨任务执行和验证规则是什么 | `operating-rules.md` |
| 当前项目已有事实、入口和边界是什么 | `projects/<project>.md` |
| 是否存在不能随意改变的既有选择 | `decisions/` |
| 是否有同类实现、排障或验证套路 | `patterns/` |
| 是否涉及稳定业务、平台或协议知识 | `domains/` |
| 上一轮做到哪里 | `active/current-session.md` |
| 正式项目文档在哪里 | `.solopreneur/documentation.json` |
| 是否有明确领域技能 | 技能 registry，再读命中的 `SKILL.md` |
| 是否需要历史运行经验 | `solomap-experience.cjs retrieve` |

### 第三步：决定是否查询账本

仅在以下情况查询：

- 接续或复核先前运行。
- 同一故障再次出现。
- 用户询问历史行为或既有处理。
- 当前证据不足，需要定位可能相关的 run。
- 需要复用已经证明有效的验证或排障路径。

普通首次内容任务、简单修改和开放讨论默认不查询。

### 第四步：形成高信号查询

查询应至少包含一种具体对象：

- 功能名。
- 文件或模块。
- 明确错误文本或错误类别。
- 用户要达成的具体结果。

不要用 URL、项目名、Solo/Flow、运行状态等泛化信息查询。如果第一次没有结果，应补充具体对象，而不是降低质量门槛。

## 使用检索结果

对返回结果按以下顺序消费：

1. 检查“适用条件”是否与当前任务一致。
2. 检查证据是否来自同类功能、文件或错误。
3. 把“应做”和“避免”转成本轮计划或验证项。
4. 回到当前代码、日志和测试确认。
5. 只有需要追溯时才打开 digest 或原始运行记录。

如果没有高质量经验，直接使用当前事实继续工作。空结果是正常结果。

## 结束任务：先分类再写记忆

任务结束前，对每条新信息依次判断：

| 判断问题 | 目标位置 |
| --- | --- |
| 换一个项目仍然是用户偏好吗 | `profile.md` |
| 所有任务都应遵守的执行规则吗 | `operating-rules.md` |
| 只对当前项目成立的稳定事实或入口吗 | `projects/` |
| 是否存在明确选择、理由和长期影响 | `decisions/` |
| 是否能指导另一个项目完成同类任务 | `patterns/` |
| 是否是跨项目成立的业务或技术知识 | `domains/` |
| 是否尚未充分验证 | `inbox/` |
| 是否只对下一轮交接有用 | `active/` |
| 是否只是本轮发生了什么 | 不写 |

### 写入项目记忆前的反向检查

准备写入 `projects/` 时，必须先回答：

1. 这是不是一个有明确理由和影响的决策？如果是，进入 `decisions/`。
2. 这是不是另一个项目也能复用的做法？如果是，进入 `patterns/`。
3. 这是不是独立于项目存在的领域事实？如果是，进入 `domains/`。
4. 只有具体入口、当前实现事实和本项目边界才留在项目记忆。

同一事实不应为了“保险”全文复制到多个位置。允许项目记忆保留一句入口索引，指向正式 decision、pattern 或 domain。

## 稳定记忆写入门槛

一条信息进入稳定记忆前必须同时满足：

- 已由用户明确确认，或由当前代码、测试、日志和命令结果验证。
- 未来大概率能改变一次执行判断。
- 能明确说明适用范围。
- 不包含原始 Prompt、终端日志、diff、提交记录和执行流水。
- 不与现有记忆重复。

不满足时写入 inbox、active 或不写，不能为了填充记忆目录而制造内容。

## 从候选到稳定记忆

学习候选不是稳定事实。候选晋升前应检查：

- 是否经过一次强验证或多次一致复用。
- 是否能写出明确的适用条件、行动和避免事项。
- 是否通过低价值内容过滤。
- 是否能确定作用域和目标位置。
- 是否与已有记忆重复或冲突。

晋升后：

- 项目事实进入 `projects/`。
- 架构或产品选择进入 `decisions/`。
- 可复制的方法进入 `patterns/`。
- 稳定领域知识进入 `domains/`。
- 跨任务行为约束进入 `operating-rules.md`。

## 质量自检

任务交付前进行两次检查：

### 检查一：读取是否克制

- 是否读取了与当前问题无关的整份账本或文档目录？
- 是否因为弱关键词打开了无关历史任务？
- 是否让历史线索覆盖了当前事实？

### 检查二：写入是否正确

- 是否又把决策、模式和领域知识全部写进项目记忆？
- 是否把本轮过程当成长期知识？
- 是否存在应该晋升但仍只留在对话里的验证结论？
- 是否把未经验证观察写成稳定事实？

任一检查不通过，任务的知识闭环就没有完成。

## 示例

一次“优化首次 Prompt”的任务可能产生三类不同知识：

- “该插件的正式查询命令和代码入口”只属于当前项目，进入项目记忆。
- “首次 Prompt 采用索引而不是知识全文”是明确设计选择，进入决策。
- “无高质量经验时宁可返回空结果”能用于其他检索系统，进入模式。

三者来自同一任务，但不能因为执行发生在同一个项目中就全部写入项目记忆。
