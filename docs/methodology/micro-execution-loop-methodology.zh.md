# SoloMap 微观执行循环方法论

## 这份文档解决什么判断

这份文档固定 SoloMap 如何把 Agent CLI 的执行黑箱拆成可观察、可复核、可滚动的微观循环。

核心判断只有一句：**一个项目不是由一次路线图推进自然完成的，而是由无数个“意图变成项目事实”的微观循环塑造出来的。**

## 方法论定位

路线图回答宏观问题：

```text
这个项目下一步要达成什么目标？
```

微观执行循环回答事实问题：

```text
Agent 如何把一个具体意图规划、实施、验证，并归并成路线图进展？
```

因此执行轨迹不是日志、总结、diff 包装或漂亮看板。它是 SoloMap Agent Task Flow 的事实账本：每个宏观环节是否可以推进，必须由足够多已闭环的微观循环支撑。

## 微观循环六阶段

每个微观循环必须围绕六个阶段留痕：

```text
意图 -> 判断 -> 动作 -> 证据 -> 结果 -> 归因
```

### 1. 意图

意图说明这轮循环为什么发生，以及项目希望被塑造成什么样。

应记录：

- 来源：路线图环节、用户输入、Issue、失败测试、Agent 发现、上一循环遗留问题。
- 用户原始要求。
- Agent 抽象出的微观目标。
- 本轮要改变的用户能力、项目边界或质量状态。
- 本轮明确不做什么。

关键判断：意图不清时不能进入实施。否则 Agent 会把用户目标翻译成自己熟悉的工程问题。

### 2. 判断

判断说明 Agent 准备怎样实现意图，以及为什么选择这条路径。

应记录：

- 计划路径。
- 影响范围。
- 依赖文件、模块、文档或外部状态。
- 关键取舍。
- 需要保留的边界。
- 已知风险和暂不处理项。
- 预期验证方式。

关键判断：黑箱不只来自代码不可见，也来自“为什么这样改”不可见。判断阶段必须可回看。

### 3. 动作

动作说明 Agent 实际做了什么。

动作应按项目塑形语言归类，而不是按终端流水账归类：

- 新增能力。
- 改造路径。
- 修复缺陷。
- 固化边界。
- 补强验证。
- 清理债务。
- 回退偏差。
- 更新长期说明。

应记录：

- 触碰的能力、模块和文件。
- 新增、修改或删除的测试。
- 变更的数据结构、配置、UI、文档或脚本。
- 新增的入口、状态、契约或边界。

关键判断：动作必须来自真实文件变化、diff、命令输出或运行事实，不能只来自 Agent 自述。

### 4. 证据

证据说明凭什么认为动作成立。

应记录：

- 测试命令和结果。
- 构建、lint、typecheck 或脚本校验结果。
- UI 截图、浏览器检查或人工验收。
- 运行日志中的关键结论。
- commit、diff 或 touched files。
- 设计对标结果。
- 未覆盖验证项。

关键判断：没有证据的动作只能是“声称完成”，不能是“已完成”。

### 5. 结果

结果说明本轮循环最终把项目推到了哪里。

结果状态至少包括：

| 状态 | 含义 |
| --- | --- |
| `closed` | 已实施且证据支撑闭环 |
| `implemented_unverified` | 已实施但缺少必要验证 |
| `verified_failed` | 已验证但失败 |
| `partial` | 只完成一部分目标 |
| `deviated` | 实际结果偏离原始意图 |
| `spawned_followup` | 产生新的微观循环 |
| `abandoned` | 明确放弃，不再推进 |

关键判断：CLI 退出码不等于结果。结果必须由意图、动作和证据共同决定。

### 6. 归因

归因说明这轮微观结果向上贡献给什么。

应记录：

- 所属路线图环节。
- 命中的环节完成标准。
- 推进的用户能力。
- 固化或改变的工程边界。
- 增加、减少或暴露的风险。
- 是否足以更新宏观进度。
- 是否需要生成下一轮微观循环。

关键判断：只有归因成立，微观循环才能推动路线图。否则它只是孤立工作记录。

## 微观循环与路线图的关系

路线图环节不应由单次 Agent run 推进，而应由微观循环聚合推进。

```text
路线图环节
  -> 微观循环 1：closed
  -> 微观循环 2：closed
  -> 微观循环 3：implemented_unverified
  -> 微观循环 4：verified_failed -> spawned_followup
```

当环节完成标准被足够多 `closed` 循环覆盖，且关键风险没有未闭环缺口时，路线图环节才可以完成。

如果存在 `implemented_unverified`、`verified_failed`、`partial` 或 `deviated`，系统应优先生成下一轮微观循环，而不是让路线图假完成。

## 与 Agent Task Flow 的关系

Agent Task Flow 是执行编排；微观执行循环是它的最小可靠单元。

```text
Roadmap = 行动目标
Micro Execution Loop = 行动如何变成事实
Execution Trace = 多个微观循环串成的项目成长轨迹
Agent Task Flow = 用这些事实驱动下一次执行和路线图滚动
```

没有微观循环，Task Flow 只能依赖 Agent 自称完成、CLI 退出码或用户手工判断。  
有了微观循环，Task Flow 可以基于证据持续滚动。

## 用户介入点

执行轨迹应让用户在以下位置介入，而不是要求用户逐行读 diff：

- 意图是否被理解错。
- 判断是否偏航。
- 动作是否只修了表面。
- 证据是否不足。
- 结果是否被过度宣称。
- 归因是否错误推动了路线图。

这些介入点是人在回路的核心，不是附加审查功能。

## 禁止项

- 禁止把微观循环退化为单次 Agent run 摘要。
- 禁止把执行轨迹做成原始日志浏览器。
- 禁止只展示文件 diff，而不展示意图、判断、证据和归因。
- 禁止让 Agent 自己单方面决定路线图是否完成。
- 禁止把没有证据的动作标记为已完成。
- 禁止把方法论解释堆到前台，增加用户认知负担。
