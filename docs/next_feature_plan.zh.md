# SoloMap 下一阶段功能优化开发文档

## 目标

把 SoloMap 方法论从文档变成产品里会判断适用场景的默认推进系统。

对需要面向用户验证并获得采用或付费的产品，SoloMap 应把用户带入一条清晰路径：

```text
发现问题 -> 打造产品 -> 卖给客户 -> 持续改进
```

对内部工具、迁移、研究、内容或基础设施项目，不应虚构获客和销售环节，而应围绕真实交付与验收组织路线图。两类项目共用的插件操作循环是：

```text
项目想法 -> 方法论路线图 -> 下一步动作 -> Agent 对话 -> 本地交付 -> 状态闭环 -> 路线图更新
```

## 产品判断

当前 SoloMap 已经具备：

- 项目级 `.solopreneur/` 本地数据目录。
- Git 友好的 `roadmap.csv`。
- 路线图环节卡片。
- 环节内 Agent 对话历史。
- Agent CLI 指派、运行、停止、重试和文件修改记录。
- 路线图调整入口。
- Solo 直接对话入口，可先处理问题，再决定是否关联到已有环节。

下一步的关键是减少用户打开插件后的判断成本：需要按计划推进时选择环节，需要快速讨论或处理临时问题时直接开始。用户应该立刻知道：

- 现在项目处于哪个阶段。
- 下一步最该做什么。
- 为什么是这一步。
- 可以直接让哪个 Agent 做。
- 做完后如何判断闭环。

## 优先级概览

| 优先级 | 功能方向 | 目标 |
| --- | --- | --- |
| P0 | 自适应方法论路线图模板 | 对商业化产品默认覆盖从问题到增长的路径，对其他项目尊重真实交付目标 |
| P0 | Next Action 视图 | 用户打开插件后直接看到下一步动作 |
| P1 | 环节完成标准模板 | 让每个环节知道什么叫完成 |
| P1 | Solo 直接对话 | 不要求用户先判断所属环节，结束后再按需要关联 |
| P1 | Build -> Sell -> Learn -> Improve 方法论落地 | 用底层方法论驱动 Next Action、路线图调整和大图视角 |
| P2 | 市场动作任务化 | 把品牌、官网、营销、销售、反馈变成 Agent 可执行任务 |

## 已落地：Solo 直接对话

### 用户动作

用户可在路线图顶部点击 `Solo`，或直接在侧边栏项目总览上方的 Solo 对话卡片中选择项目与 Agent，提出临时修复、判断或头脑风暴问题，不需要先打开项目或选择一个路线图环节。对话结束后，用户可以：

- 保持为 Solo 对话历史，不改变路线图。
- 将本次结论关联到一个已有环节，作为该环节的参考记录。
- 转入“调整路线图”，明确改变计划结构或方向。

### 产品边界

- Solo 对话保存在项目日志中，但本身不是路线图环节。
- 从侧边栏发起的 Solo 对话写入所选项目自己的 Solo 历史，与路线图中的 Solo 入口共用同一记录链路；选择总览中的项目时，Solo 目标项目同步切换。
- 路线图顶部与侧边栏的 Solo 输入都支持添加项目内补充文件，供 Agent 读取本次问题所需上下文，切换项目时不保留旧附件。
- 侧边栏 Solo 卡片展示所选项目最近一次 Solo 对话，可展开查看本轮结果、Agent 结论、命令与输出；完整历史仍在路线图顶部的 Solo 面板中查看。
- 关联操作只增加参考记录，不自动改变环节状态或完成判断。
- Solo 对话不会直接修改路线图；需要改变路线图时使用专门的调整入口。
- 讨论类 Solo 对话可以只交付结论，不因没有文件修改而被判断为失败。

## P0：方法论路线图模板

### 用户价值

新项目不应机械生成开发任务，也不应机械生成销售任务。对于面向外部用户并需要获客、采用或转化的产品，健康的 SoloMap 路线图默认覆盖四层：

1. 问题与客户发现。
2. 产品基础与首个可用版本。
3. 分发、品牌、官网、营销和销售。
4. 反馈、数据、支持、单位经济模型和扩张。

这能避免商业化产品把 SoloMap 当成普通 AI TODO 工具，也能让独立开发者从第一天就面向交付和市场。对于内部工具、迁移、研究、内容或基础设施项目，路线图应改为其真实交付、验收和迭代路径，而不是补出并不存在的营销销售任务。

### 产品行为

新项目初始化时，默认路线图仍保留“生成初始路线图”环节。Agent 先基于项目文件判断目标和服务对象；只有项目需要外部用户采用、获客或转化时，生成的真实路线图才默认覆盖方法论四层。

路线图调整时，也应提示 Agent 先判断本次目标是否包含产品市场闭环。对商业化产品，不要只调整工程任务，而要检查是否影响：

- 问题定义。
- 产品交付。
- 市场触达。
- 学习与改进循环。

对不包含市场目标的项目，应围绕其真实交付物、验证方式、使用反馈或验收结果调整路线图，不强制出现营销和销售阶段。

### 建议实现

新增一个方法论路线图指令文件，例如：

```text
.solopreneur/roadmap-methodology.md
```

内容由插件生成，写入项目 `.solopreneur/`，并在初始化路线图和路线图调整 prompt 中引用。不要把长方法论文本直接塞进 `roadmap.csv`。

商业化产品模板要求：

- 至少包含四个阶段。
- 每个阶段至少有一个可执行环节。
- 每个环节必须有可交付结果。
- 不允许只生成“研究”“规划”这类无闭环任务。
- 市场阶段不能缺失。
- 学习改进阶段不能缺失。

所有项目共用要求：

- 阶段名称与任务必须匹配真实目标，不能为满足模板创造无意义任务。
- 每个环节必须产生可查看的本地交付物或验证记录。
- CSV 校验只保障结构、依赖和可执行性，不通过硬编码阶段推断项目类型。

### 验收标准

- 面向外部用户并需要获客或转化的新项目，生成的真实路线图覆盖四层方法论。
- 内部工具、迁移、研究、内容或基础设施项目可以生成与其目标相称的阶段，而不会因缺少营销销售阶段被拒绝。
- `roadmap.csv` 中不出现大段提示词文本。
- 旧项目仍能正常读取现有路线图。
- 商业化产品的路线图调整仍保留方法论覆盖，不会无意退化成纯工程任务。
- 非商业化项目的路线图调整不会被迫引入虚假的市场任务。

## P0：Next Action 视图

### 用户价值

用户打开 SoloMap 时最需要的不是完整路线图，而是“我现在该做什么”。

Next Action 视图应成为侧边栏的核心入口，帮助用户直接推进，而不是先浏览所有卡片。

### 产品行为

侧边栏顶部新增一个紧凑区域：

```text
下一步
当前最该推进：{环节标题}
原因：{一句话}
输入框：补充这次要 Agent 做什么
Agent 选择器
发送按钮
```

它应直接复用环节对话链路，不创建新的任务系统。

### Next Action 选择规则

第一版可以用确定性规则，不需要额外 AI：

1. 如果存在 `Running` 环节，Next Action 指向该环节，提示用户查看运行状态。
2. 否则选择第一个 `Failed` 环节，提供重试入口。
3. 否则选择第一个 `In Progress` 环节。
4. 否则选择依赖已满足的第一个 `Pending` 环节。
5. 否则如果所有环节完成，指向路线图调整或 Build -> Sell -> Learn -> Improve 循环。

### 展示信息

Next Action 卡片应展示：

- 环节标题。
- 所属阶段。
- 当前状态。
- 最近一次 Agent 运行摘要。
- 修改文件数量。
- 主要失败原因或下一步建议。
- 直接发送 Agent 对话的输入框。

### UI 原则

- 不展示复杂解释。
- 不要求用户理解内部排序规则。
- 不引入新的“任务对象”。
- 只服务一个动作：继续推进当前最重要的环节。

### 验收标准

- 侧边栏打开后，用户能在首屏看到下一步动作。
- 点击发送后，走现有 `runAgent` 链路。
- 运行状态、失败、完成后，Next Action 会自动切换。
- 项目切换后，Next Action 与当前项目隔离。

## P1：环节完成标准模板（已落地）

### 用户价值

现在环节可以被用户点击完成，但“完成”标准还不够明确。每个环节应该有一个轻量闭环定义。

### 产品行为

每个路线图环节应拥有可读的完成标准：

- 本环节要交付什么。
- 完成后应该出现哪些文件、页面、配置或市场动作。
- 是否需要用户确认。
- 是否需要进入下一阶段。

### 建议数据结构

第一版不必改变 `roadmap.csv` schema。可以在 `.solopreneur/step-memory/<nodeId>.json` 中增加：

```json
{
  "completionCriteria": [
    "..."
  ],
  "lastCompletionEvidence": [
    "..."
  ]
}
```

如果未来需要在路线图中直接展示，再考虑扩展 CSV 字段。

### UI 行为

环节展开后，在对话输入区附近展示一段轻量完成标准。

不要做复杂表单。用户只需要：

- 查看标准。
- 让 Agent 按标准推进。
- 点击完成环节。

### 验收标准

- 新生成路线图的每个环节都有完成标准。
- Agent 对话 prompt 会要求 Agent 对照完成标准交付。
- 用户点击完成时能看到该环节标准。
- 旧项目无标准时不会报错。

### 落地说明

- 完成标准保存在 `.solopreneur/step-memory/<nodeId>.json` 的 `completionCriteria` 中，不改变 `roadmap.csv` schema。
- 旧项目打开时会按环节标题、阶段和 Agent prompt 自动补齐默认完成标准。
- Agent prompt 会读取并注入该环节完成标准；只有达到标准时才应写入完成判断。
- 大图中展开环节会展示完成标准；用户点击“完成环节”即为手动确认，该决定优先于 Agent 运行状态和后续回传。

## P1：Build -> Sell -> Learn -> Improve 方法论落地与输入流转机制

### 用户价值

方法论里的规模化不是线性终点，而是循环。在独立开发者的心智模式中，项目推进不应只是一条单向的工程流水线，而是一个围绕 **产品交付 (Build) -> 触达分发 (Sell) -> 获取反馈 (Learn) -> 调整优化 (Improve)** 的闭环飞轮。SoloMap 旨在帮助用户动态观测并推动这个闭环的运转，避免项目长期陷于“只写代码、没有用户、不去运营”的单点停滞状态。

### 产品决策

Build -> Sell -> Learn -> Improve 是 SoloMap 的项目判断模型，不是侧边栏里的常驻大组件。

落地边界见 [四阶段视图组件设计指导](./four-stage-view-guidelines.zh.md)。核心原则是：

- 侧边栏只显示四阶段推导出的下一步和轻量缺口信号。
- 大图可以显性展示完整四阶段视角，用于理解、筛选和导航路线图。
- 路线图生成与调整把四阶段作为底层审查标准，用户不需要手动维护它。

### 四阶段深度理解与工件细化

在 SoloMap 中，这四个阶段均在本地项目工作区中拥有具体的**实体工件（Artifacts）**和**闭环定义（DoD）**：

| 阶段 | 核心心智与定位 | 本地项目文件载体 | 闭环与验证标准 (DoD) |
| :--- | :--- | :--- | :--- |
| **1. Build** <br>*(产品交付)* | 验证“技术上是否可行”。以最小的心智负担交付最高内聚的功能增量（MVP）。 | `src/` (核心源码)<br>`package.json` (配置)<br>`.solopreneur/step-memory/` | 1. 业务逻辑或页面代码发生实质变更；<br>2. 本地回归测试与编译通过；<br>3. 产出可本地验证或直接部署的工件。 |
| **2. Sell** <br>*(分发触达)* | 验证“市场是否买单”。解决产品价值的外部呈现，将分发资产作为一等公民对待。 | `landing/` (网页版成交落地页)<br>`docs/sales-brief.md` (销售简报)<br>`outreach/` (外联执行清单)<br>`proposals/` (商业提案) | 1. 产出文案、外联 leads 或商业提案文件；<br>2. 落地页价格、CTA 与承诺阐述就绪；<br>3. 生成可直接发出的外联邮件/私信。 |
| **3. Learn** <br>*(学习反馈)* | 验证“用户如何使用”。系统化收集并沉淀真实的定性用户声音与定量转化指标。 | `docs/feedback/` (访谈/客服手记)<br>`docs/analytics.md` (关键漏斗指标)<br>`leads.csv` (线索流转状态看板)<br>GitHub Open Issues | 1. 记录了至少一份用户 qualitative 反馈；<br>2. 补充并更新了 quantitative 指标数据；<br>3. 梳理提炼出结构化的云端/本地 To-Dos。 |
| **4. Improve** <br>*(反思改进)* | 验证“下一步该怎么走”。将吸收的外部反馈转化为具体的计划调整与路线重组。 | `.solopreneur/roadmap.csv` (路线图)<br>`.solopreneur/roadmap-methodology.md`<br>`__solo__` (临时调整与头脑风暴) | 1. 重新验证并合法改写 `roadmap.csv`；<br>2. 基于新反馈确立了下一个 `Next Action`；<br>3. 新环节的完成标准（DoD）自动补全。 |

### 产品行为与 UI 呈现

侧边栏不新增常驻四阶段大面板，避免项目卡片进一步变重。侧边栏只保留轻量阶段信号，并把四阶段判断转化为 Next Action：

```text
下一步：补齐分发动作
```

或：

```text
Build 3 · Sell 0 · Learn 2 · Improve 1
```

大图中可以增加项目级四阶段视角，用于查看项目飞轮是否失衡，并定位路线图环节：

```text
+-----------------------+-----------------------+
|  Build (产品构建)      |  Sell (市场分发)      |
|  - 最近交付: src/...  |  - 最近分发: landing/ |
|  - 状态: 🟢 已完成    |  - 状态: 🟡 待优化    |
+-----------------------+-----------------------+
|  Learn (外部学习)      |  Improve (计划改进)   |
|  - 最近反馈: 3 份 qualitative | - 下一步: 🚀 Next Action|
|  - 状态: 🔵 已更新    |  - 状态: ⚡ 推进中    |
+-----------------------+-----------------------+
```

1. **象限映射与状态推断**：
   - **Build**：自动映射当前项目已完成的工程、源码类环节。
   - **Sell**：自动映射已完成的品牌、文案、推广或分发类环节。若长时间无该类型环节完成，此槽位将亮起“黄色/橙色”警告徽标，督促用户“该做分发了”。
   - **Learn**：映射当前项目中 `.solopreneur/feedback/` 及 GitHub Issues 的最新解析动态。
   - **Improve**：指向当前项目最紧迫的 `Next Action`，或路线图调整的第一个待办环节。
2. **交互体验**：
   - 侧边栏阶段信号点击后，只打开大图对应视角或定位相关环节，不展开新模块。
   - 大图中每一个象限均可点击，点击后高亮显示其关联的本地文件列表或直接跳转至路线图对应的卡片区域。
   - 动效只用于表达状态变化或阶段流转，不做纯装饰，不阻碍用户继续推进 Next Action。

### 📥 结构化输入 (Inputs) 流转机制设计

为了实现任务自动化流转，各阶段之间的“输入-输出”管道必须严格结构化。

```text
 📥 外部输入 (GitHub Issues/定性访谈/leads看板)
                       ↓
  [ docs/feedback/ ] & [ leads.csv ] & [ gh CLI outputs ]
                       ↓
    🧠 SoloMap 输入解析器 (自动分析节点属性，打包相关度最高的上下文)
                       ↓
    💬 写入 prompt.txt (注入为 Agent 系统 Prompt 里的 ## 真实输入反馈 章节)
                       ↓
    🤖 Agent 在本地执行 (完美吸纳反馈，产出完全解决问题的代码与文档)
```

1. **输入源本地沉淀**：
   - **定性数据**：在 `.solopreneur/feedback/` 或 `docs/feedback/` 沉淀 Markdown 文件（如 `user-chat-1.md`），记录真实聊天或用户吐槽。
   - **定量数据**：在 `docs/analytics.md` 记录转化数据，在 `leads.csv` 记录线索转化漏斗。
   - **云端数据**：通过本地 `gh` CLI 读取的 GitHub Issues 待办。
2. **解析与上下文打包 (Ingestion & Parsing)**：
   - 当用户为某一步骤启动 Agent 时，插件内部的输入解析器会自动扫描以上数据源：
     - 若为 **Build（代码类）** 任务：提取 `docs/feedback/` 中的 Bug 吐槽和未关闭的 Issue，打包为 `Bug & Pain Points Context`。
     - 若为 **Sell（市场类）** 任务：提取用户对于价格、体验的吐槽以及 `docs/sales-brief.md` 的产品定位，打包为 `Value Objection Context`。
     - 若为 **Improve（规划类）** 任务：整合所有负面反馈与未解决问题，生成路线图重组的 `Revision Input`。
3. **Prompt 管道注入 (Prompt Injection)**：
   - 解析出的上下文会被自动组装并以 `## 📢 来自 LEARN 循环的真实反馈` 标题注入发送给 Agent 的 `prompt.txt` 中。
   - Agent 必须在本次运行中针对这些反馈做出代码或文档的针对性修改，从根本上解决“AI 在本地盲目写代码，不接地气”的顽疾。

### 验收标准

- **侧边栏克制**：侧边栏不出现常驻四阶段大组件，仍以 Next Action 为首屏主入口。
- **大图视角**：主页面能稳定展示 Build -> Sell -> Learn -> Improve 四个维度的真实运转槽位，并支持定位关联环节。
- **空白状态友好**：即使是没有进行任何市场/反馈动作的新项目，该面板亦能展示明确的“推荐市场任务一键派发”提示，而不是尴尬的报错或空白。
- **数据流正常**：`prompt.txt` 中能稳定生成包含真实反馈文件的 `## 来自 LEARN 循环的真实反馈` 章节，且前置环节的完成手稿（Memory）被下一个推荐节点完美继承。

## 长期探索：自动驾驶与自动化任务派发 (Autopilot Mode)

在更长期的规划中，我们希望引入类似于 *Universal Paperclips* 的**自动化派发与流转回路（Autopilot）**，将 SoloMap 从“项目管理看板”升级为“全自动软件构建与分发引擎”。

### 设计愿景

实现任务的无人值守连续执行。当一个路线图环节被标记为完成，系统会根据依赖树和状态自动判断并派遣 Agent 去执行下一步，最大化释放独立开发者的交付动能。

### 状态机与推进机制

1. **自动触发点**：
   - 监听 `.agent_status.json` 的 Sentinel 变化。
   - 当检测到当前节点状态更新为 `Completed` 时，如果全局 `Autopilot` 开关处于激活状态，则进入自动推进程序。
2. **缓冲机制**：
   - Webview 界面和侧边栏显示一个 5 秒的倒计时卡片：“*当前环节已完成，5 秒后将自动驾驶推进下一步 [环节标题]...*”。
   - 用户可以随时点击“暂停自动驾驶”按钮阻断自动流转。
3. **自动派发**：
   - 倒计时结束，系统根据 `Next Action` 选择规则定位下一个可执行的 `Pending` 节点。
   - 自动读取前置环节的 `.solopreneur/step-memory/` 沉淀手稿，封装为新一轮的上下文，自动拉起新的终端，调用 `handleRunAgent` 派发执行。

### 故障拦截器 (Fail-Safe)

- 自动推进极度依赖正确性。如果任何一个 Agent 运行在某一步抛出 `Failed`（包括 CLI 退出码非 0、格式校验失败或未产生任何实质文件改变）：
  - **Autopilot 立即断开并暂停**。
  - 界面转为警示橘红/红色，高亮显示具体的失败环节日志和 `Failure Reason`。
  - 触发 VS Code 的通知系统提醒用户人工介入，直至手动重试成功或修复。

### 动效与 Wow 体验规划

- **流光连接线**：Autopilot 激活时，SVG 路线图节点之间的连接线会呈现霓虹光点沿依赖链条流动的动画效果。
- **跑马灯边框**：正在自动驾驶运行的节点卡片带有一圈淡蓝色的霓虹跑马灯呼吸边框。
- **任务舱仪表盘**：侧边栏会打上 `[AUTO-DRIVING]` 徽标，实时输出当前自动驾驶的速度、时长、已修改文件总数等数据。

## 长期探索：GitHub Issues 本地智能闭环流 (方案 B + C 融合)

为了打破本地开发与云端需求之间的壁垒，我们希望在未来探索 **GitHub Issues 待办导入（方案 B）**与 **Agent 闭环自动反馈（方案 C）**的深度整合，为独立开发者打造流畅的本地到云端的工作流闭环。

### 核心设计愿景

借助用户本地已有的安全凭证与 `gh`（GitHub CLI）工具，实现“零外部云端服务器、零复杂 OAuth 鉴权、完全本地优先”的 Issues 极速解决与状态同步。

### 整合工作流逻辑

1. **GitHub Issues 收件箱 (B)**：
   - 侧边栏新增 `GitHub 收件箱` 面板，静默运行本地 `gh issue list` 拉取当前仓库的 Open Issues 列表。
   - 用户可点击任意 Issue 卡片旁边的 **「指派给 Agent (Solve with Agent)」** 或 **「转化为新环节 (Convert to Step)」**。
2. **Issue 上下文打包注入**：
   - 插件自动获取该 Issue 相关的描述、讨论评论与标签，在启动 Agent 时将其封装为 Prompt 核心业务背景输入。
   - 引导 Agent 明确任务：*“你当前正在解决 GitHub Issue #XX。请阅读相关描述并修复本地代码，通过测试做窄验证。”*
3. **本地 Agent 闭环执行 (C)**：
   - Agent 在本地项目文件区开展编码修复，运行单元测试确认解决后退出。
4. **Git 提交与自动关联 (C)**：
   - Sentinel 监听到运行成功后，自动在生成的 Commit Message 模版中加上 `Fixes #XX` 或 `Closes #XX` 并自动关联 Agent 的交付总结。
5. **本地 gh CLI 静默闭环**：
   - 代码推送回 GitHub 后，GitHub 的 native 服务会自动关闭该 Issue。
   - **自动云端交互**：插件也可在后台调用本地 `gh` 执行：
     - `gh issue comment XX --body "SoloMap Agent 已在本地解决此问题。修改文件：[文件列表]。"` 自动去 GitHub 回复并提供透明的 Agent 运行报告。
     - `gh issue close XX` 在本地直接闭环云端状态。

- **无需额外密钥**：所有 API 请求均不经过任何插件中转服务，直接利用开发者本地已配置好的 `gh` CLI 工具链及其内嵌凭据完成。
- **透明度高**：用户可以清楚在终端中看到 `gh` 的调用 and 运行过程，无凭证泄露风险，完全自主控制。

## 长期探索：Telegram 移动端远端遥控与主动播报机制 (Telegram Integration)

为了真正将 SoloMap 打造为独立开发者的“口袋操作系统”，我们计划在未来探索 **Telegram 移动端远程控制与主动状态播报机制**。让独立开发者能够在移动场景（如外出、社交或通勤时）通过手机 Telegram 聊天框远程触发、观察、打断本地的 Agent 任务，并在大型长耗时任务完成时接收主动推送。

### 核心设计愿景

本着“本地优先、隐私第一”的原则，实现**零云端中转服务器、零公网 IP/域名配置、零端口暴露**的纯安全本地客户端通信。

### 🔌 零公网依赖：基于「长轮询 (Long Polling)」的通信架构

传统的 Webhook 通信要求开发者配置公网 HTTPS 回调地址（需要租用云服务器、购买域名及配置 SSL 证书），这大幅拉高了门槛且破坏了本地优先哲学。
- **架构方案**：SoloMap 将在 VS Code 插件激活时，于 Node.js 后台守护进程中启动一个极其轻量的 HTTPS **长轮询客户端 (Long Polling via getUpdates API)**。
- **技术优势**：插件主动向 Telegram 官方网关拉取新消息。本地电脑不论处于住宅内网、企业防火墙、NAT 路由器后还是开启了 VPN，只要能正常发出 HTTPS 请求，便能 100% 稳定接收消息，完全避免暴露任何本地端口与安全性。

### 🛡️ 绝对安全红线：Chat ID 硬件双向鉴权

由于 Telegram Bot 是公网公开实体，必须建立绝对安全的拦截机制，防止陌生人获取用户本地的命令行终端控制权：
1. **私密 Token 本地存储**：用户的 `TELEGRAM_BOT_TOKEN` 仅保存在本地的加密 `ExtensionContext.globalState` 中，绝不上云。
2. **Chat ID 单向白名单绑定**：
   - 首次启用时，用户在手机端向 Bot 发送 `/bind` 指令。
   - 本地插件检测到该未绑定 Chat ID 请求，在 VS Code 弹窗警示：*“检测到 Telegram 账号 [Username](Chat ID: XXXXX) 申请绑定控制权限，是否授权此设备控制您的本地电脑？”*
   - 用户点击确认后，该 Chat ID 被永久写入本地信任白名单。
   - **此后，插件将无情过滤并丢弃任何非白名单 Chat ID 发来的任何指令与消息，做无响应静默处理。**

### 💬 移动端交互指令与执行流程

1. **远程任务触发 (Remote Dispatch)**：
   - 用户在手机发送 `/solo 优化 landing/index.html 中的定价话术`。
   - 本地轮询器捕获指令，调取 `SyncEngine` 并在后台以 Node.js 进程拉起本地的 Agent CLI 终端。
2. **打字机流式回传 (Terminal Log Streaming)**：
   - 本地终端运行的日志实时被插件捕获，通过 TG 的 `editMessageText` API，在手机端以“流式打字机”或“定时刷新单条日志”的视觉体验向用户展现当前 Agent 的修改进度与测试状态。
3. **成果自动提交与云端推送**：
   - 任务成功完成后，Sentinel 文件触发。插件自动生成规范提交并推送至 GitHub，同时向手机发送最终交付报告：*“✅ 任务已自动执行成功！修改文件：src/index.css。已提交至 Git。”*

### 📢 主动状态播报 (Push Notifications)

对于耗时极长（如全面自动化测试、整站重构、编译打包等）的任务，开发者无需在电脑前枯等：
- 任务在本地后台安静运行，开发者可以直接出门。
- 一旦 Sentinel 检测到状态跃迁（`Completed` 或 `Failed`），插件会第一时间向绑定手机发送推送通知，播报最新项目看板进度与下一步的 `Next Action`。

## 非目标

下一阶段暂不优先做：

- 新 Agent CLI 大规模接入。
- 云同步。
- 账号系统。
- 团队协作。
- 复杂项目管理字段。
- 独立任务数据库。

原因：这些会增加系统复杂度，但不直接解决用户“下一步该做什么”的核心问题。

## 回归测试建议

新增测试应覆盖：

- 新项目 starter prompt 引用方法论模板。
- 商业化产品生成路线图时默认覆盖四个方法论阶段，内部项目可通过自定义阶段校验。
- Next Action 按状态优先级选择正确环节。
- 侧边栏渲染 Next Action 首屏入口。
- Next Action 发送任务复用现有 `runAgent` 链路。
- 项目切换后 Next Action 不泄漏上个项目状态。
- 文档或 README 改动不触发发布 workflow。

## 成功标准

下一阶段成功的标志不是功能入口更多，而是：

- 用户打开 SoloMap 后，首屏就知道下一步。
- 新项目路线图能按真实目标选择闭环；商业化产品天然覆盖产品、市场和改进路径。
- 每个 Agent 对话都绑定在路线图环节和完成标准上。
- Agent 交付后，用户能看到文件变化、状态变化和下一步变化。
- SoloMap 更像一人公司的操作系统，而不是 AI 聊天记录管理器。
