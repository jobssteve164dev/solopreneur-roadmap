# SoloMap Methodology

SoloMap is built around one operating idea: a solo builder does not need a perfect plan before moving. They need a living map that turns uncertainty into the next executable action, records what the Agent did, and keeps the project moving from idea to delivered outcome.

SoloMap 的方法论可以概括为一句话：

> 先发现真实问题，再打造可交付产品，然后获得客户反馈，最后用循环把增长放大。

## The Four Stages

### 1. Find The Real Problem

The first job is not to write a full business plan. It is to identify a valuable problem, find reachable customers, build enough momentum, and start from zero.

For SoloMap, this means the initial roadmap should force clarity on:

- what problem is worth exploring
- who can learn from or validate it
- what small action creates momentum
- what the first concrete task is

The output should be an action-ready roadmap, not a polished strategy document.

### 2. Build The Product System

A prototype is only the beginning. A useful product needs an engineering system around it: requirements, architecture, data, infrastructure, testing, design, deployment, and maintenance.

For SoloMap, each roadmap step should be executable by an Agent conversation and should leave behind:

- changed project files
- a visible run result
- a record of what the Agent attempted
- enough step memory for the next run to continue

The product is not considered real just because an Agent answered. It becomes real when the local project files change and the next user action is clear.

### 3. Sell To Customers

Building does not create customers by itself. The product needs a path for people to discover it, understand it, trust it, and become users.

For SoloMap, roadmap stages should include the customer-facing surface:

- brand
- website or distribution page
- marketing message
- sales or conversion path
- demand generation

The roadmap should not end at implementation. It should carry the project into market contact.

### 4. Scale Through A Loop

Scale is not a single phase after everything is finished. It is a loop:

Build -> Sell -> Learn -> Improve

SoloMap should make that loop visible and repeatable. After a step or revision, the project should be able to absorb feedback through:

- product analytics
- customer support signals
- unit economics
- expansion opportunities

The roadmap is therefore not static. It is a living control surface for repeated learning and improvement.

## SoloMap Operating Loop

The image's core logic is:

```text
Find problem -> Build product -> Get customers -> Keep scaling
```

SoloMap translates that into an Agent-native workflow:

```text
Idea -> Roadmap -> Step conversation -> Local file changes -> Run result -> Roadmap update
```

This loop defines the product:

1. The user starts with an idea or a changed goal.
2. SoloMap turns that into a roadmap with clear stages.
3. Each stage becomes a place to run focused Agent conversations.
4. Agents work inside the user's local project folder.
5. SoloMap records status, changed files, output, and retry options.
6. The roadmap changes as the project learns from execution and feedback.

## Product Principles

### Roadmap Before Chat

SoloMap should not be a generic chat surface. The roadmap gives every Agent conversation a business and delivery context.

### Action Before Perfection

The user should not need perfect requirements, a complete team, or a finished plan before starting. SoloMap should always preserve a small next action.

### Local Deliverable Before Agent Output

An Agent response is not enough. SoloMap should treat local project changes, visible run status, and user-controlled closure as the real proof of progress.

### Market Path Before Internal Completion

The roadmap should include how the product reaches customers, not only how the code is built.

### Loop Before Linear Plan

SoloMap should support revision, retry, learning, and improvement. A roadmap is valuable because it changes with the project.

## Default Roadmap Shape

A strong SoloMap roadmap should usually cover these layers:

```text
1. Problem and customer discovery
2. Product foundation and first usable version
3. Distribution, brand, website, marketing, and sales
4. Feedback, analytics, support, unit economics, and expansion
```

This is not a rigid template. It is the minimum mental model that keeps a solo project from becoming only code, only chat, or only planning.
