# 今日安排侧边栏设计指南

## 目标

`今日安排` 是侧边栏首屏的跨项目行动编排层。它只回答用户今天先做什么，不创建新的任务系统，也不替代项目卡片里的下一步。

## 信息层级

- `今日安排`：从所有项目中选出今天最该处理的 1-3 个动作。
- 项目卡片：展示单个项目的状态、下一步、Issue 和推进入口。
- 路线图环节：承载实际 Agent 对话、验证、完成判断和交接记录。

因此，`今日安排` 只能引用已有项目、Issue、发布检查、路线图环节和学习候选，不能生成一套独立的今日任务对象。

## 排序原则

优先级按“先保命，再推进，再复利”处理：

1. 发布检查失败、严重 bug、P0 Issue、失败环节。
2. 本周 P1 项目的 Running / In Progress / 可开始 Pending 环节。
3. 接近闭环的验证、发布、复盘、学习候选整理或路线图调整。

用户不需要看到评分模型。界面只显示行动槽、项目名、原因和下一步。

## 工作节奏

`今日安排` 内部应吸收全局工程执行指南里的日/周/月节奏，但不能把它做成用户要维护的流程页。

- 每天：优先做本地自查，先看失败、阻断、进行中和可开始动作。
- 周一：在没有更高优先级事故时，提高本周 P1、新项目起点和可开始环节的权重。
- 周五：在没有更高优先级事故时，提高收尾、复盘、学习候选和可复用经验的权重。
- 月末：在没有更高优先级事故时，提高优先级回顾、复用效果、阻断依赖和 Improve/调整动作的权重。

前台只允许显示用户能行动的理由，例如“周一先确认本周主线”“周五适合收尾沉淀”“月末适合回顾优先级和复用效果”。不要展示执行指南条目、评分公式或内部数据结构。

## 首屏形态

固定最多三条：

```text
今日安排

先处理  项目 A
发布检查需要处理 · 修复发布检查

主推进  项目 B
已经开始，今天最容易形成进展 · 完成 MVP 验证

收尾    项目 C
成果已完成，适合复盘或调整下一轮 · 整理学习候选
```

每条点击后只能回到已有项目卡片或现有推进入口。不要新增“今日任务详情页”“今日任务状态”“今日任务完成按钮”。

## Agent 使用边界

默认打开侧边栏时不自动调用 Agent CLI。首屏安排必须先由本地数据快速生成，保证插件打开快、安静、可控。

如果增加“Agent 审视”或“生成今日计划”，必须满足：

- 用户显式点击后才调用 Agent。
- 结果按当天缓存，重复打开不重新生成。
- Agent 输出只能转成对已有项目/环节的建议，不写入新的今日任务系统。
- 如果 Agent 不可用，本地今日安排仍然可用。
- 审视结果保存为当天 JSON artifact，例如 `.solomap-global/daily/YYYY-MM-DD.json`；它只是审视缓存，不是路线图、项目组合或任务完成状态的事实源。
- 提示词必须把全局工程执行指南第一部分内化成情景化审视逻辑，并要求 Agent 只写结构化 Todo JSON。
- 同一个 `Agent 审视` 按钮根据节奏和状态切换模式：日常快速自查、周一重点校准、周五收尾与学习审视、月末优先级与复用回顾、异常优先审视。
- 异常信号优先于周期节奏；只要有发布检查失败、失败环节、P0 反馈或跨项目阻断，按钮背后的审视先处理异常。
- 学习、审计、归档相关建议只能在真正需要用户判断时进入 `needsConfirmation`，不能把后台经验库维护工作变成用户任务。
- 打开侧边栏时只读取当天 JSON，不同步调用 Agent，不扫描历史审视文件。

## 禁止项

- 不要同时保留一个同等重量的“本周推进”调度卡。
- 不要把 `portfolio.csv`、`dependencies.csv`、学习候选目录等内部对象暴露成用户要操作的前台概念。
- 不要让用户在 `今日安排`、`本周推进`、项目卡片 `下一步` 三个入口之间判断哪个才是真的。
- 不要用解释文案替代行动按钮；卡片必须让用户一眼知道今天先处理什么。
