# SoloMap 自主运行时与递归改进蓝图

## 这份文档解决什么判断

这份文档固定 SoloMap 如何从依赖用户主动点击的项目驾驶舱，演进为能够持续观察项目、主动选择工作、调用 Agent 执行、独立验证结果并改进自身策略的本地自主运行时。

核心判断只有一句：**SoloMap 必须成为拥有目标、项目事实、执行权和学习闭环的常驻本地主体；内置 Pi Agent 负责统一认知循环，现有 Agent CLI 负责复用用户已登录的模型额度能力。**

设计状态：阶段 0 的常驻 Runtime 基础和阶段 1 的只读影子决策已经落地；当前同时具备内置 Pi Agent、本地 Agent CLI 模型额度管道，以及阶段 2 的项目授权、操作系统沙箱准入和持久执行恢复基础。本文是后续架构与分阶段验证的基线，不代表当前产品已经具备完整自主交付能力，也不修改现有路线图状态或完成标准。

## 最终用户结果

用户不再需要不断打开项目、判断下一步、选择 Agent、复制上下文、盯住运行并手工整理结果。用户只需要：

- 告诉 SoloMap 自己想实现什么，以及哪些结果可以自动交付。
- 在需要改变目标、承担新成本或执行高影响动作时做决定。
- 查看 SoloMap 当前为什么选择这项工作、已经取得什么结果、下一步会发生什么。
- 随时暂停、纠正或收回某个项目的自主权。

SoloMap 在已获授权的范围内持续完成：

```text
观察项目与外部信号
-> 判断最值得推进的目标
-> 选择任务、认知引擎和执行器
-> 形成带完成标准的任务
-> 执行并收集真实证据
-> 独立验证或继续修正
-> 提交项目状态
-> 从结果中改进下一轮策略
```

用户面对的产品主语始终是“项目正在向目标推进”，不是 Agent 组织、模型路由、任务状态机或内部治理对象。

## 从自动化到递归改进

本文区分三个层次：

| 层次 | 系统能力 | 不足 |
| --- | --- | --- |
| 自动化 | 用户选好任务后自动执行 | 仍依赖用户持续发现和派发工作 |
| 自主化 | 系统观察多个项目并主动选择、执行和收口 | 若策略不随结果变化，只是更复杂的自动化 |
| 递归改进 | 系统用执行结果改进自己的上下文、路由、技能、工具和决策策略，并证明新版本更有效 | 必须防止自报成功、指标污染和未经验证的自我修改 |

SoloMap 的递归改进不以“修改自身代码”为起点。第一阶段先让学习稳定改变后续行为；只有经过独立评估的能力改进，才能晋升为正式策略。

## 现有基线

当前仓库已经具备自主运行所需的部分零件：

- 项目登记、跨项目摘要与确定性的下一步推荐。
- 路线图、Solo、Flow 与现有 Agent CLI 执行路径。
- 会话身份、任务检查点、运行记录、完成判断和续接。
- 主 Agent 与只读复核 Agent 的协作边界。
- 项目生长信号、执行经验、学习账本和手动经验复盘。
- 官网账户与工作台外壳、私密协作中继和本地优先工作台设计。

当前仍缺少的不是另一个任务入口，而是一个在 VS Code 窗口之外持续存在的主体。它必须拥有跨项目观察、目标判断、任务选择、执行协调、结果验证和策略晋升的完整责任。

路线图中原有 Autopilot 设想只描述“节点完成后自动运行下一个节点”。该机制可以成为执行协调器的一种触发来源，但不能继续充当自主运行的总体架构。

## 不变量

以下约束优先于任何引擎、SDK 或实现便利：

1. 项目代码、路线图、记忆、执行证据和完整上下文继续以本地为权威。
2. 用户没有登记的目录和项目不进入观察、推理或执行范围。
3. 用户目标和明确授权高于 Runtime 的自主判断；Runtime 不能自行扩大责任范围。
4. Agent 的文本声明不是状态事实，只有可回读的文件、命令、测试、运行时和外部结果可以提交项目终态。
5. 认知引擎不拥有项目状态写入权、凭据所有权或权限策略修改权。
6. 现有 Agent CLI 选择、会话、模型和历史执行路径不得因引入首个深度引擎而被删除或降级。
7. 官网工作台继续是端到端加密的意图与结果界面，不成为项目副本或第二个执行权威。
8. 学习失败不能阻断已经取得的用户结果；改进机制必须服务交付，而不是让任务更早失败。
9. 系统必须能够选择“不行动”。没有足够价值、证据、权限或资源时，不得用制造任务维持活跃。
10. 自主运行不能把内部 Agent 角色、协议、权限路由和冲突处理转嫁给用户理解。

  本地交互                     │                                  结果提醒

       │                       │                        │

                       ├── GitHub Agentic Workflows

### Runtime 必须独立于 VS Code 窗口

Runtime 是每个操作系统用户、SoloMap 数据根和设备身份下的单一常驻本地服务，不属于某个 Webview、某个工作区窗口或某次 Agent 会话。单实例锁与 IPC 都限定在这三个身份的组合范围内。

它负责：

- 维护已登记项目及当前执行设备关系。
- 接收文件、运行、Git、CI、反馈和定时信号。
- 维护任务队列、租约、检查点和恢复状态。
- 选择下一项工作并调用认知引擎。
- 向执行器授予本次任务需要的最小能力。
- 收集并验证结果，提交项目状态。
- 生成学习材料、运行评估并晋升已证明有效的策略。
- 向插件和官网提供同一份最小状态投影。

VS Code 插件继续承担本地界面、项目加入、用户授权、详细证据查看和兼容执行入口，但不再是常驻循环唯一宿主。插件关闭不应破坏已经落盘的任务身份、检查点和恢复能力。

### Runtime 宿主生命周期

Runtime 不能由 Extension Host 临时拉起后依附其存活。阶段 0 必须选定与操作系统匹配的用户级服务宿主，覆盖安装、登录启动、健康探测、崩溃重启、受控升级和卸载；插件只通过已认证的本地 IPC 发现和连接该实例。

- 首次启用时由插件安装或注册用户级 Runtime，并显示对用户有意义的启用结果。
- 所有 VS Code 窗口关闭后，Runtime 继续接收已授权事件并推进现有任务。
- Runtime 崩溃后由宿主重启，从落盘检查点恢复；不能靠打开插件触发恢复。
- 升级先停止接收新任务，等待当前写任务到可恢复检查点，再进行版本和状态迁移。
- 卸载先撤销启动项、设备身份和持续授权；项目文件、提交和已验证结果不随 Runtime 删除。
- 插件重连只恢复界面投影，不创建第二个调度器或重放外部副作用。

## 权威对象与数据归属

| 对象 | 权威位置 | 其他层可以做什么 |
| --- | --- | --- |
| 项目代码和文件 | 项目工作区 | Runtime 和执行器按任务能力读取或修改 |
| 路线图与项目记忆 | 项目 `.solopreneur/` | Runtime 通过既有契约提交精确更新 |
| 跨项目记忆和学习 | `.solomap-global/` | 学习层按现有分类与证据门禁更新 |
| 项目目标与授权 | 本地 Runtime 持久状态，必要时项目内保留可移植声明 | 插件和官网提交用户意图，不能静默覆盖 |
| 任务、租约和检查点 | Runtime 事件账本 | 界面只显示投影，Agent 只能通过受控命令推进 |
| Agent 原生会话 | 对应 Agent 自己的会话存储 | Runtime 保存稳定绑定并验证其有效性 |
| 验证证据 | 项目运行记录与 Runtime 证据索引 | Agent 可引用，不能伪造或改写既有证据 |
| 官网投影 | 浏览器临时解密状态 | 不反向成为项目真相 |

Runtime 不复制整个项目数据库，也不建立脱离项目文件的第二份路线图。它维护的是执行所需的身份、事件、租约、策略版本和最小派生索引。

## 目标系统

自主系统必须先知道“为什么做”，再决定“做什么”。每个已启用自主推进的项目至少需要以下稳定输入：

```text
projectGoal       用户希望项目达到的结果
successSignals    可以证明目标正在达成的外部或项目内信号
constraints       时间、成本、技术、品牌、隐私和禁止项
autonomyGrant     允许 Runtime 自动交付到什么程度
pauseConditions   哪些状态下必须停止并等待用户
```

目标来源按权威顺序组合：

1. 用户当前明确指令。
2. 用户确认的项目目标、产品方向和持续授权。
3. 当前路线图及完成标准。
4. 已验证的外部反馈、交付和增长信号。
5. 系统根据现有事实形成的候选机会。

候选机会不能自行覆盖上层目标。不同目标冲突且会改变项目方向时，Runtime 必须把冲突压缩成一个用户需要做的结果选择，而不是继续执行自己偏好的方向。

## 项目世界模型

世界模型不是让大模型自由总结整个项目，而是由可验证事实和带来源的派生判断组成。

### 可验证事实

- 路线图节点、依赖、完成标准和当前状态。
- Git revision、工作区变化、分支和提交。
- Agent 运行、任务检查点、验证命令和退出结果。
- CI、部署、Issue、Release、安全和外部反馈状态。
- 用户授权、预算、设备在线状态和当前租约。

### 派生判断

- 当前阻塞。
- 值得推进的候选任务。
- 预期价值、置信度、成本和影响范围。
- 某项证据是否过期。
- 某项策略是否比现行版本更有效。

派生判断必须携带输入版本和证据引用。源事实变化后，旧判断失去提交权并重新计算，不能把一次 Agent 总结永久当成项目事实。

## 组合决策与任务选择

Runtime 每次只从已登记且允许自主推进的项目中选择工作。首版采用全局单写任务：任一时刻只能有一个会修改项目状态或文件的自主任务。

候选任务至少按以下维度比较：

- 对项目目标的预期贡献。
- 是否解除其他任务的阻塞。
- 证据完整度和成功置信度。
- 预计时间、模型成本和外部成本。
- 当前授权是否完整。
- 失败是否可恢复。
- 是否存在更便宜的确定性动作。
- 是否应该不行动并等待新事实。

现有 `getRecommendedNode` 作为确定性基线保留。智能决策器必须在真实任务中证明其选择比该基线更有价值；若无法证明，继续由确定性规则选任务，让认知引擎只负责需要推理的执行与重规划。

Runtime 不以任务数量、Token 消耗、文件改动数或保持忙碌作为优化目标。

## 用户授权与动作能力

用户不应为每个工具调用重复确认。授权应绑定项目、动作类别、结果边界、有效期和可撤销状态。

目标授权模型提供三个用户可理解的项目级选择。当前建议的首版只开放前两级；第三层在阶段 3 且经产品确认后开放：

| 用户选择 | Runtime 可以完成什么 | 不包含什么 |
| --- | --- | --- |
| 仅给建议 | 观察、排序、规划并解释下一步 | 不修改项目 |
| 自动完成本地结果（含提交） | 修改隔离工作区、按项目联网策略运行工具与验证、形成可恢复的本地提交 | 不推送、不创建 PR、不部署、不发布 |
| 自动交付 PR | 在前一层基础上推送授权分支并创建或更新 PR | 不合并、不部署、不发布、不发送外部业务消息 |

部署、上架、支付、删除、凭据、权限变更、生产数据写入和外部消息属于后续独立能力。它们可以在经过验证后获得精确的持续授权，但不得被“自动交付 PR”隐含包含。

项目设置另提供“禁止任务工具联网”。默认不禁止，因为依赖安装、资料检索和联网验证是本地交付的正常组成部分；开启后只切断任务中的命令、测试、安装器等工具进程网络，不切断智能内核调用用户本地 Agent CLI 的模型管道。允许工具联网不会让 Runtime 主动规划推送、部署或发布，这些产品动作仍需独立授权。联网策略与项目授权一起原子保存，任何变化都推进授权 epoch，使旧策略下已准备或正在运行的任务立即失效。

当前“允许工具联网”提供通用网络可达性，网络层无法判断一次 TLS 连接是在下载还是写入；因此 Runtime 不向工具沙箱注入主机 HOME、环境 Secret、SSH Agent、GitHub CLI 或部署凭据，后续隔离仓库构建还必须拒绝带内嵌凭据的 remote。独立动作授权负责禁止 Runtime 主动规划推送、部署和发布，但不能把通用联网模式描述成只读网络。需要硬性保证零外部写入的项目应开启“禁止任务工具联网”。

权限代理必须在执行前把用户授权转化为本次任务的能力集合。认知引擎只看到已授予的工具；执行器即使支持更大权限，也不能越过代理直接使用。

暂停、项目授权撤销和设备撤销会原子递增授权 epoch。权限代理立即拒绝旧 epoch 的新调用，撤销文件、网络和凭据能力，并请求宿主停止对应进程；不能等到最终提交时才复核。已经产生的隔离内容只能作为不可晋升候选保留，除非用户重新授权后按新 epoch、当前 base 和当前完成标准重新验证。无法被宿主强制收权和停止的后端不得进入自主模式。

## 任务生命周期

内部任务使用稳定身份和可恢复状态：

```text
observed
-> candidate
-> selected
-> leased
-> planning
-> running
-> verifying
-> correcting
-> succeeded / failed / blocked_user / blocked_external / cancelled
```

约束如下：

- `candidate` 只是值得考虑，不构成执行授权。
- `selected` 必须记录选择理由、目标贡献和相对其他候选的依据。
- `leased` 绑定项目实例、执行设备、工作区 revision 和策略版本。
- `running` 只能由真实执行事件建立，不能因命令已排队提前显示。
- `verifying` 使用执行完成后的精确工作区与证据快照。
- `correcting` 只处理已识别的失败项和新增差异，不无限重跑整个任务。
- `succeeded` 必须满足完成标准与结果提交条件。
- 所有终态写入后必须刷新对应项目和跨项目投影。

每个外部副作用携带稳定 operation ID。重启、重连、Watcher 重复观察和迟到事件不能重复创建任务、提交、PR、部署或消息。

## 认知引擎边界

认知引擎负责推理，不负责持久化业务真相。统一接口至少包含：

```ts
interface CognitiveEngine {
  probe(): Promise<EngineCapabilities>;
  createSession(input: SessionInput): Promise<EngineSession>;
  resumeSession(sessionId: string): Promise<EngineSession>;
  plan(input: DecisionPackage): Promise<ActionProposal>;
  steer(sessionId: string, guidance: string): Promise<void>;
  cancel(sessionId: string): Promise<void>;
  subscribe(sessionId: string, listener: EngineEventListener): Unsubscribe;
}
```

这是边界示意，不是完整 SDK 定义。`createSession` 只创建会话，不代表任务已经开始；首个和后续推理回合由 `plan` 或后续正式契约中的显式运行方法触发。正式契约还必须覆盖权限请求、等待终态、证据事件、取消确认、断线恢复和幂等键，不能把供应商的一次响应误当成任务完成。

执行后端至少遵守以下稳定边界：

```ts
interface ExecutionBackend {
  probe(): Promise<BackendCapabilities>;
  prepare(input: ExecutionPackage): Promise<PreparedExecution>;
  start(preparedId: string, operationId: string): Promise<ExecutionHandle>;
  resume(executionId: string): Promise<ExecutionHandle>;
  cancel(executionId: string): Promise<CancelResult>;
  subscribe(executionId: string, listener: ExecutionEventListener): Unsubscribe;
  collectEvidence(executionId: string): Promise<EvidenceBundle>;
}
```

`prepare` 必须在任何副作用前完成能力、隔离空间、base revision 和预算检查；`start` 使用稳定 operation ID，重复调用不得重复产生副作用；事件只报告事实，不直接提交路线图终态；`cancel` 必须返回已经发生且无法撤回的副作用；`resume` 必须绑定原执行身份和隔离空间。

公开契约只使用 SoloMap 的任务、事件、工具和确认语义，不泄露供应商专属对象。模型、Agent 角色、原生 session ID 和供应商事件保存在适配器元数据中。

### 用户本地 Agent CLI 作为模型管道

内置 Pi Agent 复用用户已经安装、登录并选择的本地 Agent CLI，而不是要求用户再次配置模型 API Key。Runtime 通过模型额度适配层把 Pi 的模型请求发送给 CLI，并把供应商输出收敛为相同的 `ActionProposal`。

- 设置页只提供“模型额度来源”：跟随主 Agent，或指定一个兼容 Agent CLI；Pi Agent 作为内部固定内核，不形成第二套用户选择。
- “跟随主 Agent”复用该 Agent 已有的模型偏好；不会再暴露第二套模型供应商心智。
- Runtime 使用直接子进程和标准输入输出调用 CLI，不经过 Shell，不创建或显示 VS Code Terminal。
- 认知调用工作目录与项目工作区隔离，不发送本地路径，不继承无关环境变量，不授予写文件或自动批准权限；支持空工具集的 CLI 必须关闭全部工具，其他 CLI 只有在其当前版本提供可验证的只读计划模式与沙箱时才能接入。只读计划模式仍可能具备受限读取工具，因此不能被描述为“纯模型 API”，也不能获得项目工作区路径。
- CLI 必须具备可验证的 headless、安全模式和结构化输出适配器；不满足时自动回到确定性本地规则，不偷偷切换到其他供应商。
- 配置写入 Runtime 的最小本地配置投影，常驻循环每轮重新读取，因此切换 Agent 不依赖重启插件或新建终端。

认知适配器与执行适配器必须分离。现有带有 `allow-all`、绕过审批或写工作区权限的任务命令不能用于智能内核推理；即使二者调用同一个 CLI，也必须使用不同的参数构造、能力声明、工作目录和审计事件。候选内容统一走标准输入，不能放进进程参数；当前版本无法满足这些条件的 CLI 不出现在可选兼容列表中，只能回落本地规则。

### 内置认知内核

认知循环固定采用内置 Pi Agent。Pi 不直接持有供应商 API Key，也不继承任务执行权限；模型调用统一经用户选择的 Agent CLI 登录额度管道完成，工具与写入能力继续经过 SoloMap 权限代理和操作系统隔离。

内核选择不改变 SoloMap 的状态、授权、验证或学习契约。模型额度管道不可用时，Runtime 保留确定性推荐并记录故障，不能静默降低权限和完成标准。

## 执行后端

认知引擎可以直接完成受控工具任务，也可以把交付任务派发给执行后端。

### 本地 Agent CLI

现有 Codex、Claude、Cursor、Copilot、OpenCode、Grok 和 Antigravity 等路径继续作为正式执行器，但区分两个宿主：

- 用户主动交互继续使用插件原生终端后端及其终端就绪门闩。
- 无人值守执行由 Runtime 直接托管可无界面运行、可恢复且受操作系统沙箱约束的 headless 后端。

两者共享命令构造、原生会话身份、任务身份、检查点、完成判断、证据和续接协议，但不共享 VS Code Terminal 或 Extension Host 生命周期。某个 CLI 若不能可靠 headless 运行或不能满足自主写入能力边界，只保留为用户主动交互执行器。

智能内核发起的执行任务一律走 Runtime 的 headless `ExecutionBackend`，不得显式新建终端窗口。终端仅保留给用户主动发起、需要观察或交互确认的会话；后台任务进度、暂停、失败恢复和证据通过现有产品界面呈现，而不是把终端当作运行状态界面。

第一段执行后端基础提供独立于 VS Code Terminal 的 headless 进程生命周期契约：`prepare` 校验隔离目录、base revision 与预算，`start` 复核工作区身份与 revision 并以 operation ID 去重，同时支持查询运行句柄、取消和证据收集。它继续作为用户主动或不需要自主写入的进程基础；自主写任务必须使用下面的持久沙箱后端，不能把普通进程后端的能力声明提升为沙箱能力。

阶段 2 的第二段基础现已落地：项目设置可以按项目保存“自动完成本地结果（含提交）”授权和“禁止任务工具联网”策略，授权按项目独立原子保存，只有真实授权或联网策略变化时才推进 epoch，重复保存项目资料不会打断正在运行的任务；删除项目会先撤销授权。持久执行后端把按项目隔离的 operation ID、执行语义指纹、准备记录、执行状态、所用工具联网策略、输出、worker 身份与启动握手落盘；Runtime 启动时会初始化该后端、恢复同一执行并记录沙箱就绪状态，worker 已丢失或启动握手中断时会终止遗留 worker 并写入明确失败终态。执行 worker 持续复核授权 epoch，授权或联网策略变化后停止旧进程并取消结果晋升资格。Linux 自主写后端只在 Bubblewrap 真实探针通过后准入，隔离进程只获得只读系统目录、独立可写工作区、空 HOME 与临时目录；任务工具默认保留网络，用户开启禁止后增加独立网络命名空间。两种模式都不继承 HOME、SSH、GitHub CLI 或部署凭据，模型管道则继续在执行沙箱之外通过本地 Agent CLI 联网。探针失败时不会降级为普通进程。当前开发宿主的内核禁止非特权用户命名空间，因此这里只能验证拒绝准入，不能把该宿主记为自主写可用设备。

这一段仍不等于阶段 2 整体完成：自动选任务、隔离仓库构建、独立复核与修正、本地提交及稳定任务 ref 的采用/放弃闭环仍需沿后续增量接入持久后端。

### 确定性工具

不需要模型推理的动作使用确定性实现，例如读取状态、计算依赖、运行已知测试、刷新 Git/CI 状态和验证最终配置。认知引擎不得为了维持控制感接管所有简单动作。

### GitHub Agentic Workflows

适合定时或事件触发的仓库巡检、Issue 分类、CI 调查、文档维护和跨仓库报告。它是云端执行后端，不是本地世界模型或 RSI 主脑。

### Copilot Cloud Agent

适合把边界清楚的 GitHub 仓库任务交给远端产生分支或 PR。Runtime 必须记录上传的最小任务包、远端任务身份、目标 revision 和最终工件，不把云端任务完成直接等同于本地项目完成。

首版用户电脑离线时保持等待，不自动迁移任务到云端。离线转云需要单独验证数据范围、Git 状态一致性、成本、身份和结果合并后再开放。

## 独立验证与完成提交

每个任务在执行前形成验收契约：

```text
用户或项目目标
适用完成标准
必须保持的不变量
允许的影响范围
验证命令或真实结果
停止与恢复条件
```

验证器必须直接读取执行后的证据，不能只读执行 Agent 的总结。根据任务类型检查：

- 精确 diff 与触碰文件。
- 语法、测试、构建和最终生成物。
- 真实 UI、运行入口或外部系统回读。
- 路线图状态、完成标准与结果是否一致。
- 用户向内容是否残留工程自描述、模板说明或实现负担。
- 是否产生未归类的临时运行、分支、资产或外部对象。

同一个认知引擎可以提供复核推理，但必须使用独立会话、原始目标和证据快照。执行会话不能修改复核标准或直接提交自己的通过结论。

## 学习与递归改进

Runtime 使用两个嵌套循环：

```text
项目循环：
观察 -> 选择 -> 执行 -> 验证 -> 提交项目结果

改进循环：
分析多轮结果 -> 提出能力变更 -> 历史回放 -> 保留任务评估
-> 小范围真实运行 -> 晋升或回退 -> 观察长期效果
```

### 第一层：执行学习

允许根据验证结果自动调整：

- 上下文检索与压缩策略。
- Agent、模型和验证器选择。
- 任务拆分与续推方式。
- 失败分类、重试和升级条件。
- 成本、延迟和质量权衡。

### 第二层：策略与能力学习

允许生成候选：

- Prompt。
- Skill。
- 工具定义。
- 任务选择策略。
- 验收模板。
- 项目类型识别和信号解释规则。

候选不能因生成成功自动应用。晋升必须证明：

1. 在相关历史任务回放中优于当前版本。
2. 在未参与生成的保留任务中没有关键回归。
3. 没有改变用户目标、授权或验收标准。
4. 小范围真实运行产生更好的结果。
5. 可按稳定策略版本回退。

### 第三层：自身代码改进

Runtime 可以把 SoloMap 自身缺陷转化为代码任务，但首版只允许：

- 在隔离分支执行。
- 运行完整项目检查和专门行为评估。
- 生成供稳定版本读取的 PR 与证据包。
- 由当前稳定 Runtime 或用户决定是否合并。

候选版本不得自行部署、覆盖稳定 Runtime、修改自己的评估标准或清除失败证据。

### 暂不开放：自主升级稳定 Runtime

自动替换自身版本需要先解决双版本运行、数据迁移、健康探针、回退、供应链和评估器独立性。它不属于首版，也不能用普通插件自动更新机制伪装实现。

## 改进评估

RSI 是否成立只能由行为和外部结果证明。核心指标包括：

- 无需用户中途介入的闭环完成率。
- 验证后返工或重新打开的比例。
- 从发现机会到产生有效结果的时间。
- 每个有效结果的模型与外部成本。
- 用户推翻任务选择或收回授权的频率。
- 新策略相对当前策略的成功率和回归差异。
- 项目发布、用户反馈、收入、留存或其他目标信号是否改善。

任务数、运行时长、Token 使用、文件改动数、记忆数量和 Agent 自报完成次数都不是能力提升证据。

每项策略评估必须记录：基线版本、候选版本、任务集合、输入快照、结果、失败、成本和最终判断。候选不能读取保留任务的预期答案或修改评估器。

## 安全与信任边界

### 能力代理

所有文件、Shell、Git、网络、凭据和外部系统动作都经过 Runtime 能力代理。能力绑定：

```text
用户 / 设备
项目稳定 ID
任务 ID
动作类别
资源范围
有效期
剩余预算
```

Agent 自报路径、仓库名称、提示词指令和模型工具参数不能扩大能力。

每个执行后端必须在注册时声明哪些能力能由宿主强制执行，而不是只靠提示词约束：

| 能力 | 准入证据 |
| --- | --- |
| 文件 | 可限制到本次隔离工作区，并能拒绝访问其他项目和用户文件 |
| Shell / 进程 | 可限制可执行入口、工作目录、子进程和资源范围 |
| 网络 | 可按任务关闭或限制目标，拒绝后不产生外部副作用 |
| 凭据 | 只注入本次动作需要的短期凭据，执行器不能枚举宿主 Secret |
| Git / 外部系统 | 使用稳定 operation ID、目标资源和最小写权限 |

不能证明这些边界的普通 CLI 仍可用于用户主动操作，但不得进入自主写模式。需要使用它时，Runtime 必须先把进程置于满足声明能力的操作系统沙箱；“Agent 承诺不越界”不构成准入证据。

### 不可信上下文

项目文件、Issue、网页、日志、依赖文档、Agent 输出和历史记忆都可能包含诱导指令。它们只能作为数据进入任务上下文，不能修改 Runtime 目标、权限、评估器和系统指令。

### 凭据

凭据由宿主安全存储管理，按动作临时注入受控进程。认知引擎不应读取原始 Secret；日志、Prompt、任务报告、网页投影和命令参数不得包含明文凭据。

### 沙箱

提示词中的“不要越界”不是安全控制。需要限制文件、进程、网络或凭据时，必须使用工具 allowlist、路径能力、子进程边界或操作系统级沙箱，并在真实副作用边界验证拒绝后没有产生写入。

阶段 2 安全验收采用以下可追踪合同：

| ID | 威胁 | 强制要求 | 验收证据 |
| --- | --- | --- | --- |
| `T-SBX-01` | 执行器越界读取或写入用户文件、访问网络或枚举宿主凭据 | 自主写仅在操作系统沙箱探针通过后启动；宿主 HOME 不挂载，网络隔离，只有任务工作区可写 | 在真实支持宿主上分别尝试越界文件写入、网络访问与 HOME 读取，全部由内核拒绝且目标无副作用 |
| `T-AUTH-01` | 旧授权被重放，撤销后进程继续写入或结果仍可晋升 | 授权绑定规范化项目身份与单调 epoch；准备、启动、运行中和晋升前均复核 | 撤销运行中授权后进程停止，旧 epoch 不能再次启动，既有候选 `promotionEligible=false` |
| `T-REC-01` | Runtime 崩溃或重复事件造成任务重复启动、重复提交或悬空运行 | operation ID 原子去重；任务状态和输出独立于 Runtime 落盘；重启只恢复同一 worker 或明确终止 | 第二个 Runtime 对相同 operation ID 得到同一 execution ID；失联 worker 被写为 `worker_interrupted` |

## 并发、租约与多设备

首版约束：

- 每台机器只运行一个有效 Runtime 实例。
- 全局同时只允许一个自主写任务。
- 只读观察和状态刷新可以并行，但不得获得项目写租约。
- 每个项目同时只有一个执行设备拥有写租约；项目稳定 ID 与允许执行的设备集合来自用户明确授权。
- 用户主动在项目中开始交互任务时，自主调度不能抢占该项目；其他项目仍可继续观察。
- 工作区 revision、目标版本或授权变化后，旧租约和旧计划失去提交权。

后续只有在不同任务拥有不重叠工作区、独立分支和可证明的合并责任时，才允许跨项目或同项目并发。多个 Agent 同时修改同一工作区不属于首版。

多设备写租约不能只靠每台机器的本地单实例。需要一个只保存不可读协调元数据的租约仲裁面。客户端根据项目稳定 ID 和用户密钥，以域分离 HMAC 派生不可反查的 lease scope；不同项目、不同用户和不同用途不能复用同一标识。租约只包含 lease scope、设备临时公钥、单调 fencing token、不透明 operation handle、到期时间和设备签名，不上传内部项目 ID、任务 ID 或名称。

同一用户的已授权设备通过端到端加密设备配置共享派生材料；撤销设备或轮换用户密钥时生成新 scope，旧 scope 只保留拒绝迟到 token 所需的最短期限，且不能与新 scope 建立服务端可见关联。仲裁面以线性化 CAS 原子授予或续租，由服务端权威时钟判断有效期；中继可以比较 token 和有效期，但不能读取项目内容或建立项目目录。

- 新设备取得更高 fencing token 后，旧设备即使离线恢复也不能提交结果。
- 网络分区时，无法续租的设备可以运行只读检查，但必须在任何新写入前停止；不能用本地时钟自行延长租约。
- 项目状态提交、正式结果 ref 更新、推送和 PR 等每个权威变更入口都必须原子拒绝旧 token；只由客户端重新校验不构成 fencing。
- 长运行执行器失去租约后立即撤销写能力并请求停止；已经在隔离空间产生的计算只能保留为候选，不得晋升或产生外部副作用。
- 每次写入、提交、推送和结果提交前都重新校验租约、base revision 和授权版本。
- 用户撤销设备后立即拒绝其续租；迟到事件只能作为审计事实，不得改变项目状态。
- 若首版不实现可信仲裁，则同一项目只能绑定一台执行设备，并且不能宣称支持多设备自主写入。

### 自主写入隔离

自主任务不得直接在用户正在使用的工作区中写入。阶段 2 前必须提供由 Runtime 创建、受操作系统沙箱约束的独立目录，并记录 base revision、任务拥有的路径与 patch。专用分支本身不构成隔离；普通 worktree 共享 Git common directory，也不能直接把该目录的写权限交给执行器。

- 启动前保存用户工作区、暂存区和未跟踪文件清单，但不复制、暂存或修改这些内容。
- 执行器只能写任务隔离空间，且不能直接写共享 Git refs、config、hooks 或对象库；用户在原工作区的后续编辑不进入任务提交。
- 暂存与提交只允许包含任务拥有的差异，检测到范围外变化立即停止提交并进入复核。
- Runtime 在验证 patch 后通过受控 Git broker 创建提交和任务 ref；需要让执行器自行操作 Git 时，必须使用真正隔离的 clone 或对象存储，再由 broker 校验导入。
- 应用或交付结果前重新校验 base revision；过期结果必须重放、重新验证或生成明确冲突，不能覆盖用户变化。
- 取消、失败和重启后，隔离空间必须明确归类为保留待查或安全清理；不得污染项目主工作区。
- 验收必须覆盖任务运行期间用户继续编辑、暂存和提交的场景，并证明用户改动不被覆盖、夹带或回滚。

### 结果晋升

阶段 2 的本地结果不会自动写入用户当前分支、索引或工作树。验证通过后，Runtime 把提交保存到稳定任务 ref，绑定 task ID、base revision、patch ownership、验证证据和当前 fencing token，并在插件中显示为可采用、可比较、可回退的结果。

结果状态分为 `ready_for_adoption`、`adopted` 和 `abandoned`。执行与验证完成只产生 `ready_for_adoption`；进入项目正式 ref 后才是 `adopted`；用户放弃或候选过期后是 `abandoned`。

- 目标分支仍精确匹配 base revision 时，用户可以通过 CAS 式操作把任务 ref 快进为正式结果；不满足时生成明确冲突或由 Runtime 在新 base 上重放并重新验证。
- 首版 Runtime 不在用户无感知时自动 cherry-pick、merge 或切换当前分支。
- 默认只有 `adopted` 结果才能提交路线图节点和项目终态。仅当任务验收契约在执行前明确规定“稳定任务 ref 本身就是最终交付物”时，`ready_for_adoption` 才可作为完成；“已产生候选 patch”不等于完成。
- 用户采用或放弃结果后，隔离 worktree、任务 ref 和证据必须归类为正式保留、待查保留或可安全清理；清理不得删除用户分支或未归属内容。
- 阶段 2 必须验证结果在插件中可发现、能安全采用、采用失败可恢复、放弃后可回退，并且临时隔离对象有明确去向。

## 触发与运行节奏

Runtime 以事件驱动为主：

- 项目文件或路线图变化。
- Agent 运行终态。
- Git、CI、部署或 Issue 状态变化。
- 用户目标、授权或反馈变化。
- 官网加密意图到达。
- 新的外部项目信号被正式读取。

低频巡检只负责发现遗漏事件、过期租约和长期停滞，不持续让大模型扫描所有项目。多个快速事件合并为同一事实刷新，重复观察不得重复派发任务。

Runtime 在以下情况下选择不行动：

- 没有比阈值更高价值的候选。
- 当前事实不足以选择方向。
- 所需权限、预算或执行设备不可用。
- 用户正在进行会与自主任务冲突的操作。
- 现有失败尚未恢复，继续执行只会扩大影响。

## 成本和资源边界

用户可以为自主运行设置日预算、并发数和允许时段。预算只限制新任务和可替代的推理，不得用粗暴超时破坏正在产生合法结果的任务。

Runtime 优先使用：

1. 已有状态和确定性规则。
2. 小范围上下文与低成本模型完成分类。
3. 只在方向冲突、重规划、复杂执行和策略评估时使用高成本推理。

达到预算后，Runtime 保存当前检查点、停止创建新任务并展示下一个待选动作，不把预算停止伪装成任务失败。

## 用户体验

插件与官网围绕同一组用户动作设计：

- 查看 SoloMap 当前选择了什么以及原因。
- 查看正在产生的结果和验证状态。
- 修改项目目标或授权边界。
- 暂停全部自主工作或单个项目。
- 处理真正需要用户承担的新责任、成本或方向选择。
- 查看最近完成结果，而不是阅读原始 Agent 戏剧化过程。

前台不展示：

- Cognitive Engine、adapter、lease、event log 等实现名词。
- Agent 角色矩阵和内部多 Agent 对话。
- 供应商专属状态机。
- 让用户逐次判断普通工具调用的权限弹窗。
- 用运行次数、Token、文件数营造虚假的生产力。

建议用户语言：

```text
SoloMap 正在推进：修复登录后的会话恢复
选择原因：它正在阻塞首次使用和本周发布
当前状态：验证修改
完成后：提交本地结果
需要你决定：是否允许创建 PR
```

## 官网工作台的关系

官网工作台是 Runtime 的远程用户界面，不是 Runtime 的宿主。

官网可以：

- 查看已授权的项目最小投影。
- 查看当前自主任务、选择原因、验证结果和待决策事项。
- 修改目标、暂停项目、追加指导和处理确认。
- 请求 Runtime 重新评估下一步。

官网不能：

- 直接调用本地 Shell、文件或 Agent CLI。
- 绕过 Runtime 权限代理创建执行任务。
- 根据消息已投递推断任务已经执行。
- 保存可读的项目副本、完整 Prompt、日志或 diff。
- 在本机离线时擅自把任务迁移到云端。

现有端到端加密消息、幂等命令、状态版本和最小投影设计继续有效；后续只增加与自主运行相关的类型化意图和状态，不开放任意远程命令。

Runtime 落地后，设备 E2EE 端点从插件生命周期中独立出来：设备私钥保存在操作系统安全存储中，由 Runtime 以设备身份维持出站连接、生成最小投影并解密类型化意图。插件通过已认证的本地 IPC 请求 Runtime 完成交互，不复制设备私钥，也不能要求中继代为解密。

- 本地端点使用操作系统 ACL 限定到当前用户和 SoloMap 数据根。首次连接由插件使用安装时一次性配对秘密发起挑战响应，成功后换取绑定插件实例、设备身份和兼容协议版本的短期 IPC 凭据。
- 每次改变状态的 IPC 请求携带单调 nonce、短时效和请求签名；Runtime 拒绝未配对进程、过期凭据、重复 nonce、已撤销设备和不兼容协议版本。是否支持某个平台以这些能力为准，不依赖笼统的“进程签名”。
- 旧 VS Code SecretStorage 私钥迁移采用事务：Runtime 先导入并证明可解密测试消息，中继再把设备端点切换到 Runtime，随后撤销旧插件凭据；失败时保持旧端点有效并回退，不能同时保留两个活跃身份。
- 用户撤销设备时同时撤销中继会话、设备密钥和未开始的持续授权。
- VS Code 完全关闭时，官网仍可收到 Runtime 生成的加密状态；中继只能看到路由、版本和过期所需元数据。
- Runtime 未运行或设备离线时，官网明确显示等待，不由插件或中继伪造最新状态。

## 分阶段落地

### 阶段 0：Runtime 基础

交付：

- 独立本地 Runtime 进程与单实例身份。
- 操作系统用户级服务宿主、登录启动、崩溃恢复、升级与卸载协议。
- 已登记项目读取、事件账本、任务身份、租约和检查点。
- 插件连接、健康状态、暂停和恢复。
- 统一 Cognitive Engine 与 Execution Backend 契约。
- Runtime 固定内置 Pi Agent，并把兼容 Agent CLI 作为无终端模型额度管道接入。
- 设置页只让用户选择模型额度来源，不暴露内部认知引擎差异。

验收：

- 关闭所有 VS Code 窗口后，Runtime 仍能处理已授权事件和继续任务；崩溃后由用户级服务恢复，不依赖打开插件。
- 两个 VS Code 窗口不能创建两个写入主体。
- Runtime 只看见用户登记项目。
- 未接入任何模型时，现有手动执行路径保持不变。
- 切换模型额度来源后常驻 Runtime 无需新建终端或重启 VS Code 即可采用新配置；模型管道不可用时保留确定性推荐，不影响现有手动执行路径。
- Pi Agent 无工具权限，模型请求只通过用户所选 Agent CLI 的已登录额度管道完成。
- 升级会先 drain 到可恢复检查点，迁移失败能回到旧版本；卸载会撤销启动项、设备身份和持续授权，同时保留项目文件与正式结果。

### 阶段 1：影子决策

交付：

- Runtime 观察所有登记项目并生成候选下一步，但不执行。
- 同时记录确定性推荐与智能推荐。
- 用户选择、忽略或改写建议，形成比较证据。
- 今日安排保持三项主安排；其下“其他项目建议”最多再显示三条，Runtime 投影与界面渲染同时收口，避免候选无限铺开。

验收：

- 每项建议能解释目标贡献和证据来源。
- 不读取未登记项目，不修改任何项目状态。
- 能量化智能选择相对现有 `getRecommendedNode` 的增益或无增益。

停止条件：若智能选择长期不能优于确定性基线，不进入自主调度；保留确定性选择并只增强执行。

### 阶段 2：本地自主交付

交付：

- 用户可为单个项目开启“自动完成本地结果（含提交）”。
- 用户可按项目禁止任务工具联网；未禁止时任务工具可以联网，但模型管道与推送、部署授权仍分别治理。
- Runtime 自动选择一个任务、派发执行、复核、修正一次并提交本地结果。
- Runtime 通过 headless Execution Backend 执行，不显式新建 VS Code Terminal；用户主动交互任务仍可使用原生终端。
- 隔离工作区、全局单写任务、暂停、取消、崩溃恢复和预算生效。

验收：

- 同一任务重复事件不会重复启动或重复提交。
- Runtime 重启后从精确检查点继续或明确终止。
- 关闭所有 VS Code 窗口后，Runtime 能完成一次真实的隔离 CLI 执行、验证并写入稳定任务 ref。
- 执行 Agent 不运行检查点命令时，宿主仍能确认身份、终态和续接。
- 完成结果具有独立证据，失败不会被包装成更早的可控失败。
- 用户在原工作区同时编辑、暂存或提交时，其变化不会被自主任务覆盖、夹带或回滚。
- 自主后端始终拒绝未授权文件和 Secret；项目选择禁止任务工具联网时，工具网络访问也会被真实边界拒绝且没有副作用。
- 在运行、验证和提交任一时点暂停或撤销授权时，旧授权 epoch 的能力会立即失效，进程停止，候选结果不能晋升。

### 阶段 3：自动交付 PR 与远程工作台

交付：

- 项目级“自动交付 PR”持续授权。
- 分支、推送、PR 身份和结果回读。
- 官网显示选择原因、运行状态、验证结果和待决策事项。
- Runtime 承担设备 E2EE 端点，插件通过认证 IPC 使用同一设备身份。
- 提供线性化租约仲裁、续租、fencing token 校验与租约丢失中止能力。

验收：

- 未授权项目不能推送或创建 PR。
- 重试不能重复创建 PR。
- 官网无法读取完整日志、代码或本地路径。
- 设备离线时只显示等待，不显示运行。
- 所有 VS Code 窗口关闭时，官网仍能读取 Runtime 生成的加密状态，而中继无法解密。
- 两设备竞争写租约、旧设备离线恢复和迟到提交时，所有权威入口都拒绝旧 fencing token；故障注入证明租约丢失的执行器无法晋升结果或产生外部副作用。
- 未配对本地进程、旧插件凭据、重放 IPC 请求和已撤销设备均无法取得项目能力；迁移失败可回退，迁移成功后同一设备只保留一个活跃身份。
- 在外部副作用前撤销设备时，旧授权 epoch 与旧 fencing token 同时被拒绝，正在运行的后端不能继续调用外部能力。

### 阶段 4：受验证的策略改进

交付：

- Prompt、Skill、检索、路由和验收模板的版本化候选。
- 历史回放、保留任务、小流量真实运行、晋升和回退。
- 策略效果面板只显示结果差异。

验收：

- 候选不能读取保留任务答案或修改评估器。
- 没有证据的候选不能晋升。
- 新策略回归时能恢复旧版本且不破坏已完成项目结果。
- 学习确实改变后续行为并改善至少一个结果指标。

### 阶段 5：自身代码改进候选

交付：

- Runtime 能把自身缺陷生成隔离代码任务。
- 候选只产生分支、完整验证和 PR。
- 当前稳定版本负责评估、合并建议和回退证据。

验收：

- 候选不能直接替换稳定 Runtime。
- 候选不能修改或删除其评估证据。
- 行为基线、完整测试、最终产物和真实入口验证全部通过后，才可提交人工或稳定 Runtime 审阅。

## 首版明确不做

- 自动部署、上架、支付、生产数据修改和外部业务消息。
- 多个写 Agent 并发修改同一项目。
- 用户电脑离线时自动迁移本地任务到云端。
- 把官网、GitHub 或某个 Agent 供应商变成项目状态权威。
- 自动改变项目目标、用户授权或完成标准。
- 让候选 Runtime 自动替换当前稳定版本。
- 以 Agent 自评、任务数、Token 或记忆增长证明 RSI 成立。
- 为了“更智能”而绕开现有手动 Agent 路径和用户已有 CLI。

## 仍需产品确认的三项边界

### 1. 首版自主权上限

建议默认：自动完成本地修改、验证和本地提交；“自动交付 PR”由用户对项目单独持续授权。

待确认：首版是否直接包含自动交付 PR，还是先只完成本地提交。

### 2. 自身代码修改时点

建议默认：首版只自动改进 Prompt、Skill、检索、路由和验收模板；自身代码改进在策略改进稳定后进入独立阶段，并且只生成隔离 PR。

待确认：是否希望早期验证中就加入“修改 SoloMap 自身代码并生成 PR”的能力。

### 3. 本机离线时的云端执行

建议默认：首版本机离线即等待。GitHub Agentic Workflows 和 Copilot Cloud Agent 先作为显式选择的执行后端，不自动接管本地任务。

待确认：后续是否把“允许离线转云”作为项目级持续授权。

## 成功与证伪条件

这条方向成立，需要同时观察到：

- 用户明显减少主动选择、打包上下文、盯运行和整理结果的次数。
- Runtime 选择的任务大多被用户认可，并比确定性下一步基线更接近项目目标。
- 无人值守任务能产生通过独立验证的完整结果，而不是更多半成品。
- 学习后的策略在保留任务和真实任务上持续优于旧版本。
- 用户仍能理解系统为什么行动、能暂停并保持项目控制权。

以下任一持续出现，都应停止扩大自治并回到边界设计：

- 智能选择不优于确定性规则，却显著增加成本。
- 用户频繁推翻任务方向或必须中途接管。
- 验证器无法区分真实完成和 Agent 自报完成。
- 自主任务产生更多返工、污染或未清理外部对象。
- 学习只增加记忆和规则，没有改善可测结果。
- 为了支持某个引擎而破坏本地权威或现有多 Agent 选择。
