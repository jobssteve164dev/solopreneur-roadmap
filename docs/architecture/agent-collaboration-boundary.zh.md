# SoloMap Agent 协作机制产品边界

## 这份文档解决什么判断

这份文档固定 SoloMap 是否应该、以及如何把多个 Agent CLI 纳入同一个任务推进链路。

核心判断只有一句：**多 Agent 协作应该成为 SoloMap 的内部闭环能力，而不是让用户管理一套复杂的 Agent 组织结构。**

## 产品目标

SoloMap 已经能把路线图环节、Solo 对话、Agent CLI 启动、运行记录、环节记忆和执行经验串起来。下一步的 Agent Task Flow 不应只是“启动一个 Agent”，而应让一个任务自然进入：

```text
用户目标 -> 主 Agent 执行 -> 副 Agent 复核 / 验证 -> 必要时打回续推 -> 完成证据沉淀
```

用户面对的仍然是项目推进：

- 现在要推进哪个环节。
- 本轮是否已经完成。
- 是否需要用户确认。
- 系统是否已经复核或发现问题。

用户不应该面对：

- Agent 角色矩阵。
- 多 Agent 聊天室。
- 调度状态机。
- 权限、路由、冲突和执行责任的内部细节。

## 第一版边界

第一版只做轻量主副 Agent 协作。

### 主 Agent

主 Agent 负责交付。

它可以：

- 读取任务上下文。
- 修改项目文件。
- 运行必要命令。
- 按完成标准推进本环节。
- 根据打回意见继续修正。

它对本轮任务的最终交付负责。

### 副 Agent

副 Agent 负责判断。

第一版默认只读，不直接改项目文件。它可以：

- 复核主 Agent 的结果是否符合用户目标。
- 检查完成标准是否被满足。
- 检查用户向内容或界面是否有工程自描述、维护者口吻或认知负担。
- 建议应补的验证命令、文件检查或风险处理。
- 输出可执行的打回意见。

它不直接成为最终交付者，避免多个 Agent 同时改文件导致责任不清。

“只读”必须是执行权限，不是提示词约定。复核 Agent 运行时不得获得项目写权限、外部发布权限或绕过审批的通用权限；它只向标准输出返回结构化结论，由 SoloMap 写入复核记录。若某个 Agent CLI 无法提供可验证的只读模式，本次复核应标记为“尚未复核”，不能以普通任务权限继续运行。

### SoloMap

SoloMap 负责闭环。

它负责：

- 选择是否触发副 Agent。
- 把主 Agent 运行结果压缩成副 Agent 可复核的上下文。
- 判断副 Agent 输出是通过、打回还是需要用户确认。
- 将明确问题打回主 Agent 续推。
- 将完成证据写入运行记录、环节记忆和执行经验层。

## 有价值复核的成立条件

复核不是让另一个 Agent 重读主 Agent 的总结。它必须同时满足：

1. **目标独立**：直接读取用户原始目标和完成标准，不以主 Agent 的完成声明代替目标。
2. **证据独立**：读取 SoloMap 采集的 revision、精确 patch、文件变化和验证记录，不以主 Agent 自述代替事实。
3. **责任不同**：主 Agent 负责交付，复核 Agent 只负责逐项判断证据是否足够。
4. **结果可执行**：不通过时必须指出失败标准、证据缺口和修正动作，并能自动回到主 Agent 续推。

复核对象必须绑定到确定的 execution 与证据快照。工作区在复核开始前再次变化时，系统不能继续对移动目标给出 `pass`，应重新采集证据或标记证据已过期。

## 普通 Step / Solo 的证据驱动复核协议

SoloMap 为每次复核生成内部验收包，至少包含：

- 被复核 execution id。
- 用户目标与路线图环节完成标准；Solo 任务使用本轮原始请求作为临时完成标准。
- 主任务开始时的 Git revision，以及结束后的精确 patch 或等价文件哈希证据。
- changed files、touched files、验证输出和已知缺口。
- 证据文件路径与摘要哈希，避免只把长日志重新塞给复核 Agent。

普通 Step / Solo 不引入 Flow 的 Planner、Builder、Verifier、H/I/J 评分或微循环对象。它只输出轻量结果：目标是否满足、证据是否足够、逐项检查、需要修正的动作或需要用户确认的问题。

Step 直接使用路线图环节目标和既有完成标准。Solo 直接使用用户本轮原始要求；实施或修复类 Solo 可以复核并续推，讨论或判断类 Solo 不套用代码交付标准，也不生成虚构的 Planner 标准。

每条适用的完成标准必须有 `pass / fail / unclear` 和证据引用。没有证据的 `pass`、引用不存在文件的 `pass`、必跑验证缺失时的 `pass` 都应由 SoloMap 拒绝，而不是相信 Agent 自报。

Flow 可以复用相同的只读执行与证据采集底座，但继续使用自己的 H/I/J 结构化验收和多轮状态；普通 Step / Solo 不得因此变成缩小版 Flow。

复核基础设施故障与交付失败必须分开：CLI 不可用、结果无法解析、证据过期属于“尚未复核”，不能证明主交付失败；只有复核证据明确否定完成标准时，才进入修正。

## 打回续推闭环

`revise` 不能只留下评论或把状态停在 `In Progress`。SoloMap 应把以下内容注入原主 Agent 会话：

- 未满足的完成标准。
- 支撑判断的文件、patch 或验证证据。
- 必须完成的最小修正动作。
- 修正后的验收方式。

修正运行结束后只复核失败项和新增差异。第一版最多自动修正一次；第二次仍未通过、连续出现相同问题或需要授权时，停止自动推进并给用户一个明确确认点。用户前台仍只看到“正在复核 / 继续修正中 / 需要确认 / 已完成”。

## 用户可见设置

第一版可以在设置中暴露一个很轻的主副 Agent CLI 设置机制。

建议前台命名：

- `Agent 协作`
- `主 Agent`
- `复核 Agent`
- `自动复核`

设置含义：

| 设置 | 用户含义 | 产品边界 |
| --- | --- | --- |
| 主 Agent | 负责实际推进任务 | 可写文件、可运行命令 |
| 复核 Agent | 负责复核结果 | 第一版默认只读 |
| 自动复核 | 任务结束后是否自动触发复核 | 可关闭，避免额外耗时和成本 |
| 仅高风险任务启用 | 只在代码、发布、路线图调整、用户向内容等任务启用 | 可作为后续选项 |

普通推进界面不应要求用户理解主副 Agent 的内部协作过程。前台最多显示：

- `正在复核`
- `复核通过`
- `发现问题，正在继续修正`
- `需要你确认`

## 不采用“虚拟内阁”作为前台心智

“虚拟内阁”可以作为内部设计比喻，但不应成为第一版用户界面主语。

原因：

- 用户目标是完成项目任务，不是管理 Agent 组织。
- 角色过多会把系统责任转嫁给用户。
- 多 Agent 同屏讨论容易产生戏剧化输出，反而让用户成为裁判。
- 第一版需要先证明协作闭环能提高完成率和复核质量。

后续可以在内部扩展更多角色，但前台仍应保持一套简单心智：

```text
推进任务 -> 系统复核 -> 完成或继续修正
```

## 与现有主路径的关系

Agent 协作不新增第三套执行入口。

它只增强现有入口：

- 路线图环节推进。
- Solo 对话。
- 路线图调整。

Issue、学习候选、交付信号和经验库可以进入上下文，但不应变成新的 Agent 派发主入口。

## 风险边界

### 不让副 Agent 直接改文件

第一版副 Agent 只读复核。若后续允许副 Agent 执行验证命令或修改文件，必须先明确：

- 谁对最终结果负责。
- 文件冲突如何处理。
- 失败后如何回退或继续。
- 用户授权何时必须介入。

### 不做多 Agent 并发改同一任务

第一版不做多个 Agent 同时改同一批文件。协作顺序应是：

```text
主 Agent 执行 -> 副 Agent 复核 -> 主 Agent 续推
```

而不是多个 Agent 并发提交结果。

### 不把自动化变成用户负担

如果某项协作机制需要用户理解内部角色、执行路由、状态转移或冲突处理，默认说明设计偏航。系统应吸收复杂度，只把目标、结果、确认点和风险暴露给用户。

### 高风险动作必须停下确认

涉及以下动作时，协作机制不能绕过用户授权：

- 发布、部署、上架。
- 支付、账单、外部消息发送。
- 权限、凭证、外部账号连接。
- 删除或不可逆写入。
- 会影响真实用户或生产环境的动作。

## 后续扩展方向

当主副 Agent 闭环稳定后，可以逐步扩展：

1. `Verifier`：运行测试、构建或检查命令。
2. `Researcher`：在需要外部信息时补充资料。
3. `Writer`：处理文档、发布说明、营销内容。
4. `Release`：在明确授权下处理发布链路。
5. 多环节连续推进：仅在低风险、依赖已满足且每个环节都有完成证据时启用。

这些扩展都应服从同一边界：

```text
主 Agent 对交付负责，辅助 Agent 对判断负责，SoloMap 对编排和闭环负责，用户只负责目标与授权。
```
