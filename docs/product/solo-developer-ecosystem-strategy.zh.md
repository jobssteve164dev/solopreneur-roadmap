# SoloMap 独立开发者生态与协作网络战略

## 这份文档解决什么判断

这份文档固定 SoloMap 是否应该从本地项目驾驶舱继续发展为面向独立开发者和一人公司的协作生态，以及这条演进路径必须遵守的产品边界。

核心判断只有一句：**SoloMap 的生态不是把用户拉进一个更大的聊天门户，而是让本地项目在用户明确授权下连接到协作者、可复用能力、真实反馈和商业机会。**

这意味着：

- 本地 SoloMap 继续掌握项目事实、Agent 执行和最终操作权。
- 官网成为项目选择性对外连接世界的入口，不成为项目云端副本。
- 协作从邀请制、端到端加密的临时房间开始。
- 公共空间与私密房间使用不同的信任、留存和治理规则。
- 生态价值用项目是否获得真实推进衡量，不用消息数、粉丝数或停留时长衡量。

## 战略机会

独立开发者使用 Agent 后，执行能力显著增强，但仍然缺少传统团队中的多种角色：

- 能从外部视角挑战产品假设的人。
- 能做技术或安全审计的人。
- 能提供真实试用反馈的人。
- 能帮助分发、销售和触达市场的人。
- 能把一次解决方案提炼为可复用能力的人。

GitHub 主要连接代码与开源协作，Discord 等社区主要连接人与讨论，传统自由职业平台主要连接订单。SoloMap 有机会连接另一组更接近项目交付的事实：

- 这个项目正在推进什么。
- Agent 当前正在执行什么。
- 用户卡在什么具体问题上。
- 哪条外部建议被项目采纳。
- 采纳后是否进入下一轮 Agent、路线图或验证。
- 最终是否形成可验证结果或可复用能力。

因此，SoloMap 的生态基本单位不是帖子和关注关系，而是：

1. **项目**：真实工作和结果的承载体。
2. **当前问题**：用户明确选择对外暴露的协作入口。
3. **有效贡献**：被项目拥有者采纳并进入行动的外部输入。
4. **可复用能力**：可以被其他项目安装、引用或复用的模板、Skill、工作流和方法。
5. **真实结果**：完成、验证、发布、用户反馈或商业结果。

## 产品表面与责任

| 产品表面 | 用户用它完成什么 | 不承担什么 |
| --- | --- | --- |
| 本地 SoloMap 插件 | 管理项目、运行 Agent、保存路线图、验证结果、决定哪些内容可以对外 | 不自动上传项目，不把执行权交给远端参与者 |
| 官网门户 | 发现项目求助、公共主题、贡献者和可复用能力 | 不成为第二份项目权威，不默认读取本地项目 |
| 私密协作房间 | 邀请可信参与者围绕当前问题交流、审计和提供反馈 | 不直接运行、停止、批准或控制用户的 Agent |
| 公共共创空间 | 围绕明确主题进行可治理的公开交流和项目互助 | 不承诺端到端加密，不做无边界公共大群 |
| 能力库与后续市场 | 发布、发现、安装和评价可复用能力或专业服务 | 不在缺少可信结果时提前变成泛接单平台 |
| SoloMap 中继 | 连接客户端、路由密文、支持短时离线恢复 | 不读取聊天正文，不保存项目副本，不理解 Agent 命令语义 |

## 生态主循环

```text
本地项目、路线图与 Agent 执行
        ↓ 用户主动选择对外
脱敏求助卡 / 共创邀请 / 可复用能力 / 发布成果
        ↓
官网发现、主题组织与协作者匹配
        ↓
邀请制加密协作房间
        ↓ 用户挑选有效输入
加入 Agent 下一轮 / 保存为项目想法 / 调整路线图
        ↓
本地执行、验证与交付
        ↓
贡献归因、结果信誉与能力沉淀
        ↓
其他项目发现并复用
```

循环必须始终回到用户项目。任何只能增加内容消费、聊天时长或社区热度，却不能形成项目下一步、能力或结果的功能，都不属于当前主线。

## 私密协作房间

### 产品定位

私密房间首先服务这个动作：**Agent 工作期间，项目拥有者邀请少数可信的人一起交流想法、审计判断，并把有价值的输入带回项目。**

它不是现有“自由研讨”的多人版：

- `自由研讨` 是用户与本地 Agent 的项目级对话。
- `协作房间` 是人与人围绕项目问题的临时交流。
- 两者可以互相引用，但不能共享同一数据模型或自动互相注入。

侧边栏顶部可以提供协作房间入口。入口打开可折叠房间区域，显示在线人数和连接状态，不新增第四种路线图模式。

### 第一版目标能力

- 随机生成房间和邀请链接，不使用项目名、仓库地址或本地路径作为房间标识。
- 无需参与者安装 SoloMap；邀请链接可以打开官网轻量房间页面。
- 使用临时昵称和房间级访问凭证。
- 支持纯文本、小段代码、回复引用和在线人数。
- 提供“加入 Agent 下一轮”和“保存为项目想法”两个本地动作。
- 只允许项目拥有者执行上述本地动作。
- 默认临时，不把完整聊天记录写入项目 SQLite、Git 或路线图。
- 可以在参与者重新连接时恢复少量短期密文消息。

### 已落地的首个可用版本（2026-07-29）

当前代码已经完成“创建房间—分享邀请—多人交流—把有效输入带回项目”的最小闭环：

- SoloMap 侧边栏顶部提供“临时共创”入口，可创建房间并复制邀请链接。
- 未安装 SoloMap 的参与者可直接在官网房间页以临时昵称加入。
- 正文在浏览器或插件内使用 AES-GCM 加密；官网中继只接收和转发密文。
- 房间最长存在 24 小时，只保留最近 100 条密文，每条消息的中继载荷不超过 16 KiB。
- 插件将房间凭证放入 VS Code SecretStorage，官网参与者的最近房间只保存在当前浏览器 IndexedDB。
- 项目拥有者可以把单条消息加入 Agent 下一轮输入，或追加保存到项目想法；两种动作都不会自动运行 Agent 或修改路线图。
- 官网中继使用一个房间一个 Durable Object 的 WebSocket 通道，房间到期后由定时清理删除状态。

首个版本尚未包含回复引用、Agent 粗粒度状态共享、文件传输、账号身份、跨设备同步和公共共创空间。这些缺口不改变当前临时房间的数据边界，也不会通过自动上传项目内容来补齐。

### 明确禁止

- 远端参与者直接运行、停止、重试或批准 Agent。
- 远端消息自动进入 Agent Prompt、全局记忆或路线图。
- 默认共享 Agent 完整输出、代码、文件路径、Git diff、日志或长期记忆。
- 用聊天室替代路线图环节、Solo 对话或项目反馈闭环。
- 把“持有邀请链接”描述为经过验证的真实身份。

### Agent 状态共享

房间可以由项目拥有者选择共享粗粒度状态：

- Agent 工作中。
- 已完成。
- 失败或等待确认。

默认不共享任务标题、Prompt、输出和文件变化。即使采用端到端加密，也必须遵守数据最小化，不能把加密当成扩大共享范围的理由。

## 官网中继选择

### 已确认方向

第一版不采用纯 WebRTC P2P 作为正式主路径，而是在 `solomap.app` 官网基础设施中增加轻量 WebSocket 消息中继。

推荐使用 Cloudflare Durable Objects：

- 每个房间映射到一个独立 Durable Object。
- 客户端通过 WebSocket 连接房间。
- 使用 WebSocket Hibernation 在空闲时降低常驻资源消耗。
- 中继只处理连接、密文、顺序、过期和投递状态。
- 不需要在第一版处理 WebRTC 信令、NAT 穿透、STUN、TURN 和多人全连接拓扑。

这条路径属于“Serverless 运维 + 中心化密文中继”，不是严格去中心化。对外应表达为：

> 端到端加密的临时协作房间，SoloMap 服务器无法读取消息正文。

不得表达为“完全无服务器”“绝对去中心化”或“服务器完全不参与通信”。

### 密钥与邀请

房间邀请至少拆分为两个能力：

- `relayToken`：允许客户端连接指定房间，由中继校验。
- `encryptionKey`：只在参与者客户端中用于加解密，不交给中继。

邀请链接可以将加密密钥放在 URL Fragment 中：

```text
https://solomap.app/room/<room-id>?token=<relay-token>#<encryption-key>
```

URL Fragment 不随 HTTP 请求发送给官网。服务端仍会看到房间 ID、访问令牌、连接时间、IP 等必要网络元数据，因此不能宣称通信完全无元数据。

### 中继可以保存的数据

- 不含项目语义的房间 ID。
- 房间访问凭证的安全摘要和有效期。
- 参与连接的临时端点 ID。
- 密文、消息 ID、顺序号、创建时间、投递状态和过期时间。
- 限流、滥用防护和故障诊断所需的最小元数据。

### 中继不得保存的数据

- 聊天正文和加密密钥。
- 项目名称、路径、仓库地址和项目列表。
- 路线图、Prompt、Agent 输出、日志、代码、diff 和长期记忆。
- 可以远程执行的任意命令字符串。
- 从聊天室自动提炼出的用户项目画像。

第一版密文默认只保留最近少量消息或不超过 24 小时。需要长期保存的内容必须由项目拥有者明确选择，并回到本地项目中的正式对象。

## 公共共创空间

### 不做单一公共大群

第一版不建设所有用户永久共用的公共聊天室。一个无边界公共大群会立即引入：

- 垃圾广告、诈骗链接和身份冒充。
- 骚扰、敏感内容和封禁申诉。
- 多语言、跨时区和主题噪音。
- 为社区活跃而制造的低价值互动。
- 端到端加密与内容治理之间的直接冲突。

公共交流应采用“共创广场”模型：

- 由官方或可信贡献者发起少量明确主题。
- 每个主题拥有独立房间、说明、存续周期和治理者。
- 默认允许浏览，登录并满足限流后发言。
- 支持举报、删除、禁言和封禁。
- 到期关闭或归档，不形成永不结束的信息垃圾场。
- 优质贡献可以由项目拥有者主动带回本地项目。

公共空间不承诺端到端加密。公开内容需要可治理、可举报并遵守明确内容政策。私密协作房间与公共共创空间可以使用相似界面，但不能用一个 `public/private` 开关强行共用信任和留存规则。

## 求助卡与选择性发布

私密房间之后，最重要的生态入口不是信息流，而是由本地项目主动生成的脱敏求助卡。

求助卡只包含用户确认公开的内容：

- 项目要达成的目标摘要。
- 当前一个具体问题。
- 希望获得的帮助类型：创意、审计、测试、技术建议、分发或其他。
- 期望交付形式和有效期。
- 是否开放临时协作房间。
- 是否提供奖励。

生成求助卡时，系统必须默认排除：

- 本地路径、仓库地址和未公开项目名。
- 代码、完整 Prompt、Agent 输出和终端日志。
- 路线图全量内容、长期记忆和附件。
- 环境变量、凭证、用户数据和内部商业信息。

发布前必须由用户看到最终公开内容并主动确认。服务端不能从本地项目自动抓取或补全更多内容。

## 贡献信誉

SoloMap 的信誉不应以粉丝数、点赞数或发言量为核心。更可信的信号来自项目结果：

- 建议被项目拥有者采纳。
- 建议被加入 Agent 下一轮或路线图。
- 审计发现的问题被真实修复。
- 测试反馈影响了交付结果。
- Skill、模板或工作流被其他项目复用。
- 复用后产生了可验证完成、发布或反馈结果。

贡献归因必须由项目拥有者确认，不能由贡献者自行声明。项目结果可以证明贡献发生过，但不应自动公开用户的私有项目信息。

## 生态的四层演进

### 第一层：项目协作网络

交付邀请制协作房间、脱敏求助卡、消息回到项目的明确动作和贡献归因。

成立条件：外部协作能够稳定形成项目下一步，而不是只形成聊天记录。

### 第二层：可复用能力网络

允许用户主动发布和发现：

- 路线图模板。
- Agent 工作流。
- Skill。
- MCP 配置包。
- 发布、审计和验证清单。
- 可复用方法和项目经验。

能力评价优先依据真实项目采用和结果，不只依据下载量。安装仍然回到本地 SoloMap，并遵守现有 Skill、连接器和权限治理边界。

### 第三层：可信匹配网络

基于项目需要、贡献记录和能力结果，逐步匹配：

- 产品互审伙伴。
- 技术或安全审计者。
- 测试用户。
- 营销和分发协作者。
- 临时领域专家。
- 长期项目合作者。

匹配不应要求用户公开完整项目，也不应以通用简历关键词代替真实贡献证据。

### 第四层：经济网络

只有前三层形成可信供给和信誉后，才逐步加入：

- 付费审计和顾问服务。
- 项目卡点悬赏。
- Skill、模板和工作流交易。
- 测试、发布和分发服务。
- 贡献者 Pro 奖励。
- 在双方明确约定下的项目合作或收入分成。

经济层不能抢先于信誉层，否则容易退化成低质量接单和广告平台。

## 验证顺序

### 阶段 A：私密协作闭环

- 官网 WebSocket 密文中继。
- 插件顶部协作入口。
- 官网轻量参与页面。
- 邀请制临时房间。
- “加入 Agent 下一轮”和“保存为项目想法”。

验收重点：不同网络下可连接；服务器无法读取正文；远端不能控制 Agent；关闭和重连行为明确。

### 阶段 B：求助与贡献闭环

- 从本地生成脱敏求助卡。
- 定向邀请或选择性公开。
- 被采纳建议的贡献归因。
- 贡献是否产生项目下一步的结果记录。

验收重点：用户不需要暴露项目即可获得有效帮助；求助卡到项目动作的转化成立。

### 阶段 C：公共共创试验

- 少量官方主题房间。
- 登录、限流、举报和治理。
- 到期关闭和内容归档策略。
- 优质贡献进入项目或能力库。

验收重点：公共交流产生高质量贡献，治理成本可控，没有演变为泛社交信息流。

### 阶段 D：能力与经济网络

- 可复用能力发布和安装。
- 结果驱动的能力信誉。
- 专家和协作者匹配。
- 小范围付费服务或悬赏验证。

验收重点：复用和交易改善真实项目结果，且没有破坏本地优先、权限和安全边界。

## 北极星指标

生态的北极星指标是：

> 每周由外部协作或可复用能力带来的、被项目拥有者采纳并形成可验证推进的项目数量。

辅助指标包括：

- 创建房间后至少产生一次有效交流的比例。
- 房间消息被保存为项目想法或 Agent 下一轮的比例。
- 求助卡获得有效回应并被标记解决的比例。
- 被采纳贡献最终形成完成、验证、发布或用户反馈的比例。
- Skill、模板和工作流被真实项目复用并产生结果的比例。
- 举报率、封禁率、诈骗和垃圾信息发生率。

不把以下指标作为主要成功标准：

- 总消息数。
- 页面停留时长。
- 粉丝数和点赞数。
- 没有结果证据的模板下载量。
- 只反映围观而不反映项目推进的日活。

## 商业化关系

生态不替代现有 Pro 订阅，而是提供新的价值来源：

- Pro：高级项目经营、跨项目判断和更强协作能力。
- 能力市场：Skill、模板和工作流交易佣金。
- 专业服务：认证审计、测试、顾问和分发服务佣金。
- 贡献激励：用 Pro 权益、平台信用或明确奖励回报高价值贡献者。

第一阶段不应为了变现限制基本邀请协作。先证明协作可以改善项目推进，再决定哪些规模、治理、信誉和市场能力属于 Pro 或交易服务。

## 长期边界

无论生态扩展到什么规模，都必须保持：

1. 用户本地项目是唯一事实权威。
2. 项目内容只在用户主动选择后对外。
3. 官网默认不知道用户有哪些项目和项目内部发生了什么。
4. 远端参与者不能直接获得 Agent、终端、文件或发布权限。
5. 私密房间和公共空间使用不同的加密、留存和治理规则。
6. 贡献信誉来自真实项目结果，不来自社交声量。
7. 所有生态入口最终都应降低项目推进阻力，而不是增加新的管理负担。

如果未来某项功能要求自动上传项目、把云端变成第二份路线图权威、让公共参与者直接操作 Agent，或要求用户理解复杂的内部权限和路由，它已经超出当前生态边界，必须重新讨论。
