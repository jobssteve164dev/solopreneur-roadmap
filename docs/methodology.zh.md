# SoloMap 方法论

SoloMap 的核心不是“再做一个 AI 聊天框”，而是帮独立开发者把不确定的项目想法推进成真实交付。它围绕一个操作原则展开：

> 先发现真实问题，再打造可交付产品，然后获得客户反馈，最后用循环把增长放大。

## 四个阶段

### 1. 找到真实问题

第一步不是写完整商业计划，而是确认一个值得解决的问题，找到可以学习和验证的人群，积累下一步行动动能，并从零开始。

SoloMap 的初始化路线图应帮助用户明确：

- 什么问题值得探索。
- 谁可以帮助验证这个问题。
- 哪个小动作能带来动能。
- 第一个可执行任务是什么。

输出物不应该是精美但无法执行的战略文档，而应该是可以立刻推进的路线图。

### 2. 打造产品系统

原型只是开始。真正能交付的产品需要完整工程系统支撑：需求、架构、数据、基础设施、测试、设计、部署和持续维护。

在 SoloMap 中，每个路线图环节都应该能展开为 Agent 对话，并留下：

- 实际修改的项目文件。
- 可见的执行结果。
- Agent 尝试过什么的记录。
- 下一轮 Agent 可以继续读取的环节记忆。

Agent 回复了不等于项目推进了。只有本地项目文件、状态和下一步动作都发生变化，才算真正产生进展。

### 3. 卖给客户

产品不会因为被构建出来就自动获得客户。用户需要能发现它、理解它、信任它，并完成转化。

SoloMap 的路线图应覆盖面向市场的环节：

- 品牌。
- 官网或分发页面。
- 营销信息。
- 销售或转化路径。
- 需求生成。

路线图不应该止步于“代码完成”，而应该把项目带到真实市场接触中。

### 4. 通过循环规模化

规模化不是所有事情完成后的单独阶段，而是一个持续循环：

```text
Build -> Sell -> Learn -> Improve
```

SoloMap 应让这个循环可见、可执行、可重复。每次环节推进或路线图调整后，项目都应该能吸收反馈：

- 产品数据。
- 客户支持信号。
- 单位经济模型。
- 扩张机会。

因此，路线图不是静态计划，而是一个持续学习和改进的控制面。

## SoloMap 操作循环

图片中的核心逻辑是：

```text
发现问题 -> 打造产品 -> 获取客户 -> 持续放大
```

SoloMap 将它翻译为 Agent 原生工作流：

```text
项目想法 -> 路线图 -> 环节对话 -> 本地文件变化 -> 执行结果 -> 路线图更新
```

这条循环定义了产品体验：

1. 用户从一个想法或变化的目标开始。
2. SoloMap 把它变成分阶段路线图。
3. 每个阶段都可以发起聚焦的 Agent 对话。
4. Agent 在用户本地项目文件夹内工作。
5. SoloMap 记录状态、修改文件、输出和重试入口。
6. 路线图随着执行结果和市场反馈持续变化。

## 产品原则

### 路线图先于聊天

SoloMap 不应成为泛用聊天界面。路线图为每次 Agent 对话提供业务和交付上下文。

### 行动先于完美

用户不需要完整需求、完整团队或完美计划才能开始。SoloMap 应始终保留一个可以推进的下一步动作。

### 本地交付先于 Agent 输出

Agent 的自然语言回答不够。SoloMap 应把本地项目变化、执行状态和用户可控闭环作为进展证据。

### 市场路径先于内部完成

路线图必须覆盖产品如何触达客户，而不仅是代码如何写完。

### 循环先于线性计划

SoloMap 应支持调整、重试、学习和改进。路线图有价值，是因为它能随着项目变化。

## 默认路线图形态

一份健康的 SoloMap 路线图通常应覆盖：

```text
1. 问题和客户发现
2. 产品基础和首个可用版本
3. 分发、品牌、官网、营销和销售
4. 反馈、数据、支持、单位经济模型和扩张
```

这不是僵硬模板，而是防止独立项目只停留在代码、聊天或计划里的最低心智模型。
