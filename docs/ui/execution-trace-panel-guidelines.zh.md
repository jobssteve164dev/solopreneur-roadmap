# 执行轨迹面板设计指导

## 这份文档解决什么判断

这份文档约束 SoloMap 的执行轨迹面板如何呈现微观执行循环，让用户能在回路中理解、指导和验收项目如何长出来。

核心判断只有一句：**执行轨迹面板不是 Agent 日志看板，而是“行动目标”和“代码 diff”之间的事实透镜。**

## 产品定位

路线图是行动目标。  
执行轨迹是行动如何变成项目事实。  
diff 是最底层代码证据。

执行轨迹面板位于路线图之下、diff 之上：

```text
路线图：要达成什么
执行轨迹：意图如何被规划、实施、验证、归因
diff / log / test：证据是什么
```

用户打开面板时，优先要回答：

- 这个项目最近是怎么被 Agent 推进的？
- 哪些微观循环已经闭环？
- 哪些只是实施了但还没验证？
- 哪些失败、偏离或生成了下一轮？
- 这些循环如何支撑路线图环节完成？
- 我现在该验收、追问、继续修，还是允许推进下一环节？

## 面板承载形态

第一版执行轨迹面板应做成 SoloMap 插件内嵌 Webview，而不是独立 HTML 文件。

原因：

- 执行轨迹需要和路线图环节、完成标准、Agent run、继续执行按钮联动。
- 用户要在同一个产品心智里完成“查看轨迹 -> 判断缺口 -> 继续微循环 -> 推进路线图”。
- 独立 HTML 更适合报告、分享或归档，不适合作为 Agent Task Flow 的控制面。

推荐关系：

```text
.solopreneur/execution-traces/*.json
  -> 插件读取并构建内存模型
  -> SQLite / 索引缓存加速聚合
  -> Webview 执行轨迹面板展示
  -> 用户触发下一轮微循环或推进路线图
```

HTML 可以作为后续导出能力：

- 导出某个路线图环节的执行轨迹。
- 导出项目级审计报告。
- 分享给不使用插件的人。
- 归档一次重要发布前的证据链。

但 HTML 不应成为第一版主面板，也不应承载“继续修正、补充验证、确认推进”等主动作。

## 用户动作模型

面板必须围绕用户动作组织，而不是围绕内部对象组织。

主要动作：

1. 查看当前路线图环节下的微观循环。
2. 判断每个循环是否可信闭环。
3. 发现证据不足、验证失败或偏离。
4. 进入证据下钻。
5. 让 Agent 继续下一轮微循环。
6. 在完成标准被证据覆盖时确认或允许推进路线图。

不应把主界面做成：

- Agent run 列表。
- 原始日志列表。
- JSON digest 浏览器。
- 模块依赖图中心。
- 多 Agent 角色聊天室。

## 信息层级

### 第一层：路线图环节执行状态

在每个路线图环节里展示微观循环聚合结果：

```text
当前环节：反馈与规模化
微观循环：6 个
已闭环：4 个
需继续：1 个
需确认：1 个
完成标准覆盖：3 / 4
下一步：补齐验证后可完成环节
```

这层回答“宏观环节为什么能或不能完成”。

### 第二层：微观循环卡片

每张卡片展示一个意图如何走到当前结果。

推荐结构：

```text
意图：侧边栏需要能停止异常 Solo 对话
判断：复用现有停止链路，不新增第二套控制
动作：改造侧边栏状态与停止消息处理
证据：webview regression test 通过；触碰 3 个文件
结果：已闭环
归因：支撑“反馈与规模化”环节的异常对话控制标准
```

卡片状态必须清晰：

- 已闭环。
- 已实施，待验证。
- 验证失败。
- 部分完成。
- 发生偏离。
- 已生成下一轮。
- 需要确认。

### 第三层：证据下钻

用户需要时再下钻：

- 关联 Agent 对话。
- 关联 run digest。
- 关联 commit 或 diff。
- 关键文件。
- 测试命令和结果。
- UI 截图或人工验收。
- 设计对标。
- 未覆盖项。

证据入口应服务判断，不应把用户推入原始日志海洋。

## 面板布局建议

### 路线图联动视图

在路线图环节详情中增加执行轨迹区域。

```text
环节目标
完成标准
执行轨迹
  - 已闭环循环
  - 需要继续循环
  - 证据不足循环
下一步动作
```

优势：用户不会离开路线图心智，能直接看到宏观目标如何被微观证据支撑。

### 项目级轨迹视图

提供项目级执行轨迹总览。

```text
最近塑造的能力
反复返工的区域
证据不足的区域
验证失败后产生的新循环
被多个循环共同塑造的模块
即将影响路线图推进的缺口
```

优势：用户能理解项目是怎样被 Agent 一轮轮塑造成当前状态。

## 状态文案

推荐使用用户能直接行动的文案：

| 内部状态 | 用户可见表达 |
| --- | --- |
| `closed` | 已闭环 |
| `implemented_unverified` | 已实施，待验证 |
| `verified_failed` | 验证失败 |
| `partial` | 部分完成 |
| `deviated` | 偏离原意 |
| `spawned_followup` | 已进入下一轮 |
| `needs_user_confirmation` | 需要你确认 |
| `abandoned` | 已放弃 |

按钮文案应围绕动作：

- `继续修正`
- `补充验证`
- `查看证据`
- `确认推进`
- `生成下一轮`
- `标记放弃`

避免：

- `Open digest`
- `Inspect orchestration`
- `Verifier output`
- `Trace schema`
- `Routing decision`

## 路线图自动推进表达

当执行轨迹足以支撑环节完成时，面板可以显示：

```text
这个环节的 4 项完成标准已有闭环证据，可以推进到下一环节。
```

当不能推进时，必须明确下一步：

```text
还不能完成：核心路径已实施，但缺少真实渲染验证。建议先补充验证。
```

用户不应自己从日志里推断为什么卡住。

## 人在回路的关键介入点

面板应把六阶段中最容易偏航的位置显性化：

- 意图：Agent 是否理解错了。
- 判断：方案是否偏离目标或扩大范围。
- 动作：是否做了与目标无关的改动。
- 证据：是否缺少必要验证。
- 结果：是否过度宣称完成。
- 归因：是否错误推动路线图。

这些介入点应该能直接触发下一轮微观循环，而不是只留下评论。

## 面板不展示什么

不在主界面展示：

- 完整 prompt。
- 完整终端日志。
- 原始 JSON schema。
- 多 Agent 内部争论。
- embedding、graph、digest、score 等内部治理对象。
- 方法论长篇解释。

这些可以作为审计层存在，但不能成为用户完成动作的前台负担。

## 与旧微观可见性工件的关系

旧的模块设计、实现总结、设计对标、模块拓扑和健康报告仍有价值，但它们不是面板主语。

它们应作为证据层进入微观循环：

- 模块设计用于支撑判断阶段。
- 实现总结用于支撑动作阶段。
- 设计对标用于支撑证据和结果阶段。
- 模块拓扑用于支撑影响范围。
- 健康报告用于发现下一轮微观循环。

面板主语始终是：

```text
意图如何变成项目事实。
```

## 验收标准

- 用户不用读 diff，也能知道一个路线图环节为什么能或不能完成。
- 每个微观循环都能看到意图、判断、动作、证据、结果、归因。
- 没有证据的循环不会显示为已闭环。
- 失败、偏离、部分完成能直接生成下一轮动作。
- 路线图推进理由来自闭环证据，而不是 Agent 自称完成。
- 主界面不要求用户理解 Agent 角色、digest schema、执行图或内部路由。
