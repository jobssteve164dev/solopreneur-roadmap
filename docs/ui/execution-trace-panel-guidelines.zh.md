# 执行轨迹面板设计指导

## 这份文档解决什么判断

这份文档约束 SoloMap 的执行轨迹面板如何呈现微观执行循环，让用户能在回路中理解、指导和验收项目如何长出来。

核心判断只有一句：**执行轨迹面板不是 Agent 日志看板，而是以推进判定为首屏的事实透镜。**

## 产品定位

路线图是行动目标。  
执行轨迹是行动如何变成项目事实。  
diff 是最底层代码证据。

执行轨迹面板位于路线图之下、diff 之上：

```text
路线图：要达成什么
执行轨迹：意图如何被规划、实施、验证、归因
diff / log / test：证据是什么
```

用户打开面板时，优先要回答：

- 当前路线图环节能不能推进？
- 不能推进时，卡在哪里？
- 下一步该补验证、继续修正、等待确认，还是允许完成环节？
- 哪些微观循环支撑或阻断了这个判断？
- 需要时，证据在哪里？

执行轨迹面板仍然要展示项目如何由微观循环长出来，但默认体验必须先服务推进控制，再服务历史回溯。

## 默认模式：推进控制台

执行轨迹面板默认打开时，不应先展示轨迹总览或微循环历史，而应先给出当前路线图环节的推进判定。

首屏顺序：

```text
1. 当前环节能否完成
2. 不能完成的阻断原因
3. 下一步动作
4. 完成标准覆盖情况
5. 支撑或阻断的微观循环
6. 证据下钻
```

推荐首屏结构：

```text
当前环节：反馈与规模化
状态：还不能完成
原因：2 个微观循环已实施，但缺少验证证据
下一步：补充验证
```

主动作按钮：

- `补充验证`
- `继续修正`
- `查看证据`
- `确认推进`

这一层应该像检查单，而不是仪表盘。它帮助用户判断是否可以安全进入下一步，不是让用户欣赏 Agent 做了多少事。

## 次级模式：回溯轨迹

回溯轨迹用于理解项目是怎样被 Agent 一轮轮塑造出来的。

它可以展示：

- 项目级微观循环时间线。
- 被多个循环共同塑造的能力。
- 反复返工的模块或用户路径。
- 证据不足长期存在的区域。
- 验证失败后生成的新循环。

但回溯模式不应抢占默认首屏。只有当用户想理解历史、审计路径或复盘项目成长时，才进入完整轨迹视图。

## 面板承载形态

第一版执行轨迹面板应做成 SoloMap 插件内嵌 Webview，而不是独立 HTML 文件。

原因：

- 执行轨迹需要和路线图环节、完成标准、Agent run、继续执行按钮联动。
- 用户要在同一个产品心智里完成“查看轨迹 -> 判断缺口 -> 继续微循环 -> 推进路线图”。
- 独立 HTML 更适合报告、分享或归档，不适合作为 Agent Task Flow 的控制面。

推荐关系：

```text
.solopreneur/execution-traces/*.json
  -> 插件读取并构建内存模型
  -> SQLite / 索引缓存加速聚合
  -> Webview 执行轨迹面板展示
  -> 用户触发下一轮微循环或推进路线图
```

HTML 可以作为后续导出能力：

- 导出某个路线图环节的执行轨迹。
- 导出项目级审计报告。
- 分享给不使用插件的人。
- 归档一次重要发布前的证据链。

但 HTML 不应成为第一版主面板，也不应承载“继续修正、补充验证、确认推进”等主动作。

## 用户动作模型

面板必须围绕用户动作组织，而不是围绕内部对象组织。

主要动作：

1. 判断当前路线图环节是否可以推进。
2. 看清不能推进的阻断原因。
3. 直接触发下一步：补验证、继续修正、确认推进或查看证据。
4. 扫描哪些微观循环支撑或阻断当前判断。
5. 进入证据下钻。
6. 需要时切换到项目级回溯轨迹。

不应把主界面做成：

- Agent run 列表。
- 原始日志列表。
- JSON digest 浏览器。
- 模块依赖图中心。
- 多 Agent 角色聊天室。

## 信息层级

### 第一层：路线图环节推进判定

在每个路线图环节里展示微观循环聚合结果：

```text
当前环节：反馈与规模化
状态：还不能完成
原因：1 个完成标准缺少验证证据
下一步：补齐验证后再完成环节
完成标准覆盖：3 / 4
微观循环：6 个，4 个已闭环，1 个待验证，1 个需要确认
```

这层回答“当前能不能推进、为什么、下一步做什么”。

### 第二层：微观循环卡片

每张卡片展示一个意图如何走到当前结果。

推荐结构：

```text
意图：侧边栏需要能停止异常 Solo 对话
判断：复用现有停止链路，不新增第二套控制
动作：改造侧边栏状态与停止消息处理
证据：webview regression test 通过；触碰 3 个文件
结果：已闭环
归因：支撑“反馈与规模化”环节的异常对话控制标准
```

卡片状态必须清晰：

- 已闭环。
- 已实施，待验证。
- 验证失败。
- 部分完成。
- 发生偏离。
- 已生成下一轮。
- 需要确认。

卡片应紧凑，不要把六阶段做成六个大 Tab。六阶段是结构，不是前台负担。

### 第三层：证据下钻

用户需要时再下钻：

- 关联 Agent 对话。
- 关联 run digest。
- 关联 commit 或 diff。
- 关键文件。
- 测试命令和结果。
- UI 截图或人工验收。
- 设计对标。
- 未覆盖项。

证据入口应服务判断，不应把用户推入原始日志海洋。

## 面板布局建议

### 推进模式布局

默认布局应从推进判定开始：

```text
[环节推进判定条]
[完成标准覆盖情况]

[微观循环列表]        [选中循环证据抽屉]
- 已闭环
- 待验证
- 验证失败
- 需要确认
```

优势：用户先得到能否推进的结论，再选择是否下钻证据或查看完整轨迹。

### 回溯模式布局

提供项目级执行轨迹总览。

```text
最近塑造的能力
反复返工的区域
证据不足的区域
验证失败后产生的新循环
被多个循环共同塑造的模块
即将影响路线图推进的缺口
```

优势：用户能理解项目是怎样被 Agent 一轮轮塑造成当前状态。

## 状态文案

推荐使用用户能直接行动的文案：

| 内部状态 | 用户可见表达 |
| --- | --- |
| `closed` | 已闭环 |
| `implemented_unverified` | 已实施，待验证 |
| `verified_failed` | 验证失败 |
| `partial` | 部分完成 |
| `deviated` | 偏离原意 |
| `spawned_followup` | 已进入下一轮 |
| `needs_user_confirmation` | 需要你确认 |
| `abandoned` | 已放弃 |

按钮文案应围绕动作：

- `继续修正`
- `补充验证`
- `查看证据`
- `确认推进`
- `生成下一轮`
- `标记放弃`

避免：

- `Open digest`
- `Inspect orchestration`
- `Verifier output`
- `Trace schema`
- `Routing decision`

## 路线图自动推进表达

当执行轨迹足以支撑环节完成时，面板可以显示：

```text
这个环节的 4 项完成标准已有闭环证据，可以推进到下一环节。
```

当不能推进时，必须明确下一步：

```text
还不能完成：核心路径已实施，但缺少真实渲染验证。建议先补充验证。
```

用户不应自己从日志里推断为什么卡住。

## 评分与闸门展示

评分制度服务于状态解释，不应成为主界面的负担。

主界面只显示：

- 当前状态。
- 阻断原因。
- 下一步动作。
- 是否可以推进路线图。

示例：

```text
状态：已实施，待验证
原因：计划要求运行 webview regression test，但本轮没有验证记录。
下一步：补充验证
```

下钻层才显示评分细节：

```text
Planner 8/9
Builder 6/12
Verifier 9/11
硬闸门：verificationExecuted = false
最终状态：implemented_unverified
```

主界面禁止显示抽象总分，例如“微循环健康度 85”。如果硬闸门失败，总分不能掩盖不能推进的事实。

## 人在回路的关键介入点

面板应把六阶段中最容易偏航的位置显性化：

- 意图：Agent 是否理解错了。
- 判断：方案是否偏离目标或扩大范围。
- 动作：是否做了与目标无关的改动。
- 证据：是否缺少必要验证。
- 结果：是否过度宣称完成。
- 归因：是否错误推动路线图。

这些介入点应该能直接触发下一轮微观循环，而不是只留下评论。

## 面板不展示什么

不在主界面展示：

- 完整 prompt。
- 完整终端日志。
- 原始 JSON schema。
- 多 Agent 内部争论。
- embedding、graph、digest、score 等内部治理对象。
- 方法论长篇解释。

这些可以作为审计层存在，但不能成为用户完成动作的前台负担。

## 用户可见事实与内部机制

执行轨迹面板只默认展示能帮助用户判断和行动的事实。评分、索引、状态机和对象模型保留在内部，只有用户主动审计时才逐层展开。

### 用户默认可见

用户应该看到：

- 当前环节能不能完成。
- 不能完成时的阻断原因。
- 下一步动作。
- 完成标准覆盖情况。
- 微循环状态：已闭环、已实施待验证、验证失败、偏离原意、需要确认、已进入下一轮。
- 六阶段摘要：意图、判断、动作、证据、结果、归因。
- 证据入口：关键文件、测试命令、测试结果、diff 摘要、关联 Agent run、截图、人工验收、commit。

这些内容要用用户语言表达，不能要求用户理解内部字段。

### 内部默认保留

以下内容不应默认出现在主界面：

- 完整 JSON trace。
- `traces.jsonl`。
- SQLite 索引结构。
- scoring schema。
- Planner / Builder / Verifier 原始输出。
- H/I/J 原始判定字段。
- 五看三定完整结构。
- Plugin gates 原始布尔值。
- embedding、Execution Graph、检索分数。
- Agent session 路由和角色切换细节。
- 内部状态机转移全量字段。

### 内部机制的用户化翻译

内部字段可以被翻译成用户能行动的解释：

| 内部机制 | 用户可见表达 |
| --- | --- |
| `verificationExecuted=false` | 缺少验证证据 |
| `verificationPassed=false` | 验证失败 |
| `hijIntentAligned=false` | 实现偏离原始目标 |
| `plannerDecisionJustified=false` | 计划依据不足，需要重新规划 |
| `roadmapAttributionValid=false` | 这轮结果不能支撑当前路线图环节 |
| `scopeRespected=false` | 改动超出本轮范围 |
| `needs_user_confirmation` | 需要你确认后才能继续 |

### 展示层级

推荐层级：

```text
主界面：推进结论 + 下一步动作
微循环卡片：六阶段摘要 + 状态
证据抽屉：关键证据 + 简化评分原因
审计模式：完整 gates / scoring / H-I-J / 五看三定
文件层：完整 JSON / JSONL / SQLite
```

审计模式可以给高级用户和排障场景，但不能作为默认体验。

## 与旧微观可见性工件的关系

旧的模块设计、实现总结、设计对标、模块拓扑和健康报告仍有价值，但它们不是面板主语。

它们应作为证据层进入微观循环：

- 模块设计用于支撑判断阶段。
- 实现总结用于支撑动作阶段。
- 设计对标用于支撑证据和结果阶段。
- 模块拓扑用于支撑影响范围。
- 健康报告用于发现下一轮微观循环。

面板主语始终是：

```text
意图如何变成项目事实。
```

## 验收标准

- 用户不用读 diff，也能知道一个路线图环节为什么能或不能完成。
- 每个微观循环都能看到意图、判断、动作、证据、结果、归因。
- 没有证据的循环不会显示为已闭环。
- 失败、偏离、部分完成能直接生成下一轮动作。
- 路线图推进理由来自闭环证据，而不是 Agent 自称完成。
- 主界面不要求用户理解 Agent 角色、digest schema、执行图或内部路由。
