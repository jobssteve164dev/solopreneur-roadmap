# Issue 面板设计 - 快速入门

这是一份给设计实现 Agent 的快速指南。详细的哲学论述见 `issue_panel_design_philosophy.zh.md`。

## 一句话总结

**Issue 面板是 SoloMap 的输入补全层，让项目对来自用户、团队、自己的多源声音进行异步决策和永久记录。**

## Issue 面板要解决的三个问题

### 问题 1：项目真实面临什么？
- **现状**：Roadmap 说"计划是这样"，但实际执行中会有意外（Bug、需求、团队想法）
- **解决**：Issue 面板让用户看到项目的 Bug、Feature 需求、Tech Debt、讨论的全景
- **UI 呈现**：侧边栏显示"Open Issues (12)"，分类为"🔴 Bug (3) / 🟡 Feature (7) / 🟢 Discussion (2)"

### 问题 2：为什么改变了计划？
- **现状**：修改了路线图，但"为什么"没有记录
- **解决**：Issue 评论链记录决策过程，从"问题发现"到"采取方案"到"为什么不选其他方案"
- **Agent 利用**：启动 Build 环节时，Agent 自动读取关联 Issue 的评论，理解修复的真实背景

### 问题 3：这个月学到了什么？
- **现状**：Improve 阶段无数据，不知道上个月花了多少时间处理"计划外"的事
- **解决**：Issue 历史自动生成统计，告诉 Agent"这个月有 30% 的时间用在了 Bug 修复"
- **Agent 利用**：Improve 阶段读取 Issue 统计数据，为下月路线图提供数据驱动的建议

## Issue 面板的核心职责

| 职责 | 具体实现 | 受众 |
|------|--------|------|
| 1. **可见化** | 侧边栏显示 Open Issues，按标签分类 | 用户（快速看项目状态） |
| 2. **上下文注入** | Issue 评论链自动打包给 Agent | Agent（理解修复的真实背景） |
| 3. **数据聚合** | 统计 Issue 历史，生成月度报告 | Agent + 用户（学习和改进） |

## 不要做的事（消除常见误解）

❌ 不是"任务追踪"（那是 Roadmap 的职责）
❌ 不是"侧边栏新增一个标签页可以任意点击"（会变成信息竞争者）
❌ 不是"一键指派给 Agent"（会增加决策瓶颈）
❌ 不是"完全幕后、用户看不见"（输入应该可见、可讨论）

## MVP 范围

### 第一版：侧边栏 Issue 面板

```
+----------------------------------+
| GitHub Issues                    |
| Open Issues (12)                 |
|                                  |
| 🔴 Bug (3)                       |
|   • 页面加载超慢 (#32)            |
|   • 登录表单校验 (#35)            |
|   • 缺少错误提示 (#38)            |
|                                  |
| 🟡 Feature (7)                   |
|   • 支持暗黑模式 (#41) [👍 28]    |
|   • 导出为 PDF (#42) [👍 15]     |
|   ...                            |
|                                  |
| 🟢 Discussion (2)                |
|   • 应该支持多语言吗？ (#51)       |
|   • API 设计评议 (#52)            |
+----------------------------------+
```

**MVP 要做的事**：
1. 用 `gh issue list` 拉取当前项目的 Open Issues
2. 按标签分类显示（bug / feature-request / discussion 等）
3. 显示优先级标签（P0 / P1 / P2）
4. 点击 Issue 卡片可展开看：标题、描述、最近 3 条评论预览
5. 显示用户投票数（👍 计数）

**不在 MVP 里**：
- 不支持创建新 Issue（用户直接在 GitHub 上创建）
- 不支持评论 Issue（用户在 GitHub 上评论）
- 不支持"一键指派给 Agent"（可后期加）

### 第二版：Agent 上下文注入

启动 Build 环节 Agent 时，自动执行：
1. 扫描关联的 Bug Issue（通过文件路径匹配或标签）
2. 获取 Issue 的完整评论链
3. 打包成 Prompt，示例：

```
## 当前环节关联的 GitHub Issues

### Issue #32: 页面加载超过 5 秒
优先级：P0（影响 40% 用户）

描述：用户打开首页需要等待 5 秒

讨论关键点：
1. 开发: "测试了，服务器端超时了"
2. 架构: "看起来是数据库 N+1 问题"
3. 产品: "影响了 58% 的请求，这是 P0"
4. 决定: 修改路线图，本周优先处理

预期方案：重构数据库查询逻辑
完成时间：2-3 天
```

### 第三版：Improve 阶段数据聚合

Improve 环节启动时，自动生成：

```
## 上个月 Issue 统计

总计：15 个 Issue（状态分布）
- 已关闭：8 个
- 待处理：7 个

类型分布：
- Bug (33%)：3 个，平均 1.2 天解决
- Feature 需求 (47%)：7 个，投票最多前 3 个
- Tech Debt (20%)：5 个，积累需要关注

建议：
1. 下月规划应预留 20% 缓冲时间处理 Bug
2. 优先开发投票最多的 Feature
3. 安排一个 Tech Debt 环节
```

## 设计检查单

- [ ] Issue 数据来自 GitHub（不手工维护）
- [ ] 标签系统规范化（bug / feature-request / tech-debt / discussion / documentation）
- [ ] 用户可见但不强行交互（可看，但不必须点）
- [ ] Agent 能自动读取 Issue 上下文
- [ ] Issue 历史能自动生成月度报告
- [ ] 支持离线（Issue 数据本地缓存）

## 后续讨论点

1. **标签系统规范**：哪些标签应该被系统识别和聚合？
2. **优先级评估**：如何自动判断 Issue 的优先级？
3. **AI 自动分类**：能否用 AI 自动分类 Issue 的类型？
4. **团队协作**：多人项目中，Issue 的权限模型是什么？
5. **数据隐私**：本地缓存多少 Issue 数据？
