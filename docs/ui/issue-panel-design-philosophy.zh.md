# SoloMap Issue 面板设计哲学

## 核心洞察

**Issue 不是任务管理工具，而是项目异步决策的永久记录。** SoloMap 的 Issue 面板不是为了"管理待办"，而是为了**建立从"问题发现"到"团队共识"到"行动执行"到"学习反思"的完整决策链**。

当前 SoloMap 的 solo 和 roadmap 只解决了**输出问题**（我要做什么、怎么做），Issue 面板应该补全**输入问题**（我为什么要改变计划、用户和团队真实在想什么）。

---

## GitHub Issue 的设计初心

### Issue 是"对话空间"，不是"TODO 列表"

GitHub 设计 Issue 的根本目的：**建立项目决策的异步、可追溯、多角色参与的讨论机制**。

一个 GitHub Issue 的完整生命周期：

```
发现问题（用户/团队/自己）
    ↓
打开 Issue：记录问题背景、现象、期望行为
    ↓
异步讨论：不同时区、不同角色的人逐步加入
    • 用户补充复现步骤
    • 开发者分析根因
    • 产品经理评估优先级
    • 维护者决定是否处理
    ↓
达成共识：整个团队对这个问题和方案有了共同理解
    ↓
执行（或决定不执行）
    ↓
验证完成
    ↓
关闭 Issue：决策理由、采取方案、为什么拒绝其他方案 都被记录
    ↓
永久记录：三年后仍可追溯为什么做了这个改动
```

### Issue 的核心特性

1. **异步性**：不要求实时对话，支持不同节奏的参与
2. **可追溯性**：完整的讨论过程保留，决策理由永不丢失
3. **多角色性**：用户、开发者、产品、维护者都能发声
4. **集体智慧**：问题的最终解决是多个人想法碰撞的结果，而非单一决定

## SoloMap 当前的"输出导向"瓶颈

### 现有工具的职责

| 工具 | 职责 | 特点 | 缺陷 |
|------|------|------|------|
| **Roadmap** | 规划 → 执行计划 | 自上而下的路线图，确定性强 | 假设计划完美，无法应对意外 |
| **Solo** | 临时对话 | 灵活处理即时问题 | 散点记录，难以形成系统的决策链 |
| **Step Memory** | 环节记忆 | 固化"按路线图执行"的思路 | 没有记录"为什么改变了计划"的理由 |

### 缺失的问题

现有工具都假设了一个理想场景：

```
管理者规划路线图 → Agent 按计划执行 → 完成
```

但独立开发者的真实场景是：

```
规划路线图
  ↓
执行到第二周
  ↓
用户报告紧急 Bug（GitHub Issue）
  ↓
团队讨论：现在修复 vs 继续按计划（Issue 评论）
  ↓
决定打破路线图，优先处理 Bug
  ↓
修复完成，Issue 关闭
  ↓
下个月路线图调整时发现：
    - 计划执行率：60%
    - 意外 Bug 修复：30%  
    - 学习反馈：10%
    ↓
这些数据来自哪？应该来自 Issue 历史
    ↓
Improve 决策：下版本需要预留 20% 缓冲时间
```

**问题**：现在的 SoloMap 工作流无法系统化地记录和利用这些"计划之外的真实发生"。

## Issue 在 SoloMap 中的三个层次职责

### 层次 1：输入汇聚 - Issue 作为声音入口

**问题**：项目面临哪些不同维度的声音和压力？

**多源声音的汇聚**：

```
不同来源的声音：
  ├─ 外部用户的 Bug 报告 → Issue + 标签 bug
  ├─ 外部用户的需求 → Issue + 标签 feature-request
  ├─ 团队成员的想法 → Issue + 标签 discussion
  ├─ 产品经理的反馈 → Issue + 标签 product
  ├─ 自己发现的技术债 → Issue + 标签 tech-debt
  └─ 架构师的设计考虑 → Issue + 标签 architecture
       ↓
   GitHub Issue 成为统一的"声音汇聚点"
       ↓
   所有人都可以看到项目真实面临的问题全景
```

**对 SoloMap 的意义**：

- 侧边栏 Issue 面板按**标签和紧急度**分类显示
- 让用户一眼看到"项目正在被哪些问题困扰"
- Build Issue（Bug）、Feature Issue、Tech Debt、Discussion 分开但相关联

**独立开发者的特殊价值**：
- 自己既是开发者，也是产品经理，也是团队
- Issue 可以成为"自我对话"的空间（给自己留笔记、思考问题）
- 对于想要外部反馈的项目，Issue 成为用户和开发者对话的公共广场

### 层次 2：决策链 - Issue 作为"为什么"的记录

**问题**：为什么采取了这个方案？有没有其他可能性？

**一个 Issue 的完整决策链**：

```
Issue 标题：页面加载超过 5 秒导致用户流失

描述：
  背景：用户反馈打开首页需要等待 5 秒
  当前行为：加载时间过长
  期望行为：2 秒内加载完成
  影响：影响 30% 的日活用户

评论历史：
  1. 用户提交（附带截图）
  2. 开发者: "我测试了，服务器端可能超时了"
  3. 架构师: "看起来是数据库查询 N+1 问题"
  4. 产品: "我们有多少用户受影响？如果不是多数，可以延后"
  5. 分析: "根据日志，58% 的请求超时，这是 P0"
  6. 开发者: "需要重构数据库查询，大概 3 天"
  7. 产品: "这打乱了本周的 AB 测试计划，但必须做"
  8. 决定: 修改路线图，本周优先处理这个

结论记录：
  采取方案：重构数据库查询逻辑
  为什么这个方案：最小化风险、影响最小
  为什么不用缓存：缓存会导致数据不一致问题
  为什么不延后：影响了大多数用户
  完成时间：3 天
```

**这是什么？**
- 不是技术实现细节（那是 PR 和代码）
- 而是**为什么做这个决定的集体记忆**
- 任何新加入的人都能看到"这个改动背后的故事"

**对 SoloMap 的意义**：

- 当 Agent 要解决一个 Issue 时，不仅读取标题，而要读取**整个评论链**
- Agent 能理解"这个修复的真实背景和约束"，而不是盲目按技术最优方案做
- 在 Improve 阶段，Agent 能看到"哪些 Issue 反映了真实用户需求"

### 层次 3：优先级协商 - Issue 作为时间管理的记录

**问题**：计划和现实的偏差是如何产生的？我们学到了什么？

**路线图 vs Issue 历史的对话**：

```
预期（Roadmap）：
  Week 1-2: 实现功能 A
  Week 3-4: 实现功能 B
  Week 5-6: 性能优化

实际发生：
  Week 1: 照常
  Week 2: 用户报告 5 个关键 Bug（Issue #101-105）
  
  决策对话在 Issue 里：
    Issue #103: "这个 Bug 影响 40% 用户"
    评论: "我们要现在修吗？还是继续做功能？"
    产品: "现在修，否则流失用户"
    开发: "需要 3 天"
    最后: 推迟功能 A，优先修 Bug
  
  Week 3: 修完 Bug，补做功能 A 的 50%
  Week 4: 完成功能 A，开始功能 B
  ... 整个计划偏移了 1 周

月底回顾数据：
  计划时间 / 实际时间：
    • 功能 A：预期 2 周 → 实际 2.5 周
    • Bug 修复（未计划）：实际 0.5 周
    • 其他：预期 2 周 → 实际 1.5 周

  总结：有 30% 的时间用在了"计划外"
```

**这个数据怎么来的？**
- 不是人工估算，而是通过 **Issue 的打开/关闭时间线**
- 通过 **Issue 标签**（bug、feature、tech-debt）分类计算
- 通过 **Issue 的优先级标签**判断为什么打破了计划

**对 SoloMap 的意义**：

- Issue 历史变成了**项目运行状态的审计日志**
- Improve 阶段时，Agent 能看到：
  ```
  上个月开了 15 个 Issue，其中：
  • 5 个 Bug（都因优先级高而打破计划）
  • 7 个 Feature 需求（最多投票的 3 个）
  • 3 个 Tech Debt（积累）
  
  建议：下个月规划时，应该预留 20% 缓冲时间
  ```

## Issue 在 SoloMap 中的具体职责

### 不应该做的事（消除误解）

1. **不是"任务追踪"**：Issue 不是 TODO 列表，不应该用来管理"做完了吗"
   - 任务追踪的职责 = Roadmap（已有）

2. **不是"展示窗口"**：Issue 面板不是"侧边栏新增一个标签页"
   - 如果设计成"用户可点击的面板"供选择，就变成了信息竞争者

3. **不是"快速指派按钮"**：不应该是"点击 Issue → 一键转给 Agent"
   - 这样会形成新的决策瓶颈（"是直接修复还是升级为环节"）

4. **不是"隐形管道"**：也不应该是完全幕后的、用户看不见的
   - 输入既然是多源的，就应该可见、可讨论、被尊重

### 应该做的事（核心职责）

1. **可见的输入多源汇聚**：
   - 侧边栏显示项目当前面临的 Issue 全景
   - 按标签和优先级分类，让用户快速理解"项目现在的状态"
   - 支持筛选：只看 Bug、只看用户需求、只看团队讨论

2. **上下文注入给 Agent**：
   - 当启动 Build 环节 Agent 时，自动分析关联的 Bug Issue
   - 把 Issue 的**完整评论链**打包给 Agent，不仅仅是标题
   - Agent 能理解"这个修复的真实背景和用户影响"

3. **决策记录的永久保留**：
   - Issue 评论链成为"为什么做这个决定"的审计日志
   - 支持 Issue 和路线图的关联显示：
     ```
     Roadmap 环节 A
       ├─ 关联的 Issue #32（这个 Issue 改变了计划）
       ├─ 关联的 Issue #35（在处理本环节时发现的问题）
       └─ 相关反馈链
     ```

4. **学习数据的自动聚合**：
   - Improve 阶段时，自动生成：
     ```
     上个月 Issue 统计：
     • 类型分布：Bug (33%) / Feature (47%) / Tech Debt (20%)
     • 优先级：P0 (2) / P1 (8) / P2 (15)
     • 平均解决时间：Bug (1.2 天) / Feature (讨论中)
     • 用户投票最多的 3 个需求
     ```
   - 这些数据自动成为"下月规划建议"的输入

## Issue 面板与 SoloMap 其他组件的关系

### Issue 面板 × Roadmap

```
Roadmap（自上而下的计划）
    ↓
执行中遇到真实情况（Issue 打开）
    ↓
Issue 评论中形成共识（是否改变计划）
    ↓
如果改变计划 → Issue 成为"路线图调整的理由记录"
    ↓
Improve 阶段读取 Issue 历史 → 数据驱动的下月规划
```

**关键点**：Issue 不是"打破路线图的敌人"，而是"路线图持续改进的数据源"

### Issue 面板 × Solo

```
Solo（临时对话，可以是任何话题）
    ↓
如果是系统性的、会重复出现的问题
    ↓
应该升级为 Issue（建立异步讨论空间）
    ↓
Issue 评论可能后续引入其他人
    ↓
最终形成团队共识
```

**关键点**：Issue 是 Solo 的升级版，当"单次讨论"变成"需要多角色参与的决策"时

### Issue 面板 × Step Memory

```
Step Memory（某个环节完成后的交接记录）
    ↓
当这个环节是因为 Issue 而打破路线图时
    ↓
Step Memory 应该链接到对应的 Issue（记录"为什么改变了"）
    ↓
下个环节启动时可以读取这个 Issue 历史
```

**关键点**：Step Memory 记录"做了什么"，Issue 记录"为什么这样做"

## 设计原则

### 原则 1：可见性优于隐形

**问题**：Issue 数据应该是"幕后管道"还是"可见的对话空间"？

**答案**：都是，但不是互相竞争的。

- **可见部分**：侧边栏 Issue 面板让用户看到项目真实状态
- **幕后部分**：Issue 数据自动打包给 Agent，用户不需要手动操作

### 原则 2：多源输入优于单一决策

**问题**：Issue 应该支持谁的声音？

**答案**：所有角色
- 外部用户的反馈
- 团队成员的想法
- 自己的自我对话
- 产品、开发、架构的不同观点

### 原则 3：异步协作优于实时协调

**问题**：如何在分布式团队中做决策？

**答案**：通过 Issue 评论链
- 不要求所有人同时在线
- 允许不同时区的人按自己的节奏参与
- 最终共识被永久记录

### 原则 4：历史追溯优于即时优化

**问题**：Issue 是否应该为了"现在方便"而损失历史信息？

**答案**：否。Issue 的价值在于永久记录，为未来学习服务。

## 实现起点

### 第一步：理解 GitHub Issue API

对接 GitHub Issue 需要理解：
1. Issue 的字段模型（title, body, labels, state, comments）
2. Issue 事件流（opened, edited, commented, closed）
3. 标签系统的使用（如何分类不同类型的 Issue）
4. 权限模型（谁能打开、评论、关闭 Issue）

### 第二步：侧边栏 Issue 面板的 MVP

**目标**：让用户看到项目的 Issue 全景

```
侧边栏：
├─ 项目选择器
├─ Roadmap 视图
├─ Solo 对话卡片
├─ [NEW] GitHub Issues 面板
│  ├─ Open Issues (12)
│  │  ├─ 🔴 Bug (3)
│  │  ├─ 🟡 Feature Request (7)
│  │  └─ 🟢 Discussion (2)
│  └─ Issue 详情（点击展开）
│     ├─ Issue 标题和描述
│     ├─ 优先级标签
│     ├─ 最近 3 条评论预览
│     └─ "用 Agent 开始解决" 或 "转为路线图环节"
```

**关键设计决策**：
- 不是"侧边栏的新标签页"，而是现有项目视图的一个 section
- 显示数字摘要（有多少个 Bug、多少个需求），让用户快速扫一眼
- 支持按标签快速筛选，但默认显示全部

### 第三步：Agent 的 Issue 上下文注入

**当 Agent 启动 Build 环节时**：
1. 系统识别关联的 Bug Issue（通过文件路径、关键词匹配）
2. 自动获取这些 Issue 的完整评论链
3. 打包成 Prompt 注入：
   ```
   ## 当前环节关联的 GitHub Issues
   
   Issue #32: 页面加载超过 5 秒
   - 优先级：P0（影响 40% 用户）
   - 讨论关键点：数据库 N+1 问题
   - 预期修复时间：2-3 天
   - 用户反馈：已在生产环境复现
   ```

### 第四步：Issue 数据的 Improve 聚合

**当进入 Improve 阶段时**：
1. 系统统计过去 1 个月的 Issue 数据
2. 生成建议信息给 Agent：
   ```
   ## Learn 阶段反馈总结
   
   过去 1 个月开了 15 个 Issue：
   • Bug（33%，3 个）：平均 1.2 天解决
   • Feature 需求（47%，7 个）：最多投票前 3 个
   • Tech Debt（20%，5 个）：积累需要关注
   
   建议：下个月路线图应该：
   1. 预留 20% 缓冲时间处理 Bug
   2. 优先开发投票数最多的 3 个需求
   3. 安排一个 Tech Debt 环节
   ```

## 常见问题

### Q: 这样的话，Issue 会不会变成"任意一个想法都往 GitHub 上扔"？

**A**: 这是特性，不是 bug。
- 好的 Issue 会被自然筛选（收到评论、获得标签、被优先处理）
- 垃圾 Issue 会自然沉没（无人评论、自动关闭）
- SoloMap 通过标签过滤可以聚焦有价值的 Issue

### Q: 独立开发者用得上 Issue 吗？不是只有团队项目才需要？

**A**: Issue 对独立开发者的价值反而更大。
- 用 Issue 进行自我对话和自我管理
- 记录自己的想法演变过程
- 一年后回顾时知道"为什么做了这个决定"
- 如果后来有他人加入，Issue 历史就是最好的文档

### Q: Issue 面板和 Roadmap 的优先级矛盾怎么处理？

**A**: Issue 不是和 Roadmap 竞争优先级，而是提供**真实数据**支持优先级重新评估。
- Roadmap 代表"计划"
- Issue 代表"现实"
- 二者的差异就是决策的输入

### Q: 会不会让工作流变得更复杂？

**A**: 短期看起来是加了一层，但实际上是：
- 之前的"意外改变计划"和"为什么改变"都没有记录
- 现在通过 Issue 系统化地记录
- 长期看会大幅降低复杂度（因为历史是清晰的）

## 后续设计工作

1. **Issue 标签系统的规范**：
   - 标准标签：bug, feature-request, tech-debt, discussion, documentation
   - 优先级标签：P0, P1, P2
   - 类别标签：对应不同的 Agent 能力或 Roadmap 类别

2. **Issue 面板的 UI/UX**：
   - 侧边栏的呈现方式（展开/折叠/筛选）
   - Issue 卡片的信息层级
   - Issue 评论链的阅读体验

3. **Agent 与 Issue 的交互**：
   - Issue 上下文的自动打包格式
   - Agent 完成后自动评论和关闭 Issue 的时机
   - Issue 链接和 Commit Message 的关联

4. **Issue 数据的 Improve 聚合**：
   - 统计维度（按标签、按优先级、按时间）
   - 自动生成的建议格式
   - Issue 历史和路线图调整的关联展示

5. **权限和协作模型**：
   - 本地开发者如何授权 SoloMap 访问 GitHub
   - 团队项目中不同角色的权限
   - 隐私和数据安全的考虑
