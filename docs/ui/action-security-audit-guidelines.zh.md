# Action 安全审计设计指南

## 目标

安全审计融入项目卡片的 Action 判断，而不是新增独立审计卡片或安全控制台。

项目卡片仍然只回答：

```text
现在最该做什么？
为什么是它？
点哪里继续？
```

安全信号只在改变下一步判断或帮助用户减少风险时出现。

## 信号来源

第一版接入三类信号：

- GitHub Dependabot open alerts
- GitHub Code scanning open alerts
- 项目基座中的 `security.yml` 本地/CI 安全检查入口

Secret scanning 第一版不作为稳定计数源。它可以在后续作为权限状态或 GitHub 侧提示出现，但不能让首版 Action 依赖敏感权限或不同 GitHub 计划下不稳定的能力。

## 优先级

只有 open 的 `critical` / `high` 安全风险可以覆盖当前 Action。

中低风险只进入展开态背景，不覆盖路线图下一步。

安全高危优先于发布检查失败。发布检查失败优先于普通路线图推进。

基座缺失只提醒，不参与 P0 排序，不阻断推进。

## 收起态

收起态只显示用户能立即判断的短状态：

```text
Action · 安全需处理 1
Action · 交付需处理
Action · 项目基座缺失 2
Action · 最近检查正常
```

不要显示 API、权限、workflow 名称、字段名、扫描器实现或长列表。

## 展开态

展开态可以显示来源，但仍然服务下一步动作：

- 安全审计：最高风险数量、来源、标题、严重度、链接
- 最近检查：失败 workflow 摘要
- 项目基座：缺失文件
- 动作：刷新状态、打开失败 Run、交给 Agent 修安全风险、补齐项目基座

展开态不是 GitHub Security 控制台，不展示完整告警管理、dismiss、severity 策略、权限配置或扫描规则说明。

## 本地扫描边界

本地扫描不在打开侧边栏时自动运行。

本地安全审计通过项目基座的 `security.yml` 和 Agent 动作触发。用户点击修复或运行审计时，Agent 根据项目技术栈执行最窄的安全审计命令。

这样避免侧边栏打开变慢、误报打断用户、或让用户理解包管理器差异。

## 失败与无权限

GitHub 安全 API 无权限、未启用或不可用时，Action 只显示未知或不显示安全计数。

无权限不能阻断项目推进。

如果用户主动刷新，刷新结果可以提示安全状态未知，但不要把 GitHub 权限问题变成用户必须先完成的主任务。

## Agent 动作

“交给 Agent 修复安全风险”必须要求 Agent 先确认告警仍然成立，再修根因并验证。

禁止只隐藏告警、绕过检查、降低阈值或关闭安全 workflow 来制造通过。

“补齐项目基座”只能创建缺失文件，不能覆盖已有文件，不能顺手扩展成大而全的文档体系。
