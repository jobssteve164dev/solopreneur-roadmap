# 项目生长图：产品判断与优化方向

## 这份文档解决什么判断

这份文档固定项目生长图下一阶段应优化什么，以及如何判断它是否真的帮助用户理解和推进项目。

核心判断是：**项目生长图不缺更多扫描结果，当前最需要的是把已有事实组织成“项目长成了什么、哪里没有长成、下一步做什么”。**

它不是路线图的另一种画法。路线图表达计划，项目生长图表达现实，并让用户看见计划与现实之间的差距。

## 当前实现审计

### 已经成立的基础

以下结论可由当前实现直接观察到：

- `src/projectGrowth.ts` 已经聚合文件结构、Git 变化、依赖关系、路线图环节、Agent 运行索引和测试信号。
- `ProjectGrowthViewModel` 已经提供项目方向、能力健康、生长焦点、建议动作、模块关系、历史快照和前后差异。
- 模块聚合会排除生成物和运行材料，并尽量把文件归并为可复用的源码模块，而不是把文件树原样搬到前台。
- `src/extension.ts` 先打开本地页面，再异步读取或刷新快照；已有缓存时优先展示缓存，符合本地优先入口的响应边界。
- `test/project-growth.test.js` 已覆盖扫描、模块唯一性、能力映射、依赖边、测试关系、快照持久化和历史差异。

因此，项目生长图已经不是概念原型。它具备继续收敛为用户产品的真实数据基础。

### 2026-07 审计发现的产品断层

#### 1. 页面主语仍然偏向代码模块

当前首屏顺序是：

1. 项目目的与路线图进度。
2. 阶段旅程。
3. 模块信号矩阵。
4. 优先动作。
5. 文件、代码行、模块、能力、依赖包和信号统计。
6. 架构关系、结构缺口、关联能力和历史快照。

这使用户先看到“项目包含哪些代码块”，再自己推断“这些代码意味着什么”。模块面积还以代码行数为主要权重，视觉上容易把“大文件”误读为“重要能力”。

更合适的阅读顺序应是：

1. 这个项目现在处于什么现实状态。
2. 哪项产品能力已经成形、正在生长或没有证据。
3. 当前最值得执行的一个动作。
4. 该判断由哪些模块、运行和验证证据支撑。
5. 需要时再下钻代码结构与历史。

#### 2. 已有的高价值视图没有进入最终页面

审计时，`src/projectGrowthWebview.ts` 已生成 `capabilityHealthHtml` 和 `focusAreasHtml`，也读取了 `insight.headline`、`insight.healthLabel`、`insight.focusLabel` 与 `insight.evidenceLabel`，但这些内容没有插入最终 HTML。

这意味着后端已经完成的“能力是否长成”“哪里最值得看”“判断依据是什么”，没有成为用户真正看到的主视图。当前页面因此更像结构健康面板，而不是项目生长判断工具。

#### 3. 建议只有陈述，没有形成动作闭环

“优先行动”卡片目前是静态信息，没有直接进入对应路线图环节、查看证据或继续 Agent 对话的动作。用户读完后仍需自己返回路线图寻找目标。

项目生长图只有在建议能落到既有入口时才闭环。它不需要创造新的任务系统，但应允许用户：

- 打开对应路线图环节。
- 查看支撑该判断的模块和验证证据。
- 对“缺归属”的代码选择关联现有环节或暂时忽略。
- 对“缺验证”的能力从现有 Agent 入口继续推进。

#### 4. “生长”仍主要由存量与快照差异表达

当前实现能展示文件数、代码行、模块数、信号数和两次快照差异，但这些指标不能单独说明产品是否变得更完整。

“代码行增加”可能是返工，“文件减少”可能是收口。更有意义的变化是：

- 某项能力从“有代码”变为“有验证”。
- 某个环节从“计划中”变为“已有真实落点”。
- 某个反复失败区域完成收口。
- 新增代码获得明确产品归属。
- 发布或用户反馈开始验证能力价值。

后续演化视图应优先展示这些状态变化，再把文件和代码行差异作为证据。

#### 5. 页面信息密度超过了用户的一次判断需求

当前页面同时提供阶段、模块矩阵、动作、六项统计、快照差异、架构图、结构缺口、关联能力和历史。内容都可能有价值，但全部平铺会让用户难以判断“此刻该先看哪里”。

建议保留三级信息层次：

- 默认层：一句现状判断、能力生长状态、一个首要动作。
- 证据层：相关模块、验证、运行与路线图归属。
- 诊断层：完整关系图、统计、结构缺口和快照历史。

诊断层默认折叠，不应与行动层争夺首屏注意力。

## 优化优先级

### P0：让能力状态成为首屏主体

直接复用现有 `capabilityHealth`、`focusAreas` 和 `insight` 数据，不先扩充扫描器。

首屏建议由三部分组成：

- **项目现在怎样**：用一句话表达已成形能力、正在推进能力和主要缺口。
- **能力生长带**：按路线图阶段展示能力卡片，状态只保留已成形、正在生长、待验证、需收口、未落地五种用户语言。
- **现在做什么**：只突出最高优先级动作，并提供进入现有路线图环节的按钮。

模块矩阵下移为“这些判断落在哪些代码区域”。

### P1：把建议连接到既有推进入口

建议动作必须携带稳定的路线图环节身份或模块身份。点击后复用路线图和 Agent 对话的现有入口，不新增平行任务模型。

完成标准：

- 用户从生长图最多一次点击即可到达建议对应的环节。
- 返回生长图后，刚才查看的能力与展开状态仍被保留。
- 刷新快照只更新事实，不重置用户当前选择。

### P1：把时间线升级为能力状态迁移

历史不再优先罗列每次扫描的文件和代码行数量，而应展示：

- 哪项能力状态发生变化。
- 新增或消失了什么验证证据。
- 哪个风险已经解除或持续存在。
- 哪次 Agent 运行或交付事件促成了变化。

如果没有能力级变化，才退回展示结构差异。

### P2：允许用户校正低置信度归类

自动归类不可能永远正确。只在归类置信度低、且错误会影响建议时提供轻量校正：

- “这块代码属于哪项现有能力？”
- “这块是正式能力还是实验？”

用户确认后应稳定保存，后续扫描不得反复推翻。界面不暴露分类器、规则来源或内部图模型。

### P2：补齐反馈与交付证据

项目是否生长不能只由代码和测试判断。后续可把 Issue、发布、用户反馈和真实使用信号挂到能力上，形成：

```text
计划中的能力
  -> 代码落点
  -> 验证证据
  -> 发布
  -> 用户反馈
```

这条链完整后，“已成形”才真正接近产品判断，而不只是工程判断。

## 不建议优先做的方向

- 不优先增加更多统计卡、评分、热力图或图算法。
- 不把项目生长图做成可自由拖拽的通用架构绘图工具。
- 不让用户维护一套独立于路线图的能力清单。
- 不把所有扫描异常都提升为用户任务。
- 不用单一健康分数掩盖“能力、证据、风险、反馈”之间的差异。
- 不先接入更重的外部 CodeGraph；当前瓶颈是已有事实没有形成用户判断，而不是缺少更多结构数据。

## 下一次产品切片

下一次最窄且完整的切片应是：

1. 在首屏真正渲染现有 `insight` 和 `capabilityHealth`。
2. 只显示一个最高优先级动作。
3. 让该动作可以打开对应的现有路线图环节。
4. 将模块矩阵、架构关系与统计移到证据区或默认折叠区。
5. 用真实项目快照验证：用户能否在十秒内回答“项目长到哪里、哪里没长成、现在做什么”。

这一步不要求改变数据模型，能直接验证项目生长图的产品主语是否已从代码结构转向项目能力。

## 2026-07 首轮闭环

首轮产品切片已经落地：

- 项目洞察、能力健康和最高优先级建议进入首屏。
- 建议可以打开并聚焦既有路线图环节，不建立平行任务系统。
- 模块协同改为“行调用列”的真实依赖矩阵，并给出协同枢纽、最强调用链和孤立模块判断。
- 架构与验证盲区成为独立大矩阵，逐个真实模块显示文件、代码行、直接测试关系和覆盖状态。
- 原有模块面积图保留为代码落点证据，不再承担协同关系和验证覆盖判断。

后续判断应以真实项目渲染结果为准：如果依赖矩阵仍出现大量空白或模块命名含糊，应优先修正模块聚合与依赖证据，不通过视觉装饰掩盖数据问题。

## 验收标准

项目生长图的下一版不以“展示了更多数据”为成功，而以以下结果为准：

1. 用户打开页面后不需要理解模块分类就能说出项目当前状态。
2. 用户能看见计划与真实落地之间的差距。
3. 用户能辨认最需要推进的一项能力及其证据。
4. 用户能从建议直接回到既有路线图推进路径。
5. 代码结构、运行历史和统计只用于支撑判断，不再充当页面主语。
