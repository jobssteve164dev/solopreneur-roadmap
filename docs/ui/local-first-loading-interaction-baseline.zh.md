# SoloMap 本地优先加载交互体验基线

## 这份文档解决什么判断

这份文档是 SoloMap 后续所有数据加载、缓存、初始化、项目切换、对话启动和大图优化的交互验收基线。

它只回答三件事：

- 用户做出一个动作后，什么时候必须看到可用结果。
- 什么才算该动作已经完整完成，而不是只显示了骨架或 loading。
- 哪些工作可以进入前台主路径，哪些工作必须退到后台。

后续实现不得用“已经创建面板”“已经显示 loading”“已经发出异步请求”代替本文件定义的完成标准。底层可以使用缓存、索引、SQLite、CSV、内存快照或其他方案，但不能改变用户动作、时限和完整结果定义。

## 第一性原则

SoloMap 是本地数据优先的行动工具。用户已经保存在本地的数据，必须优先直接支持用户继续工作，而不是先完成系统自检、迁移、扫描、聚合或外部刷新。

统一顺序是：

```text
接受用户动作
→ 保持并确认用户刚完成的选择或输入
→ 显示该动作所需的本地核心数据
→ 完成该动作的本地完整数据
→ 在不打断用户的前提下补充衍生数据和外部数据
```

任何优化如果只是更早显示骨架，却让真实任务、设置、对话或大图数据仍然超时，不算达标。

## 统一计时口径

所有时限从用户动作发生的同一时刻开始计时，不从扩展收到消息、面板创建、数据库打开或请求发出时重新计时。

| 名称 | 起点 | 终点 |
| --- | --- | --- |
| 动作开始 | click、Enter、项目选择或 VS Code 首次 resolve 侧边栏 | 记录统一 `interactionId` 和单调时钟时间 |
| 界面可用 | 用户目标区域已经出现，关键按钮、选择和滚动可操作 | 不能只是空白页、不可操作骨架或无限 loading |
| 核心数据完成 | 用户完成当前动作必需的数据已经显示 | 例如任务卡片、设置、目标项目最近对话、路线图节点 |
| 完整数据完成 | 本动作契约内规定的全部本地数据已显示且状态一致 | 不包括明确标为后台增强的数据 |
| 后台增强完成 | 衍生分析或外部信号更新 | 不计入前台完成，也不得重置用户状态 |

计时必须使用单调时钟。每个动作只允许一个开始时间和一个完成判定，禁止每进入一层函数就重新开始计算时限。

## 总体时限契约

| 用户动作 | 界面要求 | 完整完成要求 | 硬时限 |
| --- | --- | --- | --- |
| 插件冷启动 | 侧边栏可操作 | 当前项目任务卡片和已保存设置全部显示 | 15 秒内 |
| 切换侧边栏项目 | 新项目选中态立即成立 | 目标项目任务卡片与最近一次对话数据一致 | 5 秒内 |
| 从任意入口发送对话 | 输入已被系统安全接收，终端可见 | 对应 Agent 终端进程已就绪，正式命令已被接收并开始执行 | 5 秒内 |
| 打开路线图等大图 | 目标大图可操作 | 目标项目的大图本地数据全部显示 | 10 秒内可用，20 秒内完整 |
| 大图打开时切换项目 | 大图明确切到目标项目 | 大图、侧边栏和对话数据全部属于同一目标项目 | 10 秒内完整切换 |

这些是上限，不是建议值。任何一次超过上限都应留下可定位的性能记录。

## 一、插件冷启动体验

### 用户目标

用户打开 SoloMap 后，可以立即判断当前项目状态、看到任务卡片，并确认自己的设置仍然有效。

### 15 秒内必须完整出现

- 当前选中项目。
- 当前项目全部路线图任务卡片及其最新本地状态。
- 项目卡片完成主要行动所需的本地摘要。
- 已保存的语言、默认 Agent、模型偏好、全局指令、数据路径、复核方式和自动化设置。
- 可以立即使用的项目切换、设置、任务推进和 Solo 入口。

### 不属于冷启动完成条件

- GitHub Issue、PR、Release、安全告警的远端刷新。
- 全部项目的深度投入统计。
- 项目成长重新扫描。
- Agent CLI 版本探测、登录探测和模型目录刷新。
- 历史数据迁移、旧运行补索引和全局经验聚合。

这些内容可以先显示已有本地缓存，随后静默更新。它们失败或超时不能阻止侧边栏完成。

### 交互要求

- 设置在本地值到达后一次性稳定呈现，不得先显示默认值再跳成用户值。
- 任务卡片到达后不得因为组合数据、外部数据或统计数据更新而整体重建。
- 用户在冷启动期间已经展开、输入或选择的状态不得被后续回包重置。
- 同一份初始数据只允许一个主请求；宿主主动推送和 Webview 主动拉取不能形成两套并行初始化。

## 二、侧边栏项目切换体验

### 用户目标

用户选择项目 B 后，整个侧边栏立即以项目 B 为当前权威对象，并在 5 秒内恢复项目 B 最近一次工作现场。

### 动作顺序

```text
用户选择项目 B
→ 项目 B 选中态立即成立
→ 保留项目 B 已缓存的卡片、草稿、展开和滚动状态
→ 一次性读取项目 B 本地核心快照
→ 同一次提交更新任务卡片与最近一次对话
→ 后台补充项目组合与外部信号
```

### 5 秒内必须完整出现

- 项目 B 的名称、选中态和项目级操作。
- 项目 B 的任务卡片及最新本地状态。
- 项目 B 最近一次 Solo 对话。
- 项目 B 最近一次路线图任务对话；如果最近一次是续聊，应恢复到所属主对话。
- 项目 B 对应的输入草稿、附件、展开态和滚动位置。

### 一致性要求

- 一次项目切换只有一个 `projectGeneration`。
- 所有回包必须携带目标项目和 generation；旧项目或旧 generation 的结果只能进入自身缓存，不能更新当前界面。
- 任务卡片与最近对话必须来自同一个本地快照版本，不能先显示项目 B 卡片、再短暂显示项目 A 对话。
- 同一项目的对话快照只允许一个 in-flight 读取，前端和扩展端不得重复打开数据库。
- 持久化选中项目、run-index 补齐、全部项目组合重算和外部刷新不能阻塞这 5 秒。

### 空状态

目标项目没有路线图或对话时，应明确显示真实空状态。空状态也是完成结果，不能继续保持 loading。

## 三、任意对话入口发送体验

### 覆盖范围

“任意入口”包括：

- 侧边栏任务推进。
- 侧边栏 Solo、Flow、项目继续和 Issue 交给 Agent。
- 路线图环节对话、Solo、Flow 和路线图调整。
- 续聊、重试和 Continue Turn。
- 时间计划生成。
- 命令面板、内部命令、定时自动化和远程控制触发的 Agent 对话。

入口不同，终端启动体验必须相同。

### 5 秒内必须完成

- 系统已经接收这次发送，并生成稳定的本地启动身份。
- 对应项目的集成终端已经创建、显示并获得焦点或明确可见。
- 终端明确对应本次对话，而不是无法归属的通用“准备中”终端。
- 终端进程已经就绪，正式 Agent 命令已经由该终端接收并开始执行；只创建窗口或把命令交给尚未启动的 Shell 不算完成。
- 用户原输入只有在本地接收成功后才清空；启动失败时必须可以恢复。

“已经显示一个准备终端”可以满足终端可见要求，但不能掩盖正式命令尚未发送。界面应区分：

```text
已接收 → 正在准备 → Agent 已启动 → 运行中
```

### 命令窗口兼容性基线

- 所有由 SoloMap 创建并自动输入命令的终端必须复用同一个终端就绪门，不允许各入口直接调用 `sendText`。
- 终端就绪至少以宿主返回终端进程身份为准；正式命令不得依赖“窗口已经显示”或“createTerminal 已返回”推断 Shell 可以接收输入。
- 同一终端上的准备提示和正式命令必须串行排队，严格保持创建顺序；Shell 延迟启动时不得丢失、倒序或重复执行。
- 兼容不提供终端进程身份的旧宿主时可以使用明确的降级路径，但不得让该降级改变支持 `processId` 的 VS Code/code-server 主路径。
- 禁止用固定 sleep 猜测 Shell 启动时间；宿主变慢时应继续等待真实就绪信号，而不是提前失败或静默丢命令。
- 对话、续聊、重试、自动化、每日复核、技能/MCP/增强安装、CLI 检查和 GitHub 登录检查都属于同一命令窗口兼容边界。

### 不得阻塞终端显示的工作

- 项目选择持久化。
- SQLite 初始化或全量同步。
- 全部项目卡片重算。
- Git status、add、commit 或备份。
- CLI 登录和版本探测。
- Prompt 增强、历史召回、远端上下文和项目扫描。

这些工作需要启动前完成时，应在已经显示的本次终端中继续准备，并分别记录耗时；不能把用户留在没有终端反馈的界面里。

### 失败体验

- 项目无效、CLI 缺失或自动化不可用时，终端和原入口必须显示同一个可行动错误。
- 失败不能吞掉输入、附件或所选模型。
- 同一次发送只能创建一个终端；重复 watcher、回包或点击防抖不能生成重复终端。

## 四、路线图等大图打开体验

### 覆盖范围

- 单项目路线图大图，包括路线图、Solo 和 Flow 标签。
- 项目成长大图。
- 战略金字塔等组合大图。
- 后续新增的同等级全屏或大画布视图。

### 10 秒内界面可用

- 正确的视图标题、目标项目和导航已经出现。
- 返回、切换、设置、刷新和主要滚动区域可操作。
- 已有本地快照时直接显示快照，不得先替换成 loading。
- 没有快照时显示稳定骨架或真实空状态，并明确数据仍在加载。
- 用户可以关闭或切换项目，不被扩展宿主的同步扫描冻结。

### 20 秒内数据完整

路线图大图：

- 当前项目全部路线图节点、状态、依赖和当前标签页数据。
- 当前视图需要的最近对话和 Flow 状态。
- Solo 历史首屏只加载最新一页；旧对话由用户点击“加载更多”后按页追加。首屏完整不等于一次性读取全部历史。
- 每页查询必须在本地存储层限制数量，不能先读取全部历史再由 Webview 截断。

项目成长大图：

- 最近一份可用的本地成长快照、模块、能力、关系和差异数据。
- 重新扫描不是打开视图的完成条件；没有快照时，首次扫描也必须受 20 秒预算约束。

战略金字塔：

- 当前已登记项目的本地战略快照和用户做判断需要的组合数据。
- 授权检查必须使用本地状态完成首屏判断，远端授权刷新不能阻塞面板。

### 扫描与外部进程边界

- 文件全量扫描、Git 历史、dependency-cruiser 和其他外部进程不得同步阻塞扩展宿主。
- 单个子步骤的超时时间必须小于整个 20 秒预算，并为最终组装与渲染预留时间。
- 到达预算时不能无限 loading；必须显示最近快照或可行动的失败状态，并记录未完成的数据部分。

## 五、大图打开时切换项目

### 用户目标

用户在侧边栏选择项目 B 后，已经打开的大图也切换到项目 B；10 秒后侧边栏和大图不再存在项目混用、旧数据覆盖或无限 loading。

### 统一切换事务

侧边栏与所有已打开大图共享同一个项目切换身份：

```text
projectPath + projectGeneration + interactionId
```

项目选择是唯一权威动作。侧边栏、路线图、成长图和 Flow 不得分别发起互不关联的项目切换。

### 10 秒内必须完成

- 侧边栏项目 B 的任务卡片和最近一次对话完成。
- 路线图大图显示项目 B 的节点、状态和当前标签页数据。
- 项目成长大图显示项目 B 的最近快照或明确空状态。
- 所有标题、项目选择器、操作按钮和后续发送动作都指向项目 B。
- 项目 A 的迟到结果不能覆盖项目 B。

### 状态保护

- 项目 A 和项目 B 分别保存输入草稿、附件、展开态、滚动位置和选中的标签页。
- 切换期间不清空用户尚未发送的输入。
- 数据更新尽量做局部提交，不整体替换 HTML 或重建全部卡片。
- 如果某个大图子数据失败，其他已经完成的区域保持可用；整个界面不能退回全屏 loading。

### 输入中的后台刷新

- 用户正在侧边栏输入框输入或使用中文输入法组词时，后台设置、节点、对话、统计和外部数据回包不得替换输入框所在 DOM。
- 后台刷新先更新内存状态，等输入框失焦后再合并到界面；不能用“重建后恢复 value”代替焦点、光标和输入法状态保护。
- 用户主动发送、切换输入模式或切换项目仍按对应用户动作立即执行，不受后台刷新延迟约束。

## 数据优先级

| 层级 | 数据 | 前台规则 |
| --- | --- | --- |
| L0 用户状态 | 当前项目、输入、附件、焦点、展开、滚动、标签页 | 立即生效，任何异步结果不得覆盖 |
| L1 本地核心事实 | 设置、roadmap.csv、最近对话索引、Flow 当前状态、最近大图快照 | 必须进入硬时限主路径 |
| L2 本地衍生数据 | 投入统计、文档统计、组合排序、成长重算、经验聚合 | 只能在不影响 L0/L1 时补充 |
| L3 外部数据 | GitHub Issue、PR、Release、安全、远端授权刷新、模型发现 | 后台更新，失败不影响本地完成 |

任何字段如果只是为了 L2/L3 完整，却拖慢整个卡片或大图，必须拆成局部更新。

## 加载协调协议

第二轮加载机制审计确认，仅有“缓存、分批和异步”仍不足以保证体验。只要读取触发点、更新语义和结果归属不唯一，分批结果就可能互相覆盖，后台回包也可能让已经稳定的界面突然重建。

所有插件内数据视图统一遵守以下协议。

### 1. 渲染函数必须是纯消费端

- `render`、事件绑定、卡片展开、语言切换和焦点恢复不得顺带发起数据读取。
- 数据读取只能由明确动作触发：首次打开、项目切换、用户手动刷新或已确认的业务状态变化。
- 同一次渲染无论执行多少次，都不能增加数据库打开、磁盘扫描、外部请求或定时任务数量。
- TTL 只能判断一次明确读取是否可复用，不能把普通重绘变成隐式轮询器。

### 2. 完整快照与部分更新必须使用不同语义

- 完整快照可以替换对应作用域的已有数据。
- 部分更新只能按稳定身份合并；未出现在回包中的项目、卡片或字段表示“本次没有更新”，不表示删除或清空。
- 项目确实被移除时，以项目注册表中的稳定项目集合为准清理，不得通过一次不完整的组合数组推断删除。
- 本地核心状态更新不得清空已经可用的投入统计、Issue、PR、交付、安全或其他后台增强字段。
- 后台增强只能更新自己负责的字段，不能携带旧核心快照覆盖更新后的任务状态。

### 3. 每份数据只有一个触发责任方

| 数据 | 唯一前台触发方 | 允许的后台更新 | 禁止 |
| --- | --- | --- | --- |
| 侧边栏项目与核心卡片 | 扩展宿主 | 已确认的本地任务状态变化 | Webview 初始化再并行拉取同一份数据 |
| 当前项目对话首屏 | 项目选择事务 | 对话开始、结束或手动刷新 | 每次卡片重绘、展开或异步回包后重读 |
| 节点与 Flow 当前状态 | 当前项目 SyncEngine | 对应状态写入完成 | 旧项目 watcher 更新当前项目 |
| 设置与能力 | 一次显式设置读取 | 设置保存、安装或卸载完成 | 普通项目刷新重读或覆盖设置 |
| Issue、PR、交付与安全 | 首次缓存补充或手动刷新 | 对应外部请求的局部结果 | 本地任务状态变化后重启整批外部刷新 |
| 生长图与战略组合 | 对应大图打开或手动刷新 | 明确的后台重算结果 | 侧边栏普通重绘触发扫描 |

### 4. 同一作用域必须 single-flight

- 同一项目的对话快照在任一时刻只允许一个数据库读取 Promise。
- 同一轮本地项目状态变化先合并触发原因，再执行一次核心重算；连续 watcher、poller 和状态回调不得重复启动整批加载。
- 手动刷新可以使缓存失效，但如果相同作用域已经在读取，应复用进行中的读取，不得并行打开第二份数据库。
- 只有最新请求可以写入缓存并提交界面；较早请求即使完成，也只能被丢弃。

### 5. 项目切换与后台回包分离

- 项目选中态由用户动作立即决定，不能等待宿主持久化或数据库初始化。
- 后台回包可以更新其目标项目的内存缓存，但只有目标项目仍是当前项目时才能触发当前界面提交。
- A → B → A 的第二次 A 是新的选择事务；第一次 A 的迟到回包不能因为项目路径相同就获得提交权。
- 项目切换不得重新启动与目标项目核心恢复无关的全部项目外部加载。

### 6. 后台更新不得制造“整页刷新”

- 已经显示完整项目组合后，单项目核心更新必须保留其他项目卡片；不允许先缩成一个项目再逐个长回来。
- 后台组合统计和外部字段使用按项目、按字段更新；不会改变用户动作结果的回包应合并后再渲染。
- 用户悬停、聚焦、输入、组词、展开对话或点击操作期间，不替换其所在 DOM。
- 没有真实数据变化时不得重绘；有局部变化时不得把未变化区域退回 loading 或空状态。

### 7. 对话动作的响应与数据刷新解耦

- 点击续聊、重试或发送后，原按钮必须立即进入明确的进行中状态，并阻止同一次动作重复提交。
- 终端创建和可见反馈先于项目初始化、数据库准备、Git 备份与 Prompt 组装。
- 对话动作开始后的历史更新由宿主在写入本地运行记录后主动推送；前端不得同时猜测时机并再次拉取旧历史。
- 动作准备失败时，按钮恢复可操作，输入和附件保持，错误指向本次动作。

### 本轮机制审计结论

| 链路 | 审计发现 | 基线要求 |
| --- | --- | --- |
| 本地项目卡片刷新 | 分批核心结果曾可作为完整数组提交，未完成的其他卡片会暂时消失 | 部分结果只按项目合并，已显示卡片保持 |
| 卡片组合增强 | 本地状态刷新结束后曾会再次启动整批外部数据加载 | 本地刷新只更新核心与必要的本地衍生字段 |
| 最近对话 | 对话读取曾由卡片渲染隐式触发，TTL 到期后普通重绘也会打开数据库 | 项目切换由宿主推送一次快照，渲染零读取 |
| 发送与续聊后的历史 | 前端主动读取和宿主写入后推送曾可能并行并乱序 | 宿主写入后单向推送，前端不抢跑 |
| 后台项目增强 | 旧批次可携带整份旧组合结果 | 每个回包声明实际更新的项目，只合并该项目 |
| 续聊反馈 | 实际准备工作可见前，原卡片缺少稳定的动作反馈 | 点击立即锁定本次动作并显示“正在续聊” |

## 加载状态设计

每个用户动作最多使用四种用户可理解状态：

- `正在打开`：界面尚未可操作。
- `本地数据加载中`：界面已可操作，核心本地内容仍在到达。
- `已就绪`：本动作要求的完整本地数据已显示。
- `部分数据未更新`：后台增强失败，但核心功能可用。

禁止使用无法结束的通用“加载中”，也禁止把数据库、迁移、扫描器或对象名暴露给用户。

## 性能观测与验收

### 每个动作必须记录

- `interactionId`
- 动作类型
- 目标项目和 generation
- 动作开始时间
- 界面可用时间
- 核心数据完成时间
- 完整数据完成时间
- 使用了内存、本地快照还是重新计算
- 超时步骤和耗时最长的三个本地阶段
- 是否发生重复请求、旧结果丢弃或用户状态恢复

记录保存在本地诊断数据中，不上传项目内容、Prompt 或对话正文。

### 必测场景

1. 插件宿主首次启动，包含多个登记项目。
2. 当前项目有大体积 SQLite 和大量历史对话。
3. 连续快速切换 A → B → C → A，故意让回包乱序。
4. 用户在加载过程中输入、粘贴附件、展开卡片并滚动。
5. 路线图已打开时切换项目。
6. 项目成长图缓存命中和缓存未命中。
7. Git 仓库大、Git status 慢或 Git 不可用时发送对话。
8. CLI、模型发现和 GitHub 网络不可用。
9. 从每一种对话入口发送，并验证 5 秒内只有一个正确终端。
10. 数据为空、损坏或迁移失败时进入明确终态，不无限 loading。
11. Solo 历史超过一页时，首屏只读取固定页大小，后续页面按顺序追加且不重复。
12. 用户持续输入和中文输入法组词期间故意让设置、节点、对话与外部数据乱序返回，输入框 DOM、焦点、光标和组词状态保持不变。
13. 设置首次读取后再安装或卸载技能，能力扩展列表必须重新读取对应全局技能库，不得回放旧缓存。
14. 已有两个以上完整项目卡片时，仅让其中一个项目的本地状态刷新，其他卡片及其外部字段全程不消失。
15. 侧边栏稳定停留超过对话缓存 TTL 后，触发语言更新、外部字段回包和普通重绘，断言没有新增对话数据库读取。
16. 对话启动时故意让宿主推送新快照晚于前端重绘，断言只有宿主触发一次历史更新，旧历史不能覆盖新运行。
17. 连续触发同一项目的 watcher、poller 和状态完成回调，断言核心重算被合并且不会重启外部数据整批加载。
18. 故意延迟终端 Shell 进程创建，断言就绪前没有输入，进程就绪后准备提示与正式命令按顺序各执行一次，并且最终运行脚本产出启动标记和运行状态。

### 通过标准

- 每项硬时限都以真实 VS Code Extension Host + Webview 的端到端计时通过。
- 测试必须主动延迟和重排设置、项目、SQLite、扫描、Git 和外部数据回包。
- 测试必须断言用户输入、附件、焦点、展开和项目归属未被异步回包破坏。
- 命令窗口链路必须有独立自动化回归：覆盖延迟 Shell、命令顺序、无 `processId` 兼容路径，并扫描所有插件创建的命令窗口不得绕过共享就绪门。
- 真实宿主验收必须直接确认最终运行脚本已经执行并产出状态文件；终端窗口出现、源码调用成功或命令字符串已生成都不能替代这一证据。
- 源码顺序断言只能作为辅助，不能替代真实墙钟与真实渲染验证。
- 任一入口超时、重复终端、旧项目覆盖或无限 loading，整项不通过。

## 后续优化的决策门禁

每一轮加载优化开始前必须回答：

1. 优化的是哪一个用户动作？
2. 该动作的开始、界面可用和完整完成分别在哪里？
3. 本轮减少了哪段前台主路径？
4. L0/L1 数据是否仍然权威且一致？
5. 是否把 L2/L3 工作移出了主路径？
6. 是否增加真实端到端时限测试？

如果不能明确回答，不得以“缓存优化”“异步化”“先显示骨架”或“减少数据库打开”宣称完成。

## 明确禁止

- 用更早显示 loading 代替完整加载优化。
- 为了保护超时而更早失败、提前熔断或隐藏真实数据。
- 冷启动同时由宿主推送和 Webview 拉取同一份数据。
- 一次项目切换并发打开多个相同数据库快照。
- 让全部项目组合重算阻塞单项目切换。
- 让外部数据、CLI 探测或远端授权阻塞本地核心界面。
- 在用户发送确认前清空不可恢复的输入。
- 用旧项目迟到结果覆盖当前项目。
- 用源码静态顺序测试代替真实 VS Code 性能验收。

## 基线结论

SoloMap 的加载体验不是“尽快出现一个界面”，而是让用户在明确上限内继续行动，并始终看到与当前项目一致的本地事实。

后续所有相关优化都必须以本文件的动作范围、时限、完成条件、状态保护和验收场景为准。若实现方案与本基线冲突，应修改实现方案；只有用户明确改变产品要求时，才允许修改本基线。
