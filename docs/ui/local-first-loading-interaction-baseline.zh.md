# SoloMap 本地优先加载交互体验基线

## 这份文档解决什么判断

这份文档是 SoloMap 后续所有数据加载、缓存、初始化、项目切换、对话启动和大图优化的交互验收基线。

它只回答三件事：

- 用户做出一个动作后，什么时候必须看到可用结果。
- 什么才算该动作已经完整完成，而不是只显示了骨架或 loading。
- 哪些工作可以进入前台主路径，哪些工作必须退到后台。

后续实现不得用“已经创建面板”“已经显示 loading”“已经发出异步请求”代替本文件定义的完成标准。底层可以使用缓存、索引、SQLite、CSV、内存快照或其他方案，但不能改变用户动作、时限和完整结果定义。

## 第一性原则

SoloMap 是本地数据优先的行动工具。用户已经保存在本地的数据，必须优先直接支持用户继续工作，而不是先完成系统自检、迁移、扫描、聚合或外部刷新。

统一顺序是：

```text
接受用户动作
→ 保持并确认用户刚完成的选择或输入
→ 显示该动作所需的本地核心数据
→ 完成该动作的本地完整数据
→ 在不打断用户的前提下补充衍生数据和外部数据
```

任何优化如果只是更早显示骨架，却让真实任务、设置、对话或大图数据仍然超时，不算达标。

## 统一计时口径

所有时限从用户动作发生的同一时刻开始计时，不从扩展收到消息、面板创建、数据库打开或请求发出时重新计时。

| 名称 | 起点 | 终点 |
| --- | --- | --- |
| 动作开始 | click、Enter、项目选择或 VS Code 首次 resolve 侧边栏 | 记录统一 `interactionId` 和单调时钟时间 |
| 界面可用 | 用户目标区域已经出现，关键按钮、选择和滚动可操作 | 不能只是空白页、不可操作骨架或无限 loading |
| 核心数据完成 | 用户完成当前动作必需的数据已经显示 | 例如任务卡片、设置、目标项目最近对话、路线图节点 |
| 完整数据完成 | 本动作契约内规定的全部本地数据已显示且状态一致 | 不包括明确标为后台增强的数据 |
| 后台增强完成 | 衍生分析或外部信号更新 | 不计入前台完成，也不得重置用户状态 |

计时必须使用单调时钟。每个动作只允许一个开始时间和一个完成判定，禁止每进入一层函数就重新开始计算时限。

## 总体时限契约

| 用户动作 | 界面要求 | 完整完成要求 | 硬时限 |
| --- | --- | --- | --- |
| 插件冷启动 | 侧边栏可操作 | 当前项目任务卡片和已保存设置全部显示 | 15 秒内 |
| 切换侧边栏项目 | 新项目选中态立即成立 | 目标项目任务卡片与最近一次对话数据一致 | 5 秒内 |
| 从任意入口发送对话 | 输入已被系统安全接收，终端可见 | 对应 Agent 终端已被创建并显示 | 5 秒内 |
| 打开路线图等大图 | 目标大图可操作 | 目标项目的大图本地数据全部显示 | 10 秒内可用，20 秒内完整 |
| 大图打开时切换项目 | 大图明确切到目标项目 | 大图、侧边栏和对话数据全部属于同一目标项目 | 10 秒内完整切换 |

这些是上限，不是建议值。任何一次超过上限都应留下可定位的性能记录。

## 一、插件冷启动体验

### 用户目标

用户打开 SoloMap 后，可以立即判断当前项目状态、看到任务卡片，并确认自己的设置仍然有效。

### 15 秒内必须完整出现

- 当前选中项目。
- 当前项目全部路线图任务卡片及其最新本地状态。
- 项目卡片完成主要行动所需的本地摘要。
- 已保存的语言、默认 Agent、模型偏好、全局指令、数据路径、复核方式和自动化设置。
- 可以立即使用的项目切换、设置、任务推进和 Solo 入口。

### 不属于冷启动完成条件

- GitHub Issue、PR、Release、安全告警的远端刷新。
- 全部项目的深度投入统计。
- 项目成长重新扫描。
- Agent CLI 版本探测、登录探测和模型目录刷新。
- 历史数据迁移、旧运行补索引和全局经验聚合。

这些内容可以先显示已有本地缓存，随后静默更新。它们失败或超时不能阻止侧边栏完成。

### 交互要求

- 设置在本地值到达后一次性稳定呈现，不得先显示默认值再跳成用户值。
- 任务卡片到达后不得因为组合数据、外部数据或统计数据更新而整体重建。
- 用户在冷启动期间已经展开、输入或选择的状态不得被后续回包重置。
- 同一份初始数据只允许一个主请求；宿主主动推送和 Webview 主动拉取不能形成两套并行初始化。

## 二、侧边栏项目切换体验

### 用户目标

用户选择项目 B 后，整个侧边栏立即以项目 B 为当前权威对象，并在 5 秒内恢复项目 B 最近一次工作现场。

### 动作顺序

```text
用户选择项目 B
→ 项目 B 选中态立即成立
→ 保留项目 B 已缓存的卡片、草稿、展开和滚动状态
→ 一次性读取项目 B 本地核心快照
→ 同一次提交更新任务卡片与最近一次对话
→ 后台补充项目组合与外部信号
```

### 5 秒内必须完整出现

- 项目 B 的名称、选中态和项目级操作。
- 项目 B 的任务卡片及最新本地状态。
- 项目 B 最近一次 Solo 对话。
- 项目 B 最近一次路线图任务对话；如果最近一次是续聊，应恢复到所属主对话。
- 项目 B 对应的输入草稿、附件、展开态和滚动位置。

### 一致性要求

- 一次项目切换只有一个 `projectGeneration`。
- 所有回包必须携带目标项目和 generation；旧项目或旧 generation 的结果只能进入自身缓存，不能更新当前界面。
- 任务卡片与最近对话必须来自同一个本地快照版本，不能先显示项目 B 卡片、再短暂显示项目 A 对话。
- 同一项目的对话快照只允许一个 in-flight 读取，前端和扩展端不得重复打开数据库。
- 持久化选中项目、run-index 补齐、全部项目组合重算和外部刷新不能阻塞这 5 秒。

### 空状态

目标项目没有路线图或对话时，应明确显示真实空状态。空状态也是完成结果，不能继续保持 loading。

## 三、任意对话入口发送体验

### 覆盖范围

“任意入口”包括：

- 侧边栏任务推进。
- 侧边栏 Solo、Flow、项目继续和 Issue 交给 Agent。
- 路线图环节对话、Solo、Flow 和路线图调整。
- 续聊、重试和 Continue Turn。
- 时间计划生成。
- 命令面板、内部命令、定时自动化和远程控制触发的 Agent 对话。

入口不同，终端启动体验必须相同。

### 5 秒内必须完成

- 系统已经接收这次发送，并生成稳定的本地启动身份。
- 对应项目的集成终端已经创建、显示并获得焦点或明确可见。
- 终端明确对应本次对话，而不是无法归属的通用“准备中”终端。
- 用户原输入只有在本地接收成功后才清空；启动失败时必须可以恢复。

“已经显示一个准备终端”可以满足终端可见要求，但不能掩盖正式命令尚未发送。界面应区分：

```text
已接收 → 正在准备 → Agent 已启动 → 运行中
```

### 不得阻塞终端显示的工作

- 项目选择持久化。
- SQLite 初始化或全量同步。
- 全部项目卡片重算。
- Git status、add、commit 或备份。
- CLI 登录和版本探测。
- Prompt 增强、历史召回、远端上下文和项目扫描。

这些工作需要启动前完成时，应在已经显示的本次终端中继续准备，并分别记录耗时；不能把用户留在没有终端反馈的界面里。

### 失败体验

- 项目无效、CLI 缺失或自动化不可用时，终端和原入口必须显示同一个可行动错误。
- 失败不能吞掉输入、附件或所选模型。
- 同一次发送只能创建一个终端；重复 watcher、回包或点击防抖不能生成重复终端。

## 四、路线图等大图打开体验

### 覆盖范围

- 单项目路线图大图，包括路线图、Solo 和 Flow 标签。
- 项目成长大图。
- 战略金字塔等组合大图。
- 后续新增的同等级全屏或大画布视图。

### 10 秒内界面可用

- 正确的视图标题、目标项目和导航已经出现。
- 返回、切换、设置、刷新和主要滚动区域可操作。
- 已有本地快照时直接显示快照，不得先替换成 loading。
- 没有快照时显示稳定骨架或真实空状态，并明确数据仍在加载。
- 用户可以关闭或切换项目，不被扩展宿主的同步扫描冻结。

### 20 秒内数据完整

路线图大图：

- 当前项目全部路线图节点、状态、依赖和当前标签页数据。
- 当前视图需要的最近对话和 Flow 状态。

项目成长大图：

- 最近一份可用的本地成长快照、模块、能力、关系和差异数据。
- 重新扫描不是打开视图的完成条件；没有快照时，首次扫描也必须受 20 秒预算约束。

战略金字塔：

- 当前已登记项目的本地战略快照和用户做判断需要的组合数据。
- 授权检查必须使用本地状态完成首屏判断，远端授权刷新不能阻塞面板。

### 扫描与外部进程边界

- 文件全量扫描、Git 历史、dependency-cruiser 和其他外部进程不得同步阻塞扩展宿主。
- 单个子步骤的超时时间必须小于整个 20 秒预算，并为最终组装与渲染预留时间。
- 到达预算时不能无限 loading；必须显示最近快照或可行动的失败状态，并记录未完成的数据部分。

## 五、大图打开时切换项目

### 用户目标

用户在侧边栏选择项目 B 后，已经打开的大图也切换到项目 B；10 秒后侧边栏和大图不再存在项目混用、旧数据覆盖或无限 loading。

### 统一切换事务

侧边栏与所有已打开大图共享同一个项目切换身份：

```text
projectPath + projectGeneration + interactionId
```

项目选择是唯一权威动作。侧边栏、路线图、成长图和 Flow 不得分别发起互不关联的项目切换。

### 10 秒内必须完成

- 侧边栏项目 B 的任务卡片和最近一次对话完成。
- 路线图大图显示项目 B 的节点、状态和当前标签页数据。
- 项目成长大图显示项目 B 的最近快照或明确空状态。
- 所有标题、项目选择器、操作按钮和后续发送动作都指向项目 B。
- 项目 A 的迟到结果不能覆盖项目 B。

### 状态保护

- 项目 A 和项目 B 分别保存输入草稿、附件、展开态、滚动位置和选中的标签页。
- 切换期间不清空用户尚未发送的输入。
- 数据更新尽量做局部提交，不整体替换 HTML 或重建全部卡片。
- 如果某个大图子数据失败，其他已经完成的区域保持可用；整个界面不能退回全屏 loading。

## 数据优先级

| 层级 | 数据 | 前台规则 |
| --- | --- | --- |
| L0 用户状态 | 当前项目、输入、附件、焦点、展开、滚动、标签页 | 立即生效，任何异步结果不得覆盖 |
| L1 本地核心事实 | 设置、roadmap.csv、最近对话索引、Flow 当前状态、最近大图快照 | 必须进入硬时限主路径 |
| L2 本地衍生数据 | 投入统计、文档统计、组合排序、成长重算、经验聚合 | 只能在不影响 L0/L1 时补充 |
| L3 外部数据 | GitHub Issue、PR、Release、安全、远端授权刷新、模型发现 | 后台更新，失败不影响本地完成 |

任何字段如果只是为了 L2/L3 完整，却拖慢整个卡片或大图，必须拆成局部更新。

## 加载状态设计

每个用户动作最多使用四种用户可理解状态：

- `正在打开`：界面尚未可操作。
- `本地数据加载中`：界面已可操作，核心本地内容仍在到达。
- `已就绪`：本动作要求的完整本地数据已显示。
- `部分数据未更新`：后台增强失败，但核心功能可用。

禁止使用无法结束的通用“加载中”，也禁止把数据库、迁移、扫描器或对象名暴露给用户。

## 性能观测与验收

### 每个动作必须记录

- `interactionId`
- 动作类型
- 目标项目和 generation
- 动作开始时间
- 界面可用时间
- 核心数据完成时间
- 完整数据完成时间
- 使用了内存、本地快照还是重新计算
- 超时步骤和耗时最长的三个本地阶段
- 是否发生重复请求、旧结果丢弃或用户状态恢复

记录保存在本地诊断数据中，不上传项目内容、Prompt 或对话正文。

### 必测场景

1. 插件宿主首次启动，包含多个登记项目。
2. 当前项目有大体积 SQLite 和大量历史对话。
3. 连续快速切换 A → B → C → A，故意让回包乱序。
4. 用户在加载过程中输入、粘贴附件、展开卡片并滚动。
5. 路线图已打开时切换项目。
6. 项目成长图缓存命中和缓存未命中。
7. Git 仓库大、Git status 慢或 Git 不可用时发送对话。
8. CLI、模型发现和 GitHub 网络不可用。
9. 从每一种对话入口发送，并验证 5 秒内只有一个正确终端。
10. 数据为空、损坏或迁移失败时进入明确终态，不无限 loading。

### 通过标准

- 每项硬时限都以真实 VS Code Extension Host + Webview 的端到端计时通过。
- 测试必须主动延迟和重排设置、项目、SQLite、扫描、Git 和外部数据回包。
- 测试必须断言用户输入、附件、焦点、展开和项目归属未被异步回包破坏。
- 源码顺序断言只能作为辅助，不能替代真实墙钟与真实渲染验证。
- 任一入口超时、重复终端、旧项目覆盖或无限 loading，整项不通过。

## 后续优化的决策门禁

每一轮加载优化开始前必须回答：

1. 优化的是哪一个用户动作？
2. 该动作的开始、界面可用和完整完成分别在哪里？
3. 本轮减少了哪段前台主路径？
4. L0/L1 数据是否仍然权威且一致？
5. 是否把 L2/L3 工作移出了主路径？
6. 是否增加真实端到端时限测试？

如果不能明确回答，不得以“缓存优化”“异步化”“先显示骨架”或“减少数据库打开”宣称完成。

## 明确禁止

- 用更早显示 loading 代替完整加载优化。
- 为了保护超时而更早失败、提前熔断或隐藏真实数据。
- 冷启动同时由宿主推送和 Webview 拉取同一份数据。
- 一次项目切换并发打开多个相同数据库快照。
- 让全部项目组合重算阻塞单项目切换。
- 让外部数据、CLI 探测或远端授权阻塞本地核心界面。
- 在用户发送确认前清空不可恢复的输入。
- 用旧项目迟到结果覆盖当前项目。
- 用源码静态顺序测试代替真实 VS Code 性能验收。

## 基线结论

SoloMap 的加载体验不是“尽快出现一个界面”，而是让用户在明确上限内继续行动，并始终看到与当前项目一致的本地事实。

后续所有相关优化都必须以本文件的动作范围、时限、完成条件、状态保护和验收场景为准。若实现方案与本基线冲突，应修改实现方案；只有用户明确改变产品要求时，才允许修改本基线。
